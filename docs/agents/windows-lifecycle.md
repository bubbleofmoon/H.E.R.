# Windows lifecycle entry points

- Desktop QQ login polling uses authenticated `GET /api/qq/login`, even when QQ health fails. **QQ needs login** appears in the window/banner and tray only for a connected, injected SnowLuma hook with `loggedIn:false,status:"loaded"`; OneBot `online:false` alone is unknown. Contradictory or mixed-account state is unknown. OneBot `online:true` or consistent WebUI `loggedIn:true,status:"online"` confirms login. The app and tray action refresh the route, verify reported PID/start against the native QQ image, and foreground its existing visible window (restoring it if minimized). Failure to find or activate a verified window is displayed. Login observation and actions neither export a QR nor start, stop, inject or capture QQ.
- The same 30-second login-route poll raises a native Windows tray balloon when login-needed starts, including with the HER window hidden and QQ unable to send. Within the desktop session, repeated or unknown observations preserve the notification latch; only confirmed login rearms it. Native submission failure leaves it eligible for a later poll. Windows controls actual display. Saved login state is replayed after each WebView document load so sign-in/navigation retains the banner and action. Native notification display and window focus require release smoke evidence.
- Optional `snowluma.webuiUrl` is an explicit HTTP literal-loopback endpoint with a nonzero port. Provision its WebUI session token separately in selected `data/snowluma-webui-token`; this is a WebUI bearer session, never the OneBot `accessToken`. HER performs only `GET /api/processes`, never WebUI password login, session refresh, probe-login or filesystem discovery. Missing/expired credentials, failed probes and unrecognized process states remain unknown unless another supported source confirms login. No default WebUI endpoint is contacted. The existing selected OneBot endpoint/token supplies `get_status`.

- `her.exe` with no arguments (or `app`) opens a WebView2 view of the selected console and a tray. Installed images default to `<install>/runtime`; development images require `app --runtime-root <absolute root>`. `--hidden` starts only the tray. The WebView2 profile is under selected `data/desktop-webview2`; navigation stays on the selected loopback console. Issued sessions populate both console frontend stores and are renewed hourly. Closing hides the window; tray Quit exits only the desktop client.
- Desktop health consumes the existing `lifecycle assert-running` JSON every 30 seconds through a hidden CLI child: installed clients use `current/her-cli.exe`, development clients use their same-directory twin. The parent bounds its child wait to ten seconds, kills only that child through its retained handle on timeout and shows unknown health. Consumers honor the verdict's `ok` and named console part and allow additional parts. Console recovery triggers fresh sign-in. Credential transmission also verifies the connected server's native Windows user. Tray Restart uses the existing authenticated recorded restart route. The tray polls authenticated `GET /api/releases` on the same cycle. Its portable state shows current/new versions and enables approval only for a newer valid offered tag; off, unavailable and up-to-date states remain disabled. The click retains the displayed tag and posts it with confirmation to `/api/releases/approve` using the protected administrator credential. Refusal is visible and never falls back to a direct install or handover. Native rendering and hidden-window evidence belong to `docs/release-smoke.md`.
- Desktop logon is independent of the supervisor's single `HER` task. By default, an installed app launch registers `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\HERDesktop`, pointing to the stable `current/her.exe app --hidden`. With no explicit install root, desktop dispatch derives it from its verified release image and selects that root's runtime. The assembled command must fit 260 UTF-16 units before either registry or fake-store writes. Explorer starts it as the installing user without elevation. `app --register-logon` configures this entry and exits before opening the UI; real registration requires installed release images. `--run-store <data-relative file>` redirects registration to a confined atomic JSON store, preserving other entries. Installed `app --run-store <file>` registers in that fake store and continues to the UI; it does not require `--register-logon`. Use this combination for throwaway-install tray checks. Without `--run-store`, installed launches still use the real Run store. Development launches never register a real Run entry.
- PowerShell 5.1 collection consumers wrap command/pipeline results in `@(...)` before counting or indexing; `Get-Content -Raw` string lengths retain character semantics. Cache `.Handle` immediately after asynchronous `Start-Process -PassThru` when its process exit status is consumed (including returned Process objects); `-Wait` retains the handle inside the cmdlet. `scripts/test-ps-count.ps1` checks these patterns and singleton task-run matching.
- `external-path.ps1` normalizes verbatim drive/UNC paths before lifecycle helpers use PowerShell providers or launch children; device paths, ambiguous Win32 names and paths requiring long-path opt-in are refused. Package this helper beside the root launchers. Rust uses `subprocess::external_path` at external boundaries while retaining canonical paths for identity and containment.
- `her-cli install` uses the Rust task definition and native Scheduler adapter described in `lifecycle-tasks.md`. The logon action starts `current/her.exe supervise` directly with explicit install/runtime roots; the GUI image allocates no console. The old supervisor VBS/PowerShell dispatcher and task XML/deployment/restore scripts are deleted. Production switchover and changes to existing tasks remain separate operator actions.
- Lifecycle scripts select the sibling `her-cli.exe` for captured CLI commands and `her.exe supervise` for resident startup. Missing twins refuse clearly. Launcher owner checks use the resident image. Explicit GUI-image calls pipe to `Out-String` or `Out-Null` so Windows PowerShell waits and updates its exit code. `her_binaries` exercises both PE images and the stop script; seam 1 dependency tests exercise native supervisor startup. Native lifecycle fixtures package both images.
- The supervisor starts/adopts dependencies directly in Rust; `docs/agents/lifecycle-tasks.md` owns that contract. The start-all scripts, batch helpers and Rust task entry are retired.
- The owner starts the bot by hand with `her.exe supervise --runtime-root <root>`, using the installed GUI image and an absolute runtime root. For example, from PowerShell: `Start-Process -FilePath 'C:\HER\current\her.exe' -ArgumentList 'supervise --runtime-root C:\HER\runtime' -WindowStyle Hidden`. The Windows GUI subsystem keeps resident startup hidden; quote runtime paths containing spaces inside `-ArgumentList`.
- Console restart uses the authenticated Rust `/api/restart` route; the supervisor records the result in task runs.
- `restart-dsh.ps1` requires explicit paths and confirmation, reads the selected loopback DSH port from `dependencies.json`, classifies the actual Node entry point in each DSH command line while holding a process handle and rechecks the pinned identity before stopping it, and never deletes a bridge lock or scheduled task. An npx-launched child matches only its configured resolved Node entry; npm/npx package arguments confer no ownership. Restart and the Rust dependency manager defer DSH launch for up to 30 seconds while a relevant npm/npx wrapper has no resolved Node entry descendant (including through cmd); unresolved wrappers refuse launch, and proven foreign entries/wrappers are ignored without termination unless they occupy the selected port (then refused). A session reset stops the selected runtime and supervisor, invokes the guarded Rust session-map reset, and resumes after DSH is ready only if its stop revision is still current.
- Dependency recovery runs inside the Rust supervisor. `her-cli stop --runtime-root <root> --confirm` stops the bridge; `--with-dependencies` also stops the selected SnowLuma and DSH after full identity verification. `docs/agents/lifecycle-tasks.md` owns recovery and stop contracts. Session reset remains the guarded `lifecycle reset-sessions` operation on a stopped runtime.
- Memory digest jobs execute inside Rust; `docs/agents/lifecycle-tasks.md` owns their state, authentication and logging contracts.
- `scripts/test-lifecycle-fixture.ps1` takes an explicit candidate, Node executable and new temporary fixture root; it registers only a unique fixture task, uses fake loopback residents and samples its process tree for visible or foreground windows. Its opt-in `-RunLevelHighest` (`test-release-proof.py --highest`) requires an elevated interactive caller and uses that user's Interactive/Highest principal; the default remains Limited. Principal read-back is archived before the trigger is installed. The observer reads creation time and image through one limited-query process handle, excludes exited instances, retains verified descendants after parent exit and refuses live unknown identities or failed native enumeration. Native execution evidence retains the 250 ms sampling limit.
- Retain DSH restart scripts, preset/guard patches and their fixtures until #78 retires DSH (ADR 0006). Dependency patch bundles remain in the private archive and are not distributed with this snapshot; Rust does not replace those external dependencies.

## Crate contracts

QQ login state comes from SnowLuma, with unknown distinct from login-needed. `qq_login.rs` owns the read-only probes and persistent supervisor episode claim; only confirmed notice delivery marks it notified, with bounded retries surviving recovery and restarts. The administrator-only route exposes no account IDs or credentials. Desktop polling also raises a native login notification once per observed episode and replays its banner after navigation. Desktop focus uses only verified SnowLuma-reported QQ process instances; native display and activation stay manual release smoke coverage.

Desktop sign-in reads the selected token file only after native owner/ACL validation; it also requires the installing user's live loopback peer. Every successful token rotation advances the desktop session generation. Memory route credentials follow `docs/agents/social-state.md`. Tray health polls every 30 seconds, bounds each hidden CLI child independently and reports unknown on timeout. Portable tray update state binds the displayed tag to the authenticated console approval action; native menu rendering stays in release smoke coverage. Installed desktop startup infers its root from its release image; Run registration refuses commands over 260 UTF-16 units before writing. Desktop Run-store overrides and registration-only startup: see above.
