# Runtime paths and configuration

Read for runtime selection, configuration, file ownership or external process boundaries.

- `install_root.rs` owns the production layout and guards. Select an absolute root with `--install-root` or `HER_INSTALL_ROOT` (one selection only); default `C:/qqbot` on Windows (`/qqbot` elsewhere). That is the one production root: by default every production path the bridge, supervisor, backups, dependencies and the logon task resolve lies inside it; an absolute backup destination or `dependencies.directory` is the administrator's explicit choice. `her-cli install-root layout` describes `herupdate.exe`, `current`, `last-good`, `releases`, `deps/snowluma`, `deps/dsh`, `deps/relay`, `runtime`, `runtime/user/dsh` (DSH home), `runtime/dsh/work`, `runtime/data/logs` and `backups` without creating anything. Production path spellings live only in `install_root.rs`: `legacy_path!` spells the fixed-path mode's files (their old shape under the same root, until #78 retires that mode) and `legacy_dsh_home` its profile DSH home; `tests/install_root.rs` fails on a spelling anywhere else in `her/src` or `her-memory/src`, except on a line with a `// layout-literal: <reason>` comment, which is for sanitizer and test data and the `her-memory` probe until it can use the layout. This selection is separate from the legacy `tasks.installRoot` support checkout.
- Each command guards its parsed runtime selection before runtime access. A supervisor targeting the install root requires its OS-reported executable beneath that root's `releases`; other runtime commands require an installed image there too. `RuntimeContext` repeats the check after canonicalization and before layout/config access. Redirected ancestors resolving into the install root refuse even when a later parent component leaves it. This boundary prevents accidents; it does not pin handles against a local attacker. Runtime roots outside the install root (today's fixed layout) remain usable until the owner's move into the production root (#67).
- Diagnostic/probe modes and `dsh-mcp-config` are development-only even through an installed CLI. The owner's move script (#67) is the one exception: it runs `dsh-mcp-config` on a private copy outside the install root with a decoy `--install-root`, checks the result and installs it itself. Their fixed paths lie inside the default production root, so on Windows they refuse unless the selected install root is elsewhere. Guard legacy destinations, environment-selected memory databases and the selected patch file before opening them. Fixture allocators guard temporary roots and separately selected evidence/output paths before their first mutation, including media/chat evidence and the host source-transition directory.
- Fixture adapters call `her-cli install-root check-development --runtime-root <path>` before creating/removing their roots; it returns 0 when allowed and 2 with a reason on refusal. `HER_TEST_CLI` selects the built console image for script fixtures. Keep the shared check in fixture allocators, including worktree-local roots, before their first filesystem mutation.
- Launchers call `her-cli install-root check-supervisor --runtime-root <path> --executable <resident image>`. This read-only check validates the selected resident image rather than the CLI image and creates no runtime logs, locks or owner probes.

- Release installation is an explicit install-root mutation. Before configuration, current-release lookup or lock access, both the CLI install command and the install interface require the OS-reported image under the selected install root's releases directory, even with an external runtime. Restore coordination uses that installation's runtime/data/locks/update-restore.lock. Install-root and release-directory components reject symlinks, junctions and other reparse points before creation/publication. Files are create-new inside an owned staging directory; existing release images are never replaced in place. The fixed `current` link and `herupdate.exe` are outside staging.
- Release trust comes from the verified current release's signed version/key set, with shared compiled primary/backup pins at bootstrap (no versioned release folders or selection links; non-versioned local/bootstrap folders do not count). Signed checksum verification precedes image acquisition/staging and repeats for installed handover; current metadata supplies the replay floor without a separate trust-state file. Missing or invalid current metadata recovers authority from the newest verified recorded selection (last-good or an interrupted switch's previous current), then the newest verifiable installed metadata; existing versioned release folders or selections forbid compiled-pin bootstrap. No verified installed authority means refusal; only check/install admission alerts, once. The install root is the trust boundary (installed metadata self-vouches). Rollback re-verifies last-good's own metadata and images, including across key rotation, and never executes failed-current images that do not verify. Installations before the first signed release v0.1.0 are unsupported. Rotation and placeholder-key requirements are in `docs/agents/lifecycle-tasks.md`; runtime configuration and environment variables supply no trust override.

- Handover runs `<install>/herupdate.exe` from the install root; a release-local helper refuses execution. `current` and `last-good` resolve directly to versioned directories in `releases`. Windows uses junctions; a switch prepares a sibling link, renames the previous link aside, publishes the prepared link and restores the previous link on publication failure. The previous link is retained through publication and removed after a successful switch. Runtime, dependency homes and dependency working directories remain at their shared install-root paths.

- `RuntimeContext` confines selected config, data, resources, DSH credentials and dependencies to the selected root. Paths reject traversal, symlinks, junctions, reparse points and redirected ancestors. Each external endpoint must be explicit and loopback. Selected live startup requires canonical conversation keys and a selected OneBot WebSocket endpoint. No-root compatibility paths remain separate.
- Selected dependencies.json optionally accepts `relay` alongside the existing endpoints; relay launch configuration and private version-folder permissions follow `docs/agents/lifecycle-tasks.md`.
- The local voice transcription helper's origin is `config.json` `voiceTranscription.helper`, not a dependencies.json entry (a release without it ignores the member, so a rollback keeps loading); only a loopback IP origin is used (`docs/agents/media-transport.md`).
- Shared config and dependency JSON loaders accept a leading UTF-8 BOM, including config reloads and fresh runtime contexts.
- `RuntimeContext::load_config_document` reads the stored `config.json` and applies stored settings through `RuntimeContext::overlay_config`. `load_config` normalizes that document for a selected runtime. Inherited wake-plan reconciliation uses `load_config_requiring_settings`, which calls `settings::overlay_checked` directly and propagates a failed settings read. The memory, digest and schedule batch resolves its registry defaults and file values in that normalized snapshot. A Material item limit in the snapshot follows a valid configured integer recall depth when unset, with a fallback of five. Writers, the audit snapshot, the backup archive's bytes (its settings come through the overlay), the start-up validation of a fresh runtime context and the no-root legacy paths read the file itself. A cache of a value derived from the configuration is keyed on `RuntimeContext::config_stamp`, which sees only the stored file, so no registry setting may be cached on it (a registry test lists the cached members); the console's whitelist view is keyed on the settings store's mark too (`settings::store_mark`).
- The effective rollout target reads `rollout.rustGroups` from the loaded configuration. The settings overlay supplies the stored list when present. The launch target requires an explicit JSON array with one distinct canonical conversation key per item, in launch order. The suffix is a positive decimal i64 with no leading zero. An empty array selects no live owner. The same key syntax applies to each entry of the comma-separated `--live-groups` argument. Settings reset stores and mirrors an explicit empty array. Missing, null and malformed file values remain launch errors until replaced.
- Live settings (`settings.rs`, with `settings/kinds/` one file per setting kind, `settings/registry/` one table per settings group and `settings/store.rs` the store) live in `data/settings.db` of a selected runtime; a legacy context has none. It is its own SQLite file (WAL, `synchronous=FULL`, `busy_timeout` 5 s, no-follow open, sidecars checked like the database; every write holds the store gate `locks/settings-store.lock` from its inspection until its connection closes, waiting up to 5 s for it, else 503 with nothing written, so no other writer of the store can stop between a writer's inspection and its read-write open and leave a journal that open would play back; readers never take the gate; SQLite answers a switch to WAL with an immediate busy error while another connection holds a lock, so a new store is switched one writer at a time and retried for up to 5 s) with its own forward-only `user_version` (1: `settings` and the append-only `settings_audit`; 2 adds `conversation_settings`, the values kept per conversation, and a store reaches it only with its first conversation write); a newer version is refused before anything is written, and it opens no other database. Before any connection that can write opens it, the store is inspected without writing. Every store file (the database, its `-wal`, `-shm` and `-journal`, and the gate `locks/settings-store.lock`) must be a plain file with one link or missing, whether or not the database exists. A file that is not a SQLite database, a version other than 0, 1 and 2, a version 0 with any schema object and a version 1 or 2 whose `sqlite_master` is not exactly this release's schema of that version (the same objects with the same CREATE text, whitespace normalized, and nothing else) are refused. While no WAL holds later commits the version comes from the file header; otherwise a read-only connection that never checkpoints on close reads it. A leftover `-journal` (beside a missing database, or one SQLite reports hot because no connection holds the store's write lock) makes the store unusable for readers and writers alike: readers report `storeError`, a writer answers 503 with the leftover-journal message, nothing is written, recovered or copied, and the owner removes `settings.db` and `settings.db-journal`. A live writer's journal (another connection holding the write lock, as while a new store is created) is waited for, and a journal beside an empty database holds nothing to restore. So a refusal leaves the database, its WAL and its journal byte for byte (only SQLite's shared-memory index may be rebuilt). Readers read through the read-only connection; a writer keeps checkpoint-on-close off until the store is known to be usable. The registry (`settings::registry()`, the group tables joined in a fixed order; keys and pointers are unique, a registry test) is the one definition of each setting: key, configuration pointer, kind, default, when it applies, group, label, hint and whether the owner's private chat may read and change it (`chat`, `docs/agents/mcp-memory.md`). Kinds (`SettingKind`, one struct per kind that checks, reads, refuses, shows and names a value, so no code matches on a kind): an integer range (a `config.json` value outside it reads as the default, or is clamped according to the entry's file rule. Recall rounds finite file numbers and numeric strings, and the digest values that previously used JavaScript coercion still accept it in the file). An optional integer can reset to `null` to use its configured fallback, a model id (text trimmed as JavaScript trims, 1 to 200 characters, no control character; without a default it reads as not configured), model-visible text (at most the setting's count of Unicode scalar values, no control character but line feed and tab, and no denied term: the prompt text in `docs/agents/prompts-modes.md`; a `config.json` value it refuses reads as the default), a bounded number, a probability (a JSON number between zero and one with file values clamped to that range), a switch (a JSON boolean; in `config.json` only an explicit `false` reads as off, any other present value as on, a missing one as the default), an id list (at most 10000 QQ ids, each a positive safe integer or a string of digits without a leading zero, because the runtime compares ids as strings and "07001" is not 7001 there; stored as integers in first-seen order without repeats; an older alias member such as `allow.group` stands in while the pointer's member is missing or null; in `config.json` an array reads as its usable ids, a leading-zero string included among the items it skips, and anything else as empty), the owner id (a positive safe integer or a string of digits; `null`, no owner, is the default) and a daily time (`HH:MM`, 00:00 through 23:59), a time zone (`host` or an IANA database name), and a route id (an id of `harness.routes`: 1 to 64 ASCII letters, digits, `.`, `_` or `-`, never `default`, given exactly; no default, and whether it names a route of the chain is decided when each turn starts). The overlay reads the store on every load, never creates it, and applies each stored value the registry accepts at its pointer (missing or null objects on the way are created; another non-object leaves that setting unapplied); rows with an unknown key or a refused value are skipped, except that a text setting's refused value gives way to its last good version (the newest value in the global audit that the registry accepts, such as the default a reset stored; an audit row without a new value, which an undo that removes the stored value writes, ends the search) and is reported once per key and process on stderr. A store that cannot be read applies nothing and is reported once per process on stderr, so a settings problem never fails the loader. Without a stored value the file's value applies, read by the registry's rule. Its writers are the console set, reset and undo routes (actor `administrator`), the console configuration pages that save a registry setting (actor `administrator`, source `console`; `POST /api/socialV2/config` with registered reply, wake, send, tool, voice, sticker and media members and `POST /api/backups/settings` with `backup.time`: `settings::console_changes` takes each registry member the request's body carries, not `null`, whose value differs from the value in effect (the stored `config.json` the page read with the stored values applied; the file's own value is not compared, so a lagging file takes the posted value) and validates it before anything is written (400, unless the file already holds that refused value, which passes through); `console::note_config_before_request` and a canonical check of the file run before the store takes a change, so a file the runtime cannot load is 503 with nothing stored; `settings::apply_changes` stores the changes in one transaction under the configuration gate the page holds, seeded and written back like a set (503 and nothing written when the store cannot take them); the page then keeps the file's registry members as they are now and writes the rest; a member the request omits or sends as `null` is no change, and a save without a registry change runs no canonical check of its own: the console's router refuses a file the runtime cannot load (503 `runtime config is unavailable`) before any handler runs, and the handler's check covers an edit that lands after that and before the configuration gate is taken) and the owner's chat settings tools (actor `owner`, source `chat`). A page save writes one console audit record (`audit_write`, one per request): its before-state is the `config.json` the request found, taken before the store's write-back changes the file, and its after-state the file the request left. The write-back has no record of its own, so an undo of that record keeps the registry values the store holds now (`keep_registry_values`), and the setting is undone on the settings page. Readers of the settings `harness.model`, `harness.maxSteps`, `harness.maxTokens`, `harness.firstRoute`, `memory.digest.model`, `memory.digest.timeoutSecs`, `webSearch.model` and `reply.wakeQuietMs` use the registry (`Setting::read`, `integer`, `text`) for values, defaults and bounds. The normalized runtime snapshot fills reply, wake and send settings from stored, file or default values. An unrelated social save keeps registry defaults out of the file. An automatic turn-cap reset stores null and removes the file override so either release derives the cap. Timing settings that depend on each other are validated against the proposed stored and file values inside the write transaction, before commit or a file-member removal. This includes the order of the proactive check interval and wait timeout bounds. In a legacy context, the social configuration save checks turn timing only. Reply quiet triples and send timing ranges can be saved out of order, and their runtime readers use safe bounds. The prompt text settings are read by `prompt_text::text`, with the registry's check and default. `settings::apply` validates, then writes the value and one audit row (actor, source, scope, key, old and new value, request id) in one immediate transaction; the same value again writes no value and no audit row. A revision counts a setting's changes: it continues from the stored row or, without one (never set, or removed by an undo), after the setting's audit rows, so it is never reused; a seeded value is revision 1 with its one `migration` audit row, so the rule holds for seeded settings too. `settings::reset` stores the registry default (source `reset`; an empty text default is stored too), so it wins over `config.json`, and it is written back into it; a model id without a default stores `null`, written back as `null`, which every release reads as not configured. `settings::undo` takes an audit row id and, in the same transaction, refuses (409, nothing written) unless the row names a global setting the registry still has and is not a seeded copy of `config.json` (source `migration`), no later audit row names that setting, the stored value is still the row's new value and the registry still accepts the row's old value; it then restores the old value with one audit row (source `undo`), so undoing that row redoes the change. An old value of none removes the stored value and, before the commit, the setting's member from `config.json`, which held its written-back copy; a removal that fails is 503 and writes nothing, and a commit that fails after it leaves the stored value, which the overlay still applies and the next write-back puts back. An undo takes the store gate before it inspects the store; with no store yet it is 404 and creates none. `settings::history` lists audit rows newest first, 100 per page below a `before` id, through the read-only connection; no store yet is an empty list. `settings::keep_registry_values` keeps the current file's value at every ordinary registry pointer in a `config.json` that a console audit undo restores; it returns an error, and the undo refuses (409, nothing written), when a non-object in that backup would have to hold the current value; the console's write path then puts the stored values in as well. The audit undo's staleness check for `config.json` compares the record's `afterRegistryFreeSha` (the digest of the canonical document without the ordinary registry members other than the security settings, a missing, null or empty member left on their path included, `settings::registry_free`) when the record has one, so a write-back is no later change of that file; any other change still refuses it. Start-up validation reads only `config.json`: stored values are validated when written and again when overlaid. Seeding: each write (set, reset, undo, the chat tools and a console page save that changes a registry setting) first copies into the store, in the write's own transaction, every ordinary registry setting that has never been in it (no row and no audit row) and whose kind can seed a value from `config.json`, with revision 1 and one audit row each (actor `system`, source `migration`). For a clamped integer, the seed is the effective value within bounds, which an undo of its first change restores. A later write checks values that could not be seeded again, so a setting a later release adds is seeded by the first write after the upgrade and nothing is seeded twice. A write that is refused after the seed (a refused undo included) rolls the seed back with it. A write that seeds or changes only global settings leaves the schema version as it is, so a store that never held a conversation's value stays at version 1, which the previous release opens. Before that transaction, `config/config.json.pre-settings` is made from `config.json` byte for byte when missing and never replaced. A write that cannot read `config.json` as a JSON object, or cannot keep the copy (anything but a plain file there is refused and left alone), is refused with 503 before anything is stored (an undo without a store answers 404 first). Write-back (`settings::write_back`, for two releases): after each write, changed or not, every ordinary stored value is put into `config.json` at its pointer through one atomic write when the file differs, so a release without the store reads the current values (a stored `null` is written as `null`; a setting the store does not hold keeps the file's value); a member on the way that is not an object is left in place and named (`config.json cannot hold <key>`), and a file `canonical_config` refuses is not written. A failed write-back keeps the stored change (the console's set, reset and undo replies carry `mirrorError`, the chat's reply one fixed text) and is finished by the next write or by the console's start, which writes back before it notes the configuration's start stamp and answers any request, and skips the write-back gate when the store has no stored values. Gate order: every writer of the store holds the configuration gate (`console::config_gate`: the console's settings routes take it through their authority, the chat settings tools through `memory_actions::handle`) and takes the store gate inside it, never the reverse (the full order is task gate, then configuration gate, then store gate, and nothing waits for another gate while it holds the store gate; a full restore and its rollback take the store gate last, after the stop, and release it before conversation reconciliation, `docs/agents/lifecycle-tasks.md`); the write-back runs after the store gate is released, still under the configuration gate, and writers of `config.json` hold the configuration gate too. The console's one `config.json` write path (`write_selected_config_text`, the only product write of `config.json` in the console modules, a source test) never changes an ordinary registry member itself (`settings::keep_file_members`): a member the written document lacks or holds as `null` is put back from the file, and any other change of one is refused (`<key> changes only through the settings store`) with nothing written (a registry test writes every registry setting through it); it then puts the stored values in as well, so no console writer puts back an older value. While the store holds a setting, a hand edit of it in `config.json` does not apply and the next write-back replaces it. Security settings (`settings/registry/access.rs`, group `security`: `allow.private`, `allow.groups`, `deny.private`, `deny.groups`, `ownerQQ`, `security.interceptNotify`, `security.outboundGuard`, `rollout.rustGroups`; none is chat-writable): every route that changes one (the settings set, reset and undo routes, `POST /api/whitelist`, `POST /api/security`, `POST /api/conversations/scope` and the console audit undo) needs `"confirm": true` (`settings::check_confirmation`: 409 naming the setting, nothing written; `confirm` other than a boolean is 400); `her-cli conversation` confirms with its `--confirm`. A change of a list or the owner is an access change (`Setting::access`): the settings routes run it through `console::access_setting_change` (an undo looks at its entry first: only a look that names an access setting takes this path; a look that finds no entry (404) or a setting the registry lacks (409) leaves the answer to the undo under the store gate, and the plain path then refuses with 409 a security setting the look did not name, since the entry may have been created meanwhile; any other failed look is refused with that failure unless confirmed, and confirmed takes this path, which looks again) (closed-agent interaction gate, earlier pending revocations finished, configuration gate, the policy after the change computed from `settings::preview` and `RuntimeContext::effective_config_with` and recorded as a pending revocation, then the store write, then the revocation before the reply); the old routes and the audit undo store their changes (`settings::console_changes`, `settings::security_restore`) after recording the revocation, keep the file's registry members as the store wrote them back, and once the store holds a change a failed `config.json` write keeps the pending revocation; a store write that fails keeps it only when the store holds the change (`settings::holds_any`). Each security setting other than rollout is seeded only by a write of itself (with the value the next use reads: an id list's usable ids from its pointer or alias member, a blank owner as `null`), so a write of another setting never takes the access lists over from `config.json`; a `config.json` value the store cannot keep (an id list over 10000 ids, an owner that is not an id) refuses that write with 409 and nothing written, so a first change's undo always restores the file's value. `POST /api/conversations/scope` changes the list the setting reads, so a hand-edited item that is no usable id is dropped by the change and never refuses it. The write-back leaves a file member that already reads as the stored value as it is (`SettingKind::file_holds`: digit strings, an alias spelling). The owner's runtime reader applies the admin agent mode's owner after the overlay, so that owner wins while the mode is on and the stored `ownerQQ` applies in every other mode; the settings list shows it as `overriddenBy`, and a whitelist write that does not name the owner never copies it into the setting; one that names it `null` or blank changes it to no owner (the store keeps `null`), under confirmation and with its revocation computed from what is written. `config::canonical_config` still reads the lists for every access check; it admits `0`, ids above the safe-integer range and leading-zero strings (as their own strings) that the id list kind skips. Backups archive the store and a full restore replaces it (`docs/agents/lifecycle-tasks.md`).
- Rollout seeds on the first settings write that finds an explicit, well-formed file list within the effective allow lists, including stored allow values and file aliases. An absent, malformed or mismatched list stays file-backed without a migration audit row. Settings history undo returns 409 when the entry has no previous stored rollout list, keeping the explicit launch list in place. The transaction compares allow membership using the registry id-list rules. Changing membership requires the resulting rollout entries of that kind to be allowed, and changing rollout checks both kinds. A single transaction can repair a gap while a write outside the affected scope can proceed with a legacy gap. A console audit undo returns 409 if the backup would restore a legacy rollout gap, or if the backup lacks rollout and its narrower allow lists would exclude a currently served conversation. Deny remains a separate access veto.
- `harness.routes` is a global setting of kind `route list`. A valid file list is seeded on the first settings write that finds it without a row or history. The stored list preserves order and uses the runtime parser's normalized model ids and route defaults. Write-back preserves an equivalent file spelling. A reset stores and mirrors `null`, which uses `harness.model`. Invalid raw lists stay in the file until the administrator replaces or resets them. Invalid stored lists are skipped under the ordinary overlay rules. Route ids and model ids containing a stored endpoint key are refused on set and skipped on seed. The setting uses the existing global schema and history.
- Endpoint credentials are secret settings. `webSearch.apiKey` binds to the selected HTTPS search base URL and `cliModel.apiKey` binds to the selected runtime's `model` origin. Re-enter the credential after changing the endpoint. The dedicated accessor checks the exact endpoint. The config loader, seed, console config writers and mirror omit stored credentials. The legacy `webSearch.apiKey` literal is an independent compatibility source. Console config writes can replace or remove that literal, and audit undo tracks it as a regular config member. Reset clears the stored credential and allows explicit compatibility fallback.
- Tool, voice, sticker, media and alert settings are global. Their kinds own defaults and file bounds. The normalized runtime configuration fills these settings after applying stored values, while the raw overlaid document still supports reads through each setting. A scalar in place of a parent object is left in place. None of these defaults is written to disk by a read. The settings console accepts booleans for switches, bounded integers for counts and sizes, and bounded numbers for voice duration and quotas.
- Settings kept per conversation (`settings::conversation_registry()`, `ConversationSetting`, in `settings/registry/engine.rs` and `settings/registry/model.rs`; the store in `settings/store/conversation.rs`): `conversation.engine`, which falls back to the global setting `engine.default` (a choice of `dsh` or `harness`, default `dsh`, pointer `/engineDefault`, `applies` `next wake`), and `conversation.route`, which falls back to the global setting `harness.firstRoute` (a route id, no default, pointer `/harness/firstRoute`, `applies` `live`). Turn admission reads the scoped engine choice and then the global engine default (`turn_engine::Engine::selected`). For a reserved2 conversation pinned by `backends.sessions`, the CLI remains selected unless that conversation has `harness` stored in `conversation.engine`. An inherited `engine.default` never moves a pinned conversation. The model route is read when each harness turn starts (`harness::routes::selected`, `docs/agents/harness.md`) through `settings::conversation_value`, which reads one conversation's value through the read-only connection without the gate and gives none for a missing, version-1 or unreadable store, so the route reader falls back to the global setting. An unreadable engine choice refuses admission. None is chat-writable. A conversation is keyed by its canonical key (`group:<id>` or `private:<id>`, `initial_prompts::canonical_key`; the console canonicalizes what it is sent, the store refuses anything else), one row per conversation and setting in `conversation_settings`, and its audit rows carry that key as their `scope`. These values live in the store only: outside the configuration overlay and write-back. Upgrade imports admitted canonical entries from `conversationEngines` in `config.json` in one transaction, preserving existing settings and audited choices. The console configuration writer removes the old member under the configuration gate and captures the change in the write record for an HTTP request. Scoped audit history makes replay after a crash idempotent, including after access clears a choice. A malformed map refuses import. An invalid eligible value is skipped, audited as a system migration with null old and new values, and counted in a startup or import diagnostic. Its conversation follows the ordinary admission fallback, including the reserved2 CLI pin rule. The chat worker offloads legacy import to a blocking task. A conversation's value resolves as its stored value, else its global setting's value (the global setting follows the global rules: stored, then `config.json`, then the default). A changed `engine.default` moves each conversation that inherits it in a supported mode on its next admission. Each conversation has its own handover. Rows whose conversation is not canonical, whose key the conversation registry lacks or whose value it does not keep (a value its global setting accepts, or none where that setting's default is none) are skipped. Migration: a version-1 store stays at version 1 until a scoped set or reset, an explicit switch, or a nonempty legacy engine import. That write creates `conversation_settings` and sets `user_version` 2 in its immediate transaction before seeding. A crash or refusal before commit leaves version 1 intact. Undo leaves the schema version alone. A scoped reset stores the global setting's default for that conversation. A model-route reset stores JSON null, which selects the configured order whatever `harness.firstRoute` says. An undo can restore that stored null. Only an admitted conversation (`settings::conversation_admitted`: the inbound gate admits it, or it is the owner's private chat) is given a value, which the console checks under the configuration gate. Every store write that changes the stored value of an access setting (an allow or deny list, the owner; whichever route made it: `POST /api/whitelist`, `POST /api/conversations/scope`, the settings page, an audit undo) clears, in that write's own transaction, the scoped values of every conversation it leaves unadmitted. Each removal and its audit row (actor `system`, source `access`) commit together before revocation. The resulting audit entries are ineligible for undo. Admission there is decided on `config.json` as it is with the access settings that transaction holds, normalized as `load_config` does; the owner's private chat also counts by the owner setting, so the admin agent mode's owner never clears the configured owner's chat; a configuration the runtime cannot normalize clears nothing. A conversation removed by a hand edit of `config.json` keeps its value, listed as not admitted, until the next access change. Revisions, reset and undo (by audit row id through `settings::undo`, with the global rules for that conversation and setting; refused with 409 for a cleared entry, a non-canonical scope, a key the conversation registry lacks, or a version-1 store) follow the global rules per conversation; `settings::history` narrows to one conversation by its `scope`. Writers hold the configuration gate and take the store gate inside it, as every settings writer does. Console routes: `docs/agents/social-state.md`.
- `config.rs` owns runtime configuration normalization and mode aliases: `simulation` selects `reserved2`; owner IDs are positive safe integers; allow/deny aliases retain nullish precedence; missing or invalid reasoning effort becomes `max`. Stored config retains its original spellings; backup migration follows `lifecycle-tasks.md`. Writers use fresh raw config, never the effective defaults or owner overlay.
- Console authentication uses `RuntimeContext::effective_console_token`: configured token, otherwise `data/console-token`. Desktop sign-in separately requires the selected token file and validates its Windows owner/DACL; config alone cannot prove desktop identity. Generated tokens use 24 bytes of OS randomness and mode 0600; config stores an empty token. A root with neither credential refuses startup. The token file is written first under the state gate and restored if config persistence fails.
- `subprocess::external_path` converts canonical verbatim drive/UNC paths to ordinary spelling for child args/env/cwd, generated MCP config, PowerShell-readable state and displayed paths. Device namespaces, ambiguous Win32 names and paths requiring external long-path opt-in fail explicitly. Canonical paths remain the identity and containment authority.
- `her`, `her-cli` and `herupdate` attempt to clear `HANDLE_FLAG_INHERIT` on all incoming Windows standard handles at entry, before threads or children start. Absent handles are skipped; other failures never abort startup and share one best-effort stderr diagnostic naming each failed stream and OS error code. Diagnostic write failures cannot panic. They retain their own streams; Command duplicates explicitly selected child stdio. Redirecting child stdio alone does not prevent `CreateProcessW` from inheriting the parent's original pipe handles into surviving supervisors or dependencies.
- `guarded_file.rs` owns every atomic file replacement, link check and gate open. An atomic write refuses an existing target that is a link, reparse point or non-file, fsyncs a fresh sibling temporary file, replaces the target (Windows: `MoveFileExW` with write-through; only on access denied, std's POSIX-semantics rename, which has no write-through and also replaces a read-only target) and then fsyncs the parent folder on Unix; any failure before publication removes the temporary file. Only the replacement retries, on Windows access/sharing/lock violations, for at most one second; selected runtime writes revalidate containment before every attempt. Gates open read-write without truncation and never follow a final link; private gates are 0600 with a single hard link owned by the caller. State errors retain operation, path class, I/O kind and OS code without disclosing absolute paths, tokens or payloads.
- Windows data ACL hardening grants the current user, SYSTEM and Administrators before removing inherited or broad access; failed grants stop before revocation. System trustees use SIDs. Future state must remain readable by the owner and newly started MCP processes. Settings ACL changes are scoped to `data/settings.db` and its SQLite sidecars, with these same trustees and protected file DACLs.
- `her/build.ps1` writes candidate directories only. It refuses live target trees, redirected candidate components and artifacts escaping the candidate or aliasing live output. Contained Cargo hardlinks are allowed. Deployment is separate.
- Integration fixtures retain child guards through assertions, check lock contents after releasing ownership, keep fakes alive through backend deadlines and capture MCP stderr/EOF. Inbound reconnect tests witness durable admission before dropping a socket and hold history responses until live-frame progress is observed. Windows curl fakes compile from their fixture directory; PowerShell fakes import the exact built-in JSON module manifest.
- For a nonblocking loopback fixture listener, set each accepted stream's blocking mode explicitly before applying socket timeouts; Windows accepts inherit the listener mode.

## Crate contracts

Every executable attempts to clear inheritance on all incoming Windows standard handles before starting threads or children; failures never abort startup and share one nonpanicking diagnostic naming the streams and OS codes. Explicit child stdio remains supported. Process and fixture boundaries: `docs/agents/runtime-paths.md`.
