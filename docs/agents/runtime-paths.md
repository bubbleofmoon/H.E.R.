# Runtime paths and configuration

Read for runtime selection, configuration, file ownership or external process boundaries.

- `install_root.rs` owns the production layout and guards. Select an absolute root with `--install-root` or `HER_INSTALL_ROOT` (one selection only); default `C:/HER` on Windows. `her-cli install-root layout` describes `herupdate.exe`, `current`, `last-good`, `releases`, `deps/snowluma`, `deps/dsh`, `deps/relay`, `runtime`, `runtime/dsh/home`, `runtime/dsh/work` and `backups` without creating anything. This selection is separate from the legacy `tasks.installRoot` support checkout.
- Each command guards its parsed runtime selection before runtime access. A supervisor targeting the install root requires its OS-reported executable beneath that root's `releases`; other runtime commands require an installed image there too. `RuntimeContext` repeats the check after canonicalization and before layout/config access. Redirected ancestors resolving into the install root refuse even when a later parent component leaves it. This boundary prevents accidents; it does not pin handles against a local attacker. Legacy runtime roots outside the install root remain usable until switchover.
- Diagnostic/probe modes and `dsh-mcp-config` are development-only even through an installed CLI. Guard legacy destinations, environment-selected memory databases and the selected patch file before opening them. Fixture allocators guard temporary roots and separately selected evidence/output paths before their first mutation, including media/chat evidence and the host source-transition directory.
- Fixture adapters call `her-cli install-root check-development --runtime-root <path>` before creating/removing their roots; it returns 0 when allowed and 2 with a reason on refusal. `HER_TEST_CLI` selects the built console image for script fixtures. Keep the shared check in fixture allocators, including worktree-local roots, before their first filesystem mutation.
- Launchers call `her-cli install-root check-supervisor --runtime-root <path> --executable <resident image>`. This read-only check validates the selected resident image rather than the CLI image and creates no runtime logs, locks or owner probes.

- Release installation is an explicit install-root mutation. Before configuration, current-release lookup or lock access, both the CLI install command and the install interface require the OS-reported image under the selected install root's releases directory, even with an external runtime. Restore coordination uses that installation's runtime/data/locks/update-restore.lock. Install-root and release-directory components reject symlinks, junctions and other reparse points before creation/publication. Files are create-new inside an owned staging directory; existing release images are never replaced in place. The fixed `current` link and `herupdate.exe` are outside staging.
- Release trust comes from the verified current release's signed version/key set, with shared compiled primary/backup pins at bootstrap (no versioned release folders or selection links; non-versioned local/bootstrap folders do not count). Signed checksum verification precedes image acquisition/staging and repeats for installed handover; current metadata supplies the replay floor without a separate trust-state file. Missing or invalid current metadata recovers authority from the newest verified recorded selection (last-good or an interrupted switch's previous current), then the newest verifiable installed metadata; existing versioned release folders or selections forbid compiled-pin bootstrap. No verified installed authority means refusal; only check/install admission alerts, once. The install root is the trust boundary (installed metadata self-vouches). Rollback re-verifies last-good's own metadata and images, including across key rotation, and never executes failed-current images that do not verify. Installations before the first signed release v0.1.0 are unsupported. Rotation and placeholder-key requirements are in `docs/agents/lifecycle-tasks.md`; runtime configuration and environment variables supply no trust override.

- Handover runs `<install>/herupdate.exe` from the install root; a release-local helper refuses execution. `current` and `last-good` resolve directly to versioned directories in `releases`. Windows uses junctions; a switch prepares a sibling link, renames the previous link aside, publishes the prepared link and restores the previous link on publication failure. The previous link is retained through publication and removed after a successful switch. Runtime, dependency homes and dependency working directories remain at their shared install-root paths.

- `RuntimeContext` confines selected config, data, resources, DSH credentials and dependencies to the selected root. Paths reject traversal, symlinks, junctions, reparse points and redirected ancestors. Each external endpoint must be explicit and loopback. Selected live startup requires canonical conversation keys and a selected OneBot WebSocket endpoint. No-root compatibility paths remain separate.
- Selected dependencies.json optionally accepts `relay` alongside the existing endpoints; relay launch configuration and private version-folder permissions follow `docs/agents/lifecycle-tasks.md`.
- Shared config and dependency JSON loaders accept a leading UTF-8 BOM, including config reloads and fresh runtime contexts.
- `config.rs` owns runtime configuration normalization and mode aliases: `simulation` selects `reserved2`; owner IDs are positive safe integers; allow/deny aliases retain nullish precedence; missing or invalid reasoning effort becomes `max`. Stored config retains its original spellings; backup migration follows `lifecycle-tasks.md`. Writers use fresh raw config, never the effective defaults or owner overlay.
- Console authentication uses `RuntimeContext::effective_console_token`: configured token, otherwise `data/console-token`. Desktop sign-in separately requires the selected token file and validates its Windows owner/DACL; config alone cannot prove desktop identity. Generated tokens use 24 bytes of OS randomness and mode 0600; config stores an empty token. A root with neither credential refuses startup. The token file is written first under the state gate and restored if config persistence fails.
- `subprocess::external_path` converts canonical verbatim drive/UNC paths to ordinary spelling for child args/env/cwd, generated MCP config, PowerShell-readable state and displayed paths. Device namespaces, ambiguous Win32 names and paths requiring external long-path opt-in fail explicitly. Canonical paths remain the identity and containment authority.
- `her`, `her-cli` and `herupdate` attempt to clear `HANDLE_FLAG_INHERIT` on all incoming Windows standard handles at entry, before threads or children start. Absent handles are skipped; other failures never abort startup and share one best-effort stderr diagnostic naming each failed stream and OS error code. Diagnostic write failures cannot panic. They retain their own streams; Command duplicates explicitly selected child stdio. Redirecting child stdio alone does not prevent `CreateProcessW` from inheriting the parent's original pipe handles into surviving supervisors or dependencies.
- `guarded_file.rs` owns every atomic file replacement, link check and gate open. An atomic write refuses an existing target that is a link, reparse point or non-file, fsyncs a fresh sibling temporary file, replaces the target (Windows: `MoveFileExW` write-through, falling back to std's POSIX-semantics rename on access denied) and then fsyncs the parent folder on Unix; any failure before publication removes the temporary file. Only the replacement retries, on Windows access/sharing/lock violations, for at most one second; selected runtime writes revalidate containment before every attempt. Gates open read-write without truncation and never follow a final link; private gates are 0600 with a single hard link owned by the caller. State errors retain operation, path class, I/O kind and OS code without disclosing absolute paths, tokens or payloads.
- Windows data ACL hardening grants the current user, SYSTEM and Administrators before removing inherited or broad access; failed grants stop before revocation. System trustees use SIDs. Future state must remain readable by the owner and newly started MCP processes.
- `her/build.ps1` writes candidate directories only. It refuses live target trees, redirected candidate components and artifacts escaping the candidate or aliasing live output. Contained Cargo hardlinks are allowed. Deployment is separate.
- Integration fixtures retain child guards through assertions, check lock contents after releasing ownership, keep fakes alive through backend deadlines and capture MCP stderr/EOF. Inbound reconnect tests witness durable admission before dropping a socket and hold history responses until live-frame progress is observed. Windows curl fakes compile from their fixture directory; PowerShell fakes import the exact built-in JSON module manifest.
- For a nonblocking loopback fixture listener, set each accepted stream's blocking mode explicitly before applying socket timeouts; Windows accepts inherit the listener mode.

## Crate contracts

Every executable attempts to clear inheritance on all incoming Windows standard handles before starting threads or children; failures never abort startup and share one nonpanicking diagnostic naming the streams and OS codes. Explicit child stdio remains supported. Process and fixture boundaries: `docs/agents/runtime-paths.md`.
