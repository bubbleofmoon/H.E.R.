# Harness

Read before changing harness admission, model streaming, tool dispatch, engine selection or conversation storage. Decision: `docs/adr/0006-own-harness-dsh-upstream.md`; scope: the vault's `C:/her-vault/.scratch/harness/spec.md` (named by path; it is not part of this repository).

- `turn_engine.rs` is the turn-engine seam: the pipeline runs each admitted turn on one adapter (DSH, the harness, or the scripted adapter in tests), which submits the prompt, streams the turn, stops when it is cancelled and reports the turn's facts; the pipeline writes the turn timing record from those facts. Engine selection, the modes an engine runs and whether its turns need DSH are asked of the seam (`Engine`, `Adapter`), never re-derived at a call site. The DSH turn code is `pipeline/dsh_adapter.rs`, reached from `pipeline.rs` only through its registration points (the `Adapter::Dsh` arm of `run_admitted_turn` and `closed_preset` for a DSH closed-agent turn). `Pipeline::build` still sets up the DSH client (`Rpc`) and the other DSH fields in `pipeline.rs` until #13 removes DSH; retiring DSH deletes that module, `Engine::Dsh`, `Adapter::Dsh`, those registration points and that setup.
- Chat and owner-private closed-agent select `conversationEngines[conversation]`: `dsh` (also absent) or `harness`. Unknown selections fail closed. The chat worker captures the selection between turns; configuration changes cannot reroute an admitted turn. Existing DSH and CLI routes retain their contracts. Other participation drivers and the console migration switch are separate slices.
- Harness chat bypasses DSH outage queues, login, sessions, prompt submission and follow streams. The chat worker builds a harness conversation's pipeline without a DSH credential or login (`Pipeline::new_without_dsh`); every DSH call on it fails locally without contacting DSH, and a later DSH turn of that conversation builds a new pipeline with a login. Runtime-wide DSH health probes and the administrator interaction subscription remain while other conversations and jobs still use DSH, so bridge startup and health checks still require the selected runtime's DSH credential.
- `harness.rs` owns admission for a conversation generation, event subscription, status and cancellation. The pipeline owns prompt composition, permissions and delivery. Generation is the existing agent-token SHA-256 epoch. The existing turn ledger identifies harness turns; unfinished harness turns pause without DSH probing or automatic replay. Outbox uncertainty takes priority: unknown or unreadable sends pause as `send-unresolved`, and retry requires `confirm:true`. Administrator resolution cancels only that turn's running conversation-DB work before marking the bridge resolution applied; completed facts and other turns are preserved.
- `data/conversations.db` is separate from long-term memory and DSH's `data/sessions.json`. SQLite uses WAL and synchronous FULL; initialization takes `BEGIN IMMEDIATE` before reading the schema version. Sessions are scoped to conversation and generation; turns and model attempts are durable, and events are append-only. Each attempt has its own minted ID; completion updates only the active attempt and preserves prior attempt facts. Admission commits before network work; a complete assistant message commits before any reply reaches the outbox. Open turns block another admission for that conversation until cancellation or administrator resolution.
- Backup and restore of conversation storage follow `docs/agents/lifecycle-tasks.md`; restore everything includes the database, while memory-only leaves it untouched. Before full-restore startup, retained terminal ledger outcomes close restored running turns and attempts without model replay or sending; missing assistant facts are not reconstructed. Unfinished turns retain interruption/uncertain-send pauses; running or uncertain tool intents require the uncertain-effect confirmation guard even when the retained ledger has no send evidence. Canonical events and tool intents are preserved without fabricated results. Turns missing from the ledger gain a paused harness entry using their stored ID, conversation, generation and start time, so administrator abandon/retry can close their running storage through the existing resolution path.
- The model connection uses genai 0.7.3 and an explicit OpenAI-compatible Chat Completions target, streaming with the HER tools captured at admission. The turn's routes name the models ("Model routes and failover" below; a turn without a valid chain fails as not configured); the selected runtime's `model` dependency supplies the bare origin, with `/v1/` appended by the adapter. The API key comes only from `config/harness-api-key`, never an ambient environment variable, provider default or process argument. Provider errors are classified without formatting SDK error payloads; stored and relayed provider content is redacted for that key.
- Conversation schema version 2 adds attempt-linked tool runs. New user, assistant and tool-result events store canonical genai messages, including complete assistant call lists and reasoning, for replay of completed turns after restart, subject to the record masking below. Version 1 text-only facts remain readable without rewriting append-only events. Model attempts have independent lifecycle records for every step.
- The loop commits the complete assistant call list before any dispatch. Each call gets a durable start intent, then its result and canonical tool response before the next model request. Unknown tool names and invalid arguments become recorded refusals without effects. QQ sends distinguish definite refusals from uncertain delivery: a lost or unprovable response records an uncertain result and pauses as `send-unresolved` before another dispatch or model request; retry requires `confirm:true`. Duplicate call IDs within an assistant response fail closed; later model attempts may reuse provider IDs. Interrupted calls retain their unfinished intent; startup checks both the outbox and conversation storage. Running or uncertain tool intents and unreadable conversation storage pause through the existing bridge ledger as `send-unresolved`, requiring `confirm:true` before retry even without an outbox send. Completed facts replay only from completed turns; interrupted tools never replay automatically.
- Tools use HER's registered MCP names and schemas directly in process: QQ through the existing console clients, memory/settings through `memory_actions`, and auxiliary web/host handlers. No DSH MCP configuration is read. A turn's tools are its mode profile's menu (`harness/profile.rs`, one exact list per participation mode and conversation kind and per harness job: chat, the owner's chat-mode private chat, closed-agent, reserved2, the owner's reserved2 private chat, digest and slang learner), narrowed by the configuration's tool switches, the console's direct-send switches (`sendPrivate`, `sendGroup`, `reply`) included. `Tools::capture` takes the mode the pipeline admitted the turn under and refuses the turn when the current mode differs (an unreadable or missing mode file included), the harness does not run that mode or no profile serves the conversation. Every model request and every call recheck the current mode, allow-list, owner and switches: a mode or owner change revokes the turn, and the next turn captures the new menu; a switch turned off mid-turn leaves the next request's menu, and one turned back on restores only a tool the turn captured. The admission record keeps the captured menu. A call outside the menu is a recorded refusal without effect, and dispatch checks the menu again. Only the owner's profiles hold the owner-only ACL and settings tools, and no menu holds a shell, filesystem, plugin or agent tool, so harness turns do not rely on DSH's preset guard (`qq-tool-restrict`), which serves only DSH turns. Console authorization, current tool flags, mode and conversation generation remain authoritative. Validated empty session key/token fields bind to the admitted conversation; omitted or empty optional image-lookup tokens retain the existing tokenless closed-agent route. Generation is checked independently before dispatch; ambient QQ session variables are ignored. MCP image blocks persist as canonical binary image parts. Chat Completions receives them as user image content after the complete tool-response group, including on history replay; base64 is excluded from tool text.
- A turn's system message is its profile's mode prompt (`Profile::prompt_key`: chat, the owner's chat-mode private chat and closed-agent each have one; the prompt text settings in `docs/agents/prompts-modes.md`), read with the turn's configuration when `Tools::capture` runs and model-view stripped, then a blank line and the tool session line; with no mode prompt saved it is the session line alone. The system message is never stored, so an edit applies from the next turn and history replay never carries an old one. The profiles no harness turn admits (reserved2 and the jobs) have no mode prompt; the change that admits one adds its key.
- Inbound media of a chat turn are the parts the pipeline already acquires for DSH (`media::model_parts`: `[图片N]`/`[表情N]` labels and images normalized under the same count, size and pixel limits). They follow the prompt in the turn's canonical user message (`TurnRequest::user_message`): labels as text, images as binary image parts sent as Chat Completions `image_url` data URLs; the stored user event keeps `text` as the prompt alone. Voice notes reach the model only as text in the prompt (the inbound renderer's `[语音]` label); no audio is sent. Delivery filters label text like other user text and never alters image data. `harness.imageInput` (default true) is captured at admission: when false, every image part of a delivered request, inbound or from a tool, live or replayed, becomes the text `（这张图片现在看不到）`; canonical facts keep the image, so turning it back on restores replayed images. A route that refuses images while `harness.imageInput` is true fails its turns as a model/backend failure until it is set to false.
- Turn budgets are captured at admission: `harness.maxSteps` defaults to 8 (1–64), `harness.maxTokens` to 32768 (1 to 1_000_000), and the existing `socialV2.turnTimeoutSecs` covers the entire loop. Each request caps output at the remaining token budget, up to its route's `maxOutputTokens` (default 4096). Reported total usage is charged per step; missing usage is conservatively charged by UTF-8 response bytes. Exhaustion records a terminal reason; proposed calls after token exhaustion receive recorded refusals without dispatch.
- `harness.maxSteps` and `harness.maxTokens` are settings: their defaults and bounds live in the settings registry (`docs/agents/runtime-paths.md`), and a `config.json` value outside the bounds is clamped into them.
- Oversized tool results reach the model as a preview. `harness.toolResultChars` (captured at admission and recorded with the turn budgets; default 8000, 1000–100000) caps the characters of each tool response in a model request, measured after model-view filtering and memory rendering. A longer response is replaced in that request by one MCP result: the longest leading part of its text that keeps the whole copy within the cap, a note naming how many of how many characters it shows and that the rest was omitted, and the original `isError`. Canonical tool facts and tool-run records keep the whole result, so every request, history replay after restart included, previews again from the full fact. Tool images are separate parts and are not shortened. Refusal references are read from the whole filtered result before the preview is cut, so they cover the IDs the preview shows and those it omits.
- Each turn dispatches tools sequentially. Cancellation, the turn deadline and generation/authority are checked before dispatch; the existing console checks continue to guard each send. Cancellation or deadline revokes only the admitted token, then retains ownership of any dispatched synchronous handler through its existing timeout and durable result settlement. Model waits cancel promptly. The running turn blocks admission throughout settlement; a completed send remains recorded even when the bound ends the turn. An unprovable handler completion or failed result write pauses behind `send-unresolved` with its unfinished intent and confirmation guard; paused conversation-DB turns block admission until administrator resolution. No subsequent tool, model continuation or final reply runs after interruption.
- Chat replies use the existing automatic-reply policy and guarded outbox, including acknowledgement, splitting, silence, sentinel checks and deduplication. A successful QQ send tool suppresses automatic final-text relay while the final model answer remains recorded. A cancelled or invalidated generation cannot send a late reply. Tests use scripted loopback SSE, fake QQ and a recording DSH fake; no real services.
- `/reset` and `/new` also work for a harness-selected conversation with no DSH session mapping. Reset is recorded before invalidation and replaces the agent token/generation; delayed output from the old generation cannot send. A live harness holds a per-turn OS lock from admission through durable handler settlement and uncertainty publication. Reset leaves that owner to record a submitted handler's result before cancellation; an unprovable result remains paused for administrator resolution. Paused or crashed turns without a live owner resolve immediately. The running or paused turn blocks fresh admission until settled or resolved; the new generation starts with fresh history. A DSH chat reset with no session (404) is a silent no-op; other reset failures are reported to the owner.
- An active stream cancelled before completion produces no assistant reply or completed turn. A dropped stream may retry once per admitted turn, only before any validated handler dispatch. The failed attempt closes durably before a fresh attempt begins; incomplete content and tool fragments never become canonical facts. Retry consumes the same step allowance and wall deadline, preserves history and generation, offers the captured tools narrowed as for any request, and rechecks cancellation and authority. A second drop before dispatch fails over like other failures ("Model routes and failover"); a drop after dispatch ends the turn without replaying tools. Refusals, empty answers, HTTP failures and timeouts do not enter this stream-retry path. The model fixture restores blocking mode on accepted sockets before setting timeouts and can pause after emitting an SSE delta or truncate the response.

- Harness model delivery filters the current prompt, replayed chat/assistant text and chat-bearing tool text through `model_view` using current config plus the blacklist; canonical user/assistant and QQ tool data retain text removed by model-view filtering, subject to record token masking. Facts whose source text was removed before storage cannot recover it on replay. Live delivery and replay filter QQ memory `formatted`, slang `block`/`meaning`/`usage`/`example`, and `messages` strings or string arrays. Provider content-filter stops, nonempty streamed refusal deltas and refusal-shaped final prose fail before successful assistant completion or relay. HTTP quota/5xx, timeout, network and empty answers retain separate content-free failure classes. The pipeline privately reports model/backend failures through the shared notifier and refusal record format. Refusal references include structured message IDs/sequence numbers in the actual model request, including recalled QQ packets and read results; chat prose is never parsed for IDs. Harness provider identity is `openai` (the explicit OpenAI-compatible adapter). Reserved/reserved2 participation is not implemented in this slice.
- The history budget, checkpoints and the idle rotation's handover follow "History budget and checkpoints" below; the idle rotation rule (route cache life `harness.cacheTtlMinutes`, cap `harness.rotation.caps`, never the DSH settings) is `docs/agents/prompts-modes.md` "Harness idle rotation".

- Recorded memory tool outcomes keep `_meta.herMemoryResult` version 1 (`v`, registered `name`, formatter-only `args` containing `id`/`action`, and structured source `data`, subject to record token masking). No bound token or arbitrary call arguments enter this source snapshot. Each model request filters chat fields in that data before applying the shared MCP formatter, preserving generated IDs/counts, and removes the internal snapshot from the wire copy. Existing rendered-only memory facts have no structured source; field-aware regeneration of those legacy facts is unavailable. Standard MCP wire result shapes and the conversation schema version remain unchanged.

- Harness record copies mask known session tokens (including whitespace/escaped breaks) and contiguous 48-hex shapes in model/tool text, arguments, results and diagnostic raw captures before persistence. Canonical protocol references requiring masking use stable opaque aliases (`her_call_` IDs, `her_tool_` names); reserved-prefix inputs are aliased too, preserving uniqueness and call/result pairing on replay. Canonical binary bytes/URLs, MIME types and provider signatures retain their integrity; display names remain redacted. Opaque protocol data is excluded from rendered tool text. Ordinary text and provider-key masking remain unchanged. Live dispatch/delivery use originals; record masking changes no tool authority or sends. Harness diagnostics share the process diagnostic mask.

## Model routes and failover

- `harness/routes.rs` owns the candidate chain, failover, the sticky degraded route, the retry cap, the two kinds of 429, empty-answer retries and the failure classes; `harness.rs` runs every turn on it. The one-shot jobs read only the chain's first route and never fail over: the digest asks `memory.digest.model`, else that route's model; slang learning asks that route's model with its `maxOutputTokens`. Usage facts and route health (below) build on it.
- The chain, read when each turn starts: `harness.routes`, an ordered list of 1 to 8 routes `{id, model, reasoningEffort, maxOutputTokens, retry429}`. `id` is 1 to 64 ASCII letters, digits, `.`, `_` or `-`, unique in the list and never `default`; `model` follows the registry's model id rule; `reasoningEffort` is one of `zero`, `none`, `minimal`, `low`, `medium`, `high`, `xhigh` or `max` (absent or null: no effort is sent); `maxOutputTokens` is 1 to 32768 (default 4096); `retry429` is a boolean (default true). Unknown fields are ignored. Any invalid route refuses the whole list, and the turn fails as not configured with the route's position and field, never a configured value; it never falls back to `harness.model`. Without `harness.routes` (absent or null) the chain is one route whose id and model are `harness.model`, so tables keyed by that model id keep naming it. Every route uses the selected runtime's `model` relay and `config/harness-api-key`.
- Every model request, retries and failovers included, counts against `harness.maxSteps` and asks for at most the remaining token budget; no request is made once the budget is spent. A request without a usable answer is retried, failed over or ends the turn (`routes::decide`). A first 429 on an unchanged request is retried once on the same route after the response's `retry-after-ms`, else its `retry-after` in whole seconds, else 2 s, when the route's `retry429` is true, the wait is at most 30 s and it ends before the turn deadline; a repeat 429, or a 429 not retried, moves to the next route. An empty answer is retried on the same route up to 3 times, after 1, 2 and 4 s, while nothing was sent in the turn. The first dropped stream of a turn is retried at once. Any other failure moves to the next route, except that a drop, a timeout or a network failure after a validated dispatch ends the turn, and no failure moves to another route once a QQ send of the turn succeeded.
- A conversation makes at most two failovers until one of its turns completes. Its last degraded route is where its next turns start; that memory, and the spent failovers, lapse 30 minutes after its last failover, with a new generation or with any change to the chain. The memory is per runtime and process (`routes::with_memory`): a restart starts every conversation on its first route.
- Each attempt records its route id in its `model_attempt_started` event and its model in `model_attempts`. Each route request that fails over or ends the turn is reported like a failed DSH candidate: the pipeline's model/backend alert and refusal record name that route's model. Every retry, failover and final route failure goes to the run record (component `model-chain`, events `route-retry`, `failover-step` and `route-failed`) with the conversation, the route id, the content-free failure summary and the size of the request's delivered messages.
- Usage facts (`harness/usage.rs`): every model request through the route module or a one-shot job that returns a response end (an answer, an empty answer, or a refused or cut-off stop) appends one sample to the selected runtime's token ledger, `data/token-usage-rust.jsonl` (`docs/agents/sessions-recovery.md`): `k` `turn`; `key` the conversation (the digest's `internal:digest`, or the conversation a slang learning is for); `sid` `<process id>/<key>`, the process id minted once per process; `turn` a wall-clock number in ms, strictly increasing within the process (one per harness turn, one per one-shot request); `step` the request's place in its turn; `retry` the requests already sent for the same unchanged request (its retries and failovers); `seq` 0, so a repeated place is read once; `model`, `route`, `provider` and `engine` `harness`, `job` (`turn`, `digest` or `slang`); and `b`, the reported usage as buckets (hits the prompt's cached tokens, writes its cache-creation tokens, misses the rest of the prompt, output the completion tokens, reasoning shown only), or null when the response reported neither prompt nor completion tokens. A request that ends without a response end (an HTTP error, a dropped stream) records nothing. A failed write goes to the run record (`model-chain`, `usage-unrecorded`) and never fails the request. The console's token views read these samples with DSH's and price them by model at read time; `/api/usage/attribution` leaves out samples with `engine` `harness`, which DSH's own total never saw. The one-shot jobs (`harness/one_shot.rs`) record their answered requests the same way: the digest under `internal:digest` with `job` `digest`, and the slang learner under the conversation key it learns for with `job` `slang`, each on the route it asked. A refused answer is recorded before the refusal is decided.
- One-shot jobs (`harness/one_shot.rs`): the digest and slang learning each send one non-streaming Chat Completions request with no tools and no history to the selected runtime's `model` relay with `config/harness-api-key` (`ModelRoute::for_model`), bounded by the job's timeout and output cap; an empty system text is left out, so the learner's prompt is the request's only message. Failures are fixed classes (`quota`, `timeout`, `backend`, `network`, `refusal`, `unconfigured`) without provider text. They offer no tool, so the `Digest` and `SlangLearner` rows of `harness/profile.rs` are not used yet. An armed upstream capture on route `harness` takes the request (`docs/agents/prompts-modes.md`). Tests install a fake per runtime root and job (`one_shot::install_test_model`).

## History budget and checkpoints

- `harness/budget.rs` estimates a request: four ASCII characters count one token (rounded up), every other character one, each message four and each image part 1500, inbound or from a tool, live or replayed (with `harness.imageInput` false the placeholder text counts instead). A route's window is `harness.contextTokens.<route id>` (an integer from 1000 to 10 million, else 64000); its budget is the window times `harness.historyShare` (0.1 to 0.95, else 0.82, rounded to thousandths). Both are configuration keys read when each request is built, not registry settings.
- History counts in rounds: one round is one completed turn's replayed facts, or the replayed summary, so a tool call and its result are always in one round. Before every request (retries and failovers included, on that request's route) the oldest whole rounds are left out until the request is within the budget (`budget::fit`). The system instruction and the current turn (the owner's latest message and every call and result of the turn) are never left out; when they alone are over, the request still goes. In the same copy oversized tool results become previews, and a replayed assistant message with a call to a tool the request does not offer has every call turned into text (`〔我用了 …〕`) and each answering tool message turned into a user message with the result as text (`〔… 的结果〕`) and its images; calls of the current turn stay calls. Canonical facts never change; message references are read from the kept rounds before previews.
- Before the turn's first request `harness/handover.rs` checks the session. Idle rotation: the idle start is when the session's last turn ended and the evidence is `store::last_call`; once `rotation::due_at` has passed, a rotation checkpoint keeps the newest whole rounds within 4000 estimated tokens (the handover). Budget: when the replayed history with the instruction and the user message is over the start route's budget, a budget checkpoint keeps the newest whole rounds within 15% of the window. A checkpoint covers the older rounds and carries a new summary of them that folds in the earlier one, or, with `harness.summaries` false (default true), the earlier summary unchanged. A rotation is in place: generation, token and facts stay. The memory digest is not part of it.
- A checkpoint is the event `checkpoint` (`purpose` `rotation` or `budget`, `through` the sequence of the last fact it covers, `summary` text or null), appended by the running turn in one transaction with any `checkpoint_failed` (`purpose`, content-free `class`). Admission replays the newest checkpoint's summary as a user message headed `【之前聊天的摘要】` (model-view filtered like other chat, and left out like a round) and only completed turns' facts after `through`. No schema change: a database without checkpoints replays whole until its first one, and a release without checkpoints ignores the events and replays every fact.
- Summaries use the digest's model port (`memory.digest.model`, else the chain's first route, bounded by `memory.digest.timeoutSecs` and by the turn's deadline less 5 seconds (`SUMMARY_RESERVE`), where a summary still running fails as `timeout`, and one whose bound has already passed when it is asked for is not sent): a fixed prompt, the earlier summary and the model-view copy of the covered rounds as labelled lines, newest rounds first within 24000 estimated tokens, each tool result cut to 2000 characters; the system instruction is never in it. A summary is trimmed and cut to 4000 characters, and refused as `wording` when it names a #142 denied term (`settings::denied_in_text`, applied to the summary and to its input alike, so full-width and zero-width-split forms count) its own input did not. A failed or refused rotation summary leaves the session unrotated; a failed or refused budget summary still covers the older rounds with the earlier summary, and after a failed rotation summary the same turn's budget checkpoint asks for none. Run record (component `model-chain`, content-free): `history-checkpoint` and `summary-failed`.
- A cancelled or timed-out turn writes no part of a checkpoint: the summary is awaited before anything is written, a cancellation returns at once and a late answer is dropped. A cancelled or timed-out turn revokes its admitted token, so the conversation's next turn starts a new generation and session with no replayed history; its facts stay in storage. Only after a crash does the next admission of the same session check again: a turn left `running` is resolved by `harness::resolve_interrupted` (cancelled, its facts kept, no checkpoint written), and the next turn of that generation checks its history.
- Route health (`harness/route_health.rs`): every answer marks its route `ok`, and every route failure (a request that fails over or ends the turn; a miss retried on the same route is none, and a refusal is content, not a route failure) marks it `failed` with its class, in the selected runtime's `data/route-health/state.json` (changed under `data/locks/route-health.lock`, waiting at most 2 s for it, and written only when a route's state or class changes; never in backups). A state of another chain (any change to the chain) or an unreadable one (over 64 KiB included) starts over; a write that fails goes to the run record (`model-chain`, `route-health-unrecorded`) and never fails the request. When every route of the chain is failed, an outage episode starts: after a turn with a route failure, the pipeline offers the owner one notice (`admin_alert::notify_notice`, key `model-routes-all-failed`) naming the conversation, the number of routes and the last failure class, never a route id, a model, a maker or provider text. An offer claims the owed episode under the gate before it calls the notice queue (one at a time; a claim a crash left expires after one notice window), and settles it by the episode's own number, never by a time. The episode stays owed until the notice queue accepts it (a refusal releases the claim; run record `routes-all-failed`), is alerted once, and ends with any answer; the per-route alerts above continue. The health check reports each route's state beside its parts (`modelRoutes`, `docs/agents/lifecycle-tasks.md`), never as a part.
