# Harness

Read before changing harness admission, model streaming, tool dispatch, engine selection or conversation storage. Decision: `docs/adr/0006-own-harness-dsh-upstream.md`; scope: the vault's `C:/her-vault/.scratch/harness/spec.md` (named by path; it is not part of this repository).

- Chat and owner-private closed-agent select `conversationEngines[conversation]`: `dsh` (also absent) or `harness`. Unknown selections fail closed. The chat worker captures the selection between turns; configuration changes cannot reroute an admitted turn. Existing DSH and CLI routes retain their contracts. Other participation drivers, the console migration switch, failover and compaction are separate slices.
- Harness chat bypasses DSH outage queues, login, sessions, prompt submission and follow streams. Runtime-wide DSH health probes and the administrator interaction subscription remain while other conversations and jobs still use DSH. This slice requires the existing selected-runtime layout, including its DSH fixture credential; it does not retire DSH startup or health requirements.
- `harness.rs` owns admission for a conversation generation, event subscription, status and cancellation. The pipeline owns prompt composition, permissions and delivery. Generation is the existing agent-token SHA-256 epoch. The existing turn ledger identifies harness turns; unfinished harness turns pause without DSH probing or automatic replay. Outbox uncertainty takes priority: unknown or unreadable sends pause as `send-unresolved`, and retry requires `confirm:true`. Administrator resolution cancels only that turn's running conversation-DB work before marking the bridge resolution applied; completed facts and other turns are preserved.
- `data/conversations.db` is separate from long-term memory and DSH's `data/sessions.json`. SQLite uses WAL and synchronous FULL; initialization takes `BEGIN IMMEDIATE` before reading the schema version. Sessions are scoped to conversation and generation; turns and model attempts are durable, and events are append-only. Each attempt has its own minted ID; completion updates only the active attempt and preserves prior attempt facts. Admission commits before network work; a complete assistant message commits before any reply reaches the outbox. Open turns block another admission for that conversation until cancellation or administrator resolution.
- Backup and restore of conversation storage follow `docs/agents/lifecycle-tasks.md`; restore everything includes the database, while memory-only leaves it untouched. Before full-restore startup, retained terminal ledger outcomes close restored running turns and attempts without model replay or sending; missing assistant facts are not reconstructed. Unfinished turns retain interruption/uncertain-send pauses; running or uncertain tool intents require the uncertain-effect confirmation guard even when the retained ledger has no send evidence. Canonical events and tool intents are preserved without fabricated results. Turns missing from the ledger gain a paused harness entry using their stored ID, conversation, generation and start time, so administrator abandon/retry can close their running storage through the existing resolution path.
- The model connection uses genai 0.7.3 and an explicit OpenAI-compatible Chat Completions target, streaming with the HER tools captured at admission. `harness.model` names the model; the selected runtime's `model` dependency supplies the bare origin, with `/v1/` appended by the adapter. The API key comes only from `config/harness-api-key`, never an ambient environment variable, provider default or process argument. Provider errors are classified without formatting SDK error payloads; stored and relayed provider content is redacted for that key.
- Conversation schema version 2 adds attempt-linked tool runs. New user, assistant and tool-result events store canonical genai messages, including complete assistant call lists and reasoning, for replay of completed turns after restart, subject to the record masking below. Version 1 text-only facts remain readable without rewriting append-only events. Model attempts have independent lifecycle records for every step.
- The loop commits the complete assistant call list before any dispatch. Each call gets a durable start intent, then its result and canonical tool response before the next model request. Unknown tool names and invalid arguments become recorded refusals without effects. QQ sends distinguish definite refusals from uncertain delivery: a lost or unprovable response records an uncertain result and pauses as `send-unresolved` before another dispatch or model request; retry requires `confirm:true`. Duplicate call IDs within an assistant response fail closed; later model attempts may reuse provider IDs. Interrupted calls retain their unfinished intent; startup checks both the outbox and conversation storage. Running or uncertain tool intents and unreadable conversation storage pause through the existing bridge ledger as `send-unresolved`, requiring `confirm:true` before retry even without an outbox send. Completed facts replay only from completed turns; interrupted tools never replay automatically.
- Tools use HER's registered MCP names and schemas directly in process: QQ through the existing console clients, memory/settings through their existing action handler, and auxiliary web/host handlers. No DSH MCP configuration is read. Group tools exclude owner-only ACL/settings and never include shell, filesystem, plugin or agent tools. Console authorization, current tool flags, mode and conversation generation remain authoritative. Validated empty session key/token fields bind to the admitted conversation; omitted or empty optional image-lookup tokens retain the existing tokenless closed-agent route. Generation is checked independently before dispatch; ambient QQ session variables are ignored. MCP image blocks persist as canonical binary image parts. Chat Completions receives them as user image content after the complete tool-response group, including on history replay; base64 is excluded from tool text.
- Turn budgets are captured at admission: `harness.maxSteps` defaults to 8 (1–64), `harness.maxTokens` to 32768 (1–1000000), and the existing `socialV2.turnTimeoutSecs` covers the entire loop. Each request caps output at the remaining token budget, up to 4096. Reported total usage is charged per step; missing usage is conservatively charged by UTF-8 response bytes. Exhaustion records a terminal reason; proposed calls after token exhaustion receive recorded refusals without dispatch.
- Each turn dispatches tools sequentially. Cancellation, the turn deadline and generation/authority are checked before dispatch; the existing console checks continue to guard each send. Cancellation or deadline revokes only the admitted token, then retains ownership of any dispatched synchronous handler through its existing timeout and durable result settlement. Model waits cancel promptly. The running turn blocks admission throughout settlement; a completed send remains recorded even when the bound ends the turn. An unprovable handler completion or failed result write pauses behind `send-unresolved` with its unfinished intent and confirmation guard; paused conversation-DB turns block admission until administrator resolution. No subsequent tool, model continuation or final reply runs after interruption.
- Chat replies use the existing automatic-reply policy and guarded outbox, including acknowledgement, splitting, silence, sentinel checks and deduplication. A successful QQ send tool suppresses automatic final-text relay while the final model answer remains recorded. A cancelled or invalidated generation cannot send a late reply. Tests use scripted loopback SSE, fake QQ and a recording DSH fake; no real services.
- `/reset` and `/new` also work for a harness-selected conversation with no DSH session mapping. Reset is recorded before invalidation and replaces the agent token/generation; delayed output from the old generation cannot send. A live harness holds a per-turn OS lock from admission through durable handler settlement and uncertainty publication. Reset leaves that owner to record a submitted handler's result before cancellation; an unprovable result remains paused for administrator resolution. Paused or crashed turns without a live owner resolve immediately. The running or paused turn blocks fresh admission until settled or resolved; the new generation starts with fresh history. A DSH chat reset with no session (404) is a silent no-op; other reset failures are reported to the owner.
- An active stream cancelled before completion produces no assistant reply or completed turn. A dropped stream may retry once per admitted turn, only before any validated handler dispatch. The failed attempt closes durably before a fresh attempt begins; incomplete content and tool fragments never become canonical facts. Retry consumes the same step allowance and wall deadline, preserves history, tools and generation, and rechecks cancellation and authority. A second drop or a drop after dispatch ends the turn without replaying tools. Refusals, empty answers, HTTP failures and timeouts do not enter this stream-retry path. The model fixture restores blocking mode on accepted sockets before setting timeouts and can pause after emitting an SSE delta or truncate the response.

- Harness model delivery filters the current prompt, replayed chat/assistant text and chat-bearing tool text through `model_view` using current config plus the blacklist; canonical user/assistant and QQ tool data retain text removed by model-view filtering, subject to record token masking. Facts whose source text was removed before storage cannot recover it on replay. Live delivery and replay filter QQ memory `formatted`, slang `block`/`meaning`/`usage`/`example`, and `messages` strings or string arrays. Provider content-filter stops, nonempty streamed refusal deltas and refusal-shaped final prose fail before successful assistant completion or relay. HTTP quota/5xx, timeout, network and empty answers retain separate content-free failure classes. The pipeline privately reports model/backend failures through the shared notifier and refusal record format. Refusal references include structured message IDs/sequence numbers in the actual model request, including recalled QQ packets and read results; chat prose is never parsed for IDs. Harness provider identity is `openai` (the explicit OpenAI-compatible adapter). Harness failover, reserved/reserved2 participation and compaction are not implemented in this slice.

- Recorded memory tool outcomes keep `_meta.herMemoryResult` version 1 (`v`, registered `name`, formatter-only `args` containing `id`/`action`, and structured source `data`, subject to record token masking). No bound token or arbitrary call arguments enter this source snapshot. Each model request filters chat fields in that data before applying the shared MCP formatter, preserving generated IDs/counts, and removes the internal snapshot from the wire copy. Existing rendered-only memory facts have no structured source; field-aware regeneration of those legacy facts is unavailable. Standard MCP wire result shapes and the conversation schema version remain unchanged.

- Harness record copies mask known session tokens (including whitespace/escaped breaks) and contiguous 48-hex shapes in model/tool text, arguments, results and diagnostic raw captures before persistence. Canonical protocol references requiring masking use stable opaque aliases (`her_call_` IDs, `her_tool_` names); reserved-prefix inputs are aliased too, preserving uniqueness and call/result pairing on replay. Canonical binary bytes/URLs, MIME types and provider signatures retain their integrity; display names remain redacted. Opaque protocol data is excluded from rendered tool text. Ordinary text and provider-key masking remain unchanged. Live dispatch/delivery use originals; record masking changes no tool authority or sends. Harness diagnostics share the process diagnostic mask.
