# Inbound, sessions and recovery

Read for durable ingress, session mapping, turn recovery or usage accounting.

- `inbound.rs` journals allowed events before wake scheduling into `data/inbound.db` (WAL, synchronous FULL). Identity is conversation plus message ID, otherwise raw-text hash; duplicates create no second turn. Lone UTF-16 surrogate escapes are replaced with U+FFFD and logged rather than dropping the frame.
- Stages are received → processing → handled; backfilled history never wakes. Startup processing events become interrupted and run again only when turn recovery proves non-execution. On reconnect, saved received events precede new input. History runs in a blocking background task; journal work uses `SharedJournal` so ingress never waits for fsync/HTTP. Heartbeats update last-alive at disconnect rather than being journaled individually.
- Each reconnect opens gaps for allowed conversations. Only recovered closes a gap; unknown/unrecovered persist. Incomplete history is unknown. Permanent gateway refusal is unrecovered, unclear/transient failure unknown. Group history uses `get_group_msg_history` and `message_seq`; private-history-unverified gaps are terminal unrecovered (no verified private-history capability), have zero retry deadline and are excluded from automatic and manual retries. Group recovery is attempted on reconnect once its retry deadline is due; no timer runs recovery on a stable connection. Backoff is 60 seconds doubling to six hours, at most eight attempts. Admin gap retry resets attempts/deadline for retryable group windows in the selected conversation.
- Gap notices go only to the owner's private chat, without message text or gateway detail. Each conversation gets one line: new window count, overall local-time span, recovered/retrying/unrecoverable counts and an action. Private notices explain that messages may have been missed and important messages should be re-sent; the owner's own private conversation is identified plainly. Recovered-history notices explain that a reply still requires re-sending. Recovered and unresolved windows with a result are atomically claimed across opening and recovery notices before entering the bounded owner outbox. `notified_ms` records confirmed OneBot delivery only. Durable `noticeState` is pending → queued → unknown → sent; live startup returns queued windows to pending because network I/O has not begun. Immediately before sending, queued windows become unknown. A known refusal or failure proven before submission returns them to pending for a later reconnect/restart. A timeout, ambiguous reply or crash after that checkpoint leaves unknown windows visible in the console and never automatically resends them, including a confirmed send followed by a crash before marking. This conservative choice follows the OneBot/admin-alert unknown-send rule: avoiding duplicate private sends takes priority over delivery certainty in that narrow window. It cannot guarantee delivery or exactly-once messaging; a crash after the unknown checkpoint but before network submission can suppress an unsent notice. At most ten conversations are listed, fewer when redacted text would exceed the 800-character body; the true unlisted window count and `/api/inbound/gaps` pointer survive. Only windows represented by listed conversations are marked. Admission refusals and unlisted windows remain pending; queue acceptance never counts as delivery. `/api/inbound/gaps` retains all unresolved windows in `unresolvedGaps`, including `notifiedMs` and `noticeState`. Existing rows gain pending state additively; positive legacy `notified_ms` markers remain authoritative and are not resent.
- Startup interrupted-event notices identify the conversation and original event time in local time (receipt time if unavailable), without chat text. They tell the owner to re-send if no reply arrived, or do nothing if it was answered, and identify a later turn in that conversation when the turn ledger proves one. The bounded event list retains the total count and console pointer when entries are omitted. Only events newly moved from processing to interrupted produce this startup notice; another restart does not repeat it.
- Retention runs on reconnect and hourly: handled/backfilled raw frames one day, rows seven days/50,000 cap, interrupted 30 days, recovered gaps seven days. Received/processing and unresolved gaps are never pruned. Gap details stay in the authenticated console, never groups.
- `session_map.rs` is the only selected `data/sessions.json` writer: fresh locked read-modify-write, preserving unknown top-level fields. `sessions`, `sessionPolicies` and `workspaceId` are shared by console and live turns. Damaged data fails instead of creating new sessions. Guarded confirmed reset clears mappings/policies with verified backup and audit; no-root compatibility uses separate `rust-sessions.json` without a turn ledger.
- Sessions survive turns and restarts. Exact DSH session-not-found permits replacement and token revocation; admin reset cancels/archives and creates a new conversation epoch. Mode transitions retire mappings immediately; other session-policy changes retire before reuse. Unknown state never rebuilds a session.
- Harness sessions, events, attempts and generation-scoped history use a separate conversation database; see `docs/agents/harness.md`. Interrupted harness ledger entries pause without DSH probing or automatic replay. Startup includes unfinished conversation-store tool intents in the existing `send-unresolved` confirmation guard, even without an outbox send; unreadable conversation storage retains that guard.
- Turn ledger writes begun before any DSH work and attempt, with the stored RPC ID, before prompt submission. No attempt proves non-submission. Inbound keys, DSH turns, tool calls and outbox batches link to the turn. Cancelled/timed-out/replaced/unprovable turns rotate conversation tokens, invalidating late tools and sends. A layered briefing attempt also records `layers` (per-layer injected and cut item counts, `docs/agents/prompts-modes.md`).
- Only turn-worker and recovery ledger appends retry Windows sharing/lock violations (OS 32/33), using one two-second deadline across open, append-lock acquisition, tail inspection, writes and sync. Successful partial writes advance the remaining slice; a later error never restarts the record. Terminal `ended` records and notice claims sync while retaining the append lock. Retry exhaustion emits content-free diagnostics without paths or record text, then follows existing fail-closed recovery. Other errors and non-Windows I/O remain single-attempt. Scheduler/hub cancellation, closed-agent cancellation under its interaction gate, administrative reset/revocation and stopped-writer restore reconciliation disable append retries; outbox, usage, diagnostic and other runtime appends retain their prior one-shot behavior. No retrying append runs under a send-chain, token-publication, hub or tick lock. Worker shared update-admission handles, per-turn harness ownership and recovery resolution gates may remain held after handlers/storage/token mutation finish. The finalization gate is one runtime-wide lock: retrying recorders wait for it up to the two-second conflict budget, inline `without_retry` recorders try once, and an inline or closed-agent cancellation that finds it busy leaves the turn open for recovery instead of failing the cancellation. The administrative session reset holds no hub lock, so it keeps the retrying wait; a turn it still cannot settle is reported as a non-success after the remaining turns and the DSH stop/archive ran. On worker paths the terminal/claim decision read (tail fold) shares the record's two-second conflict budget (typed OS 32/33 retained; ordinary and inline-cancellation reads stay one-shot).
- Selected-runtime terminal writes, completed-end observations and cancellation intents share the cross-process `data/locks/turn-ledger-finalize.lock` gate. Each turn has at most one `ended` record. The collector durably claims a genuine completed DSH end before usage/tool bookkeeping; an observation before cancellation intent preserves collector ownership while its terminal write is pending. The collector may finalize completed or failed after classifying the result; a completed wire end containing a backend refusal/error remains failed, never an open turn. After completion observation, parity-clock bookkeeping-barrier errors emit content-free diagnostics and leave result classification unchanged. Otherwise a durable `cancel-requested` leaves finalization to the cancellation handler after token revocation; collector completion/failure cannot close that turn. The collector reports a bridge-requested cancellation as cancelled even when DSH returns an aborted end successfully. After a crash, pending cancellation revokes any authority still belonging to that turn before probing, reattaching or deferring. Unproven work stays open; once proven finished or unexecuted, recovery closes it as cancelled without replaying its input, except that a proven-finished `observationSleep` claim closes as completed.
- Completion claims are scoped to the prompt RPC attempt: the collector claims a completed end with `observe_completion(rpcId)` and either accepts it with `end_attempt` or releases it (`release_completion`) before rejection or failover; a released or foreign attempt cannot accept another result, and fold/recovery ignore released claims. A cancellation intent behind a provisional completion stays durable and its confirmed-stop decision (`cancellation-ready`) settles when the claim is released. A cap that lands inside a live messages observation is a cancellation-owned `completed` end with reason `observationSleep` (`end_cancellation`); an unconfirmed stop pauses the turn instead. Cap stop and token revocation continue when the intent or terminal write fails. Recovery keeps the active claim after DSH/outbox reconciliation, re-reads it at apply and settles through `end_reconciled`, which errors on a stale or incompatible claim before any input replay; a cancellation claim also rotates the turn's token first, and `observationSleep` closes as completed.
- Reconciliation consults DSH and the send outbox before reuse: finished closes, running/queued reattaches, provably unexecuted still-valid events return to ingress, unreachable DSH pauses and retries. Truncated logs, unresolved sends, unreadable ledgers, text-backend ambiguity and unclear errors pause and revoke authority without resubmission. Only exact session-not-found, prompt absence in an inbox, or a complete log without it prove non-execution. Persist verdict before settling/replaying. Paused conversations admit no new turn. Admin resolution is abandon/retry, with the send confirmation rule in `social-state.md`.
- Wake claims persist sleep deadlines until begun and a token-free wake_claim are durable. Proven unexecuted recovery restores claims before closing turns while preserving newer operator config. Preparation failures return drained jobs to received and retry at most three times with 5/10/20-second backoff; failed rollback bookkeeping remains pending. Epoch checks run again before begin/submission.
- Usage reads merge selected `token-usage.jsonl` and Rust-appended `token-usage-rust.jsonl`, mapping DSH sessions to conversations. Single files retain line order, merged files time order. Samples key on session/turn/step/retry; newer seq wins. Bases use asOfSeq, eviction summarizes compaction; null-bucket turn rows are evidence rather than billing. Append planning writes only new/newer samples. Model attribution prefers sample, session selection, then event; provider prefers event then selection. Attribution subtracts ledger samples from DSH request events, while conversation-turn counts remain separate.
- Recorded token-ledger fixtures are the independent expected outputs for ledger readers and HTTP totals. `socialV2.turnTimeoutSecs` (default 180, 3–900) bounds chat, closed-agent and first-generation reserved turns; reserved2 turns use the observation-derived budget in `prompts-modes.md`. Recovery reattach wait defaults to 900 (1–3600). Missing DSH RPC correlation pauses instead of guessing.
- DSH collector timing records (`turn-timing.jsonl`) carry bridge `turnId` (null without a ledger turn), submitted `attemptRpcId`, nullable `endKind`, `cancelled` and nullable `cancelReason` (`turnTimeout`, `superseded`, `turnCancelled`, `turnInvalidated`, `dshAborted`, `collectorTimeout`, `collectorFailure`), also for failed collection. The cancel reason comes from the turn's own ledger records, read from the ledger length captured before its `begun` record, so the turn-end lookup does not grow with ledger history. Reserved2 invalidation records in `rbridge-live.jsonl` name the first fired `predicate`: `suspended`, `notTaken`, `notAllowed`, `missing` or `tokenChanged`. These records contain no agent tokens.

- Pauses persist their first `pausedAt`; repeated probes/restarts never extend it. `socialV2.pausedTurnAutoAbandonMinutes` defaults to 10; integer 0 disables expiry. Recovery only auto-abandons, never auto-retries. Auto/chat/console use one fresh-read resolver under `locks/turn-resolution.lock`, including unknown-send retry confirmation and abandon token revocation. Late reconciliation rechecks final state under the same gate before applying a verdict or replaying input.
- Each turn has a stable eight-hex code derived from its full ID, exposed by the turns API. A pause gets one owner-private alert with conversation, reason, code, local-time deadline (or disabled state) and commands, then one resolution notice identifying auto/chat/console or recovery. Claims are flushed/synced before a bounded separate notice worker sends; full queues retain pending claims, failed claims prevent delivery. A crash after claim or uncertain delivery can lose a notice; it never automatically repeats a potentially delivered notice. Historical final turns without notice intent remain quiet.
- Only the configured owner's private message (`user_id` and any sender ID equal ownerQQ) intercepts `放弃 <code>` / `重试 <code>` and ASCII case-insensitive `abandon` / `retry` before participation-mode dispatch and model-readable history. The whole message must be exactly `<verb> <code>` or `<retry verb> <code> <确认|confirm>`, with the code exactly eight hex digits (ASCII case-insensitive) as shown in the pause alert; anything else, including a message that merely starts with a verb (`retry later`, `放弃 吧`), has an extra word (`重试 20261109 的任务`, `放弃 <code> 吧`) or attaches punctuation to the code, is ordinary model input. A well-formed command with an unknown, stale or ambiguous code gets a short private reply. Unknown-send retry asks for `重试 <code> 确认` (`confirm` also accepted). Other senders/groups use ordinary ingress. Commands are journaled and marked handled before resolution so they never replay to a model; a crash between consumption and resolution requires re-sending the command.
- Briefing delivery evidence and cache-aware idle session rotation are specified in `prompts-modes.md`; `session_map.rs` remains their only selected sessions.json writer. Reset resolves string and object session mappings through that shared store; an unresolved DSH mapping returns non-success. Harness reset without a DSH mapping retains its separate generation contract. Reset revokes a live harness generation immediately but leaves storage and ledger finalization to its handler owner until durable settlement; uncertain effects remain paused. Paused or crashed harness turns without an owner resolve immediately.

- Journal open silently migrates existing private-history gaps to terminal policy without changing attempts, evidence or timestamps; schemas without notice claims gain no historical notice intent. Existing modern pending claims retain their delivery contract. Migration reserves the writer only when needed and rechecks schema under that reservation. Startup read-then-write recovery uses `BEGIN IMMEDIATE` before selecting processing rows; already-migrated console opens do not acquire a write transaction.

## Crate contracts

Inbound journal recovery reserves the SQLite writer before reading. Already-migrated opens stay readers; historical private-history gaps migrate silently to terminal policy. Only turn-worker/recovery ledger appends and the terminal/claim decision read that precedes them retry Windows sharing/lock errors (32/33), with one shared two-second budget per record and terminal sync (ordinary ledger reads stay one-shot); scheduler/hub or interaction-gated cancellation, administrative reset/restore and all other runtime appends remain fail-fast. Never retry under send-chain, token-publication, hub or tick locks. Notice delivery, append progress and finalization-gate contracts: `docs/agents/sessions-recovery.md`.

Reserved2 adopts only tokens minted by its own turn. Rotation holds the shared publication mutex across token persistence/publication and releases it before ledger persistence. Ingress, tick invalidation and completion use the same state/publication observation read under that mutex, including across repeated owned rotations. Completion observes again before removing Active or replaying work; reset and mode changes still invalidate queued ingress.
