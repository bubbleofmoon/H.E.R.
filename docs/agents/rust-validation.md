# Rust build and validation

## Every host

- `her/Cargo.toml` builds `her` (Windows GUI subsystem) and `her-cli` (console subsystem) from shared `her/src/entry.rs`, plus the short-lived GUI-subsystem `herupdate` helper from `her/src/updater.rs`. Unit tests: `cargo test --bin her <filter>`; integration tests: `--test <target>`. Never `--lib`. `her_binaries` reads the built PE headers and checks app/CLI dispatch.
- Rust builds run only inside a build slot, offline. Each candidate gets its own `CARGO_TARGET_DIR`; production build trees and executables remain read-only.
- `release_install` requires `--features parity-clock,release-test-keys`; full integration gates include both features so the signed fake feed runs. `release-test-keys` compiles synthetic public pins and is rejected in release profiles, at nonzero optimization levels, and without debug assertions. The package build guard applies to all three binaries even with `CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS=true`. Production builds use the default feature set and the owner-supplied compiled pins; placeholder warnings and rotation rules are in `lifecycle-tasks.md`.
- Format only files you own; never run fmt over the whole repo.
- Tests use synthetic roots and started fakes only: no personal config or tokens, no real QQ, model, DSH, ACL or restart calls. Do not stop services or run the old `check-all` or every test target indiscriminately; some old tests touch fixed production paths.
- Fixture allocators use the shared install-root guard before mutation. Set `HER_INSTALL_ROOT` to an unused temporary production boundary for validation, and `HER_TEST_CLI` to this candidate's built `her-cli` for Python/PowerShell/Node helpers (after building the paired binaries). Script helpers fail closed when the CLI is unavailable. Package `fixture-paths.ps1` beside a copied fixture observer.
- Guard evidence/output destinations independently of runtime roots, including `TICKET13_EVIDENCE`, `TICKET15_EVIDENCE`, `TICKET19_MEDIA_EVIDENCE`, native release evidence and observer/cleanup outputs. Validate redirected temporary directories before evidence allocation or tempfile's write probes.
- Classify honestly: a failure before Cargo starts is a harness setup failure, not a compile failure or product red. SKIP, startup failures and `--no-run` builds are not passes. Keep raw logs of every run with byte hashes.
- A fixed parity epoch starts independently in each process. Fixtures comparing console/live timestamps use the shared host clock and seed randomness with `HER_PARITY_RANDOM_SEED` instead. Wait for operation completion in observable state: cancellation RPC receipt precedes token rotation, and a tool send precedes the collector's usage, timing and terminal ledger writes. Keep fixture dependencies alive through that completion.
- Fake DSH receipt logs record request arrival before the HTTP response and HER's subsequent state publication. Closed-agent assertions after `$events/result` await the exact `/api/pending` payload and HTTP success with a bounded deadline; an answered approval is absent while claimed and restored after success. Retain full payload and receipt-count assertions. For expiry during stream loss, hold the fake reconnect handshake until expiry is observed and assert no new event client; do not race expiry against the jittered reconnect timer.
- `supervisor_dependencies` fixtures wait for the child to leave the inherited test-binary image before recording its PID/start/image cleanup identity. Cleanup retains exact identity checks; it never follows an executable change with a PID-only kill.
- Dependency-upgrade crash fixtures use parity-only confined `data/lifecycle/dependency-upgrade-pause` controls and `dependency-upgrade-reached` observations. Pauses are bounded to 30 seconds and control only transaction timing; ownership, desired-state and health decisions remain real.
- Portable handover fixtures bound both child exit and capture-pipe EOF while replacement owners remain alive, and terminate only recorded PID/start/image identities. Dependency outage fixtures install a matching disposable file scheduler and answer login status as online, so startup drift and login polling do not contaminate notice assertions.
- The QQ login episode test in `console_runtime_routes` runs with either clock: `--features parity-clock` advances synthetic epochs across supervisor restarts; default builds wait for the persisted host-clock retry deadlines. The fake timestamps deliveries on the corresponding clock, independently of product deadlines, and asserts at least 60 seconds between attempts, including a quiet restart 45 seconds after failure. Both modes assert the same attempts and confirmed deliveries, await delivery separately from observation publication, and retain real 30-second polls for recovery without a restart. Use the feature for repeated target validation; default-mode coverage takes several additional minutes.
- Fix compile errors in the calls and error handling, never by returning empty responses or removing features.
- A patch rejected by auto-review or a guard hook has not taken effect; do not repeat the same action through another tool.

## Linux host (`/root/her`)

- The host has 4 cores and 7 GB of RAM and will not grow: one build slot, and one full test suite at a time across all tickets, started through `/root/orch/serial/one-suite.sh <driver>`.

- Run every cargo command through `scripts/cargo-slot.sh <ticket> <worktree> <evidence-dir> <run-name> <cargo subcommand> [args...]`. It runs `/root/.cargo/bin/cargo <subcommand> --offline -j 2` at `nice -n 10` with `CARGO_TARGET_DIR=/root/rb-targets/<ticket>`, writes `<run-name>.{stdout.log,stderr.log,exit.txt}` (plus `<run-name>.build.log` for `test`/`run`) and removes only its own locks (a lock holder heartbeats its `owner.txt` every 60 s; waiters break a lock only after 300 s without a heartbeat, because Codex sandboxes cannot see host PIDs). For `test` and `run` it holds the machine-wide build slot only while compiling, then runs the tests outside it in one of `QQBOT_TEST_SLOTS` (default 3) test slots; other subcommands hold the build slot throughout. Never create or remove the lock by hand. It also sets `RUSTC_WRAPPER=sccache` (cache in `/root/.cache/sccache`, shared across tickets) and `CARGO_INCREMENTAL=0`; set `RUSTC_WRAPPER=` to build without the cache. Dependencies are built at `opt-level = 2` even in test builds (`her/Cargo.toml`).
- Integration tests: run each `--test <target>` with `-- --test-threads=1` (default threads on 4 cores time out in `mcp_core_e2e`), and `session_turn_recovery_e2e` and `release_install` with `--features parity-clock`. The host user is root, so the unwritable-ledger fixture uses `chattr +i`.
- Rustfmt: `/root/.cargo/bin/rustfmt`.

## Windows host (clone `C:/her`)

- Git Bash shell gotchas: Git Bash rewrites `rev:path` and `/x` arguments as Windows paths, so prefix `git show <rev>:<path>` with `MSYS_NO_PATHCONV=1`. Inline `python -c` and Python string literals turn backslash paths into escapes (`\b` becomes a backspace, `\0` a NUL), so write such edits as a script file that builds backslashes with `chr(92)`; `scripts/check-repo.py` catches the leftovers. PowerShell `-match` reads `C:\her` as a regex escape; use `-like` or `[regex]::Escape`, and pass non-trivial PowerShell as a `-File` script.

- Layout: integration checkout `C:/her`, worktrees `C:/her-wt/<ticket>`, prompts/receipts/build-slot lock `C:/her-orch`, build targets `C:/her-targets/<ticket>`. The production checkout `C:/qqbot` is read-only for migration work: never edit or build into it, and never touch its running services, scheduled tasks, config, tokens or executables. A production host's own working state is operator detail and is written down only in the vault copy of `docs/agents/production-ops.md`. Production releases under `C:/qqbot-rust/releases` remain read-only too; a source rename does not deploy them.
- Build and test only through `scripts/cargo-slot.ps1 <ticket> <worktree> <evidence-dir> <run-name> "<cargo subcommand> [args...]"` (the cargo command is one quoted string, e.g. `"test --test x -- --test-threads=1"`). It sets up MSVC (vswhere/vcvars64), runs the stable MSVC `cargo.exe` under `$env:USERPROFILE\.cargo\bin` (never a hard-coded account home) `+stable-x86_64-pc-windows-msvc <subcommand> --offline -j 2` (override `QQBOT_CARGO_JOBS`) hidden with `CARGO_TARGET_DIR=C:/her-targets/<ticket>` and writes `.stdout.log`, `.stderr.log` and a numeric `.exit.txt` (plus `.build.log` for `test`/`run`). Compiling holds one of two build slots (`C:/her-orch/build-slot.lock`, `build-slot-2.lock`; `QQBOT_BUILD_SLOTS`) on CPUs 0-3 at BelowNormal. `test` and `run` compile first, release the build slot, then run at Normal in one of two test slots (`QQBOT_TEST_SLOTS`, 1 or 2): `C:/her-orch/test-slot.lock` on CPUs 4-7 alone, or `test-slot-2.lock` on CPUs 0-3, which it shares with the BelowNormal compilers that yield to it; no two suites share CPUs (hex masks `QQBOT_BUILD_CPUS`, `QQBOT_TEST_CPUS`, `QQBOT_TEST2_CPUS`). `<run-name>.slot.txt` names the test slot and mask a run used; record it with timing-sensitive evidence. Production is not pinned. A test run past 60 minutes (`QQBOT_TEST_TIMEOUT_MIN`) or a compile past 90 (`QQBOT_BUILD_TIMEOUT_MIN`) has its own process tree stopped and exits 124 with `<run-name>.timeout.txt`, so a hanging test cannot hold the slot. Always run `C:/her/scripts/cargo-slot.ps1 -WorkTree <worktree>`; a differing worktree copy writes `<run-name>.stale-slot-script.txt`. Never create or remove a lock by hand. A failed PATH lookup for cargo does not mean the tool is missing.
- Target disk admission: before each Cargo phase, after acquiring its slot, the Windows launcher checks available space on the drive containing `HER_TARGET_ROOT` (default `C:/her-targets`). `QQBOT_MIN_FREE_GB` defaults to 40; units are GiB (PowerShell `1GB`). Below that minimum it first prunes, then refuses Cargo if space is still low. Refusal or an unverifiable disk check exits **123**, writes the reason (including measured space and the minimum when available) to `<run-name>.disk.txt`, preserves the usual output/exit receipts and releases its slot. This is a harness refusal, not a compile/test failure; timeout remains 124.
- Target retention: pruning runs only below the disk minimum. `QQBOT_TARGET_MAX_AGE_DAYS` defaults to 2; age is time since the newest write anywhere in the tree, including hidden files and directories. Eligible direct children of the target root are removed oldest first until available space reaches the minimum plus **20 GiB** headroom, or candidates run out. Cargo may proceed after pruning whenever the minimum is met. The current ticket's target and targets named by live build/test-slot `owner.txt` PIDs are protected; unreadable or incomplete owners conservatively protect all targets. Slot publication and pruning share a named mutex. Root/ancestor reparse points cause refusal; child trees containing junctions or symlinks are skipped, and deletion checks each leaf and removes empty parents without recursive traversal. `<run-name>.prune.txt` appends removed paths, byte sizes and ages, lock/reparse skips and nonfatal deletion failures (including ACL denials); failures are skipped so later eligible targets can still be removed. Threshold and age overrides accept finite, nonnegative numbers. Test disk guards only with throwaway `HER_TARGET_ROOT`, build/test lock overrides and evidence under the ticket's `C:/her-orch/<ticket>/tmp`; force refusal with a threshold above the drive's capacity, never by filling the real target drive.
- Start other runners hidden: `Start-Process -WindowStyle Hidden -PassThru`, immediately cache `$null = $process.Handle`, set `.PriorityClass = [Diagnostics.ProcessPriorityClass]::BelowNormal` on the returned Process (there is no `-PriorityClass` parameter), wait on that same object and write its numeric exit code as the receipt. PowerShell 5.1 can return a null ExitCode after exit without the cached handle; `Start-Process -Wait` retains it inside the cmdlet. Do not assign `$PID`. Create directories with `[IO.Directory]::CreateDirectory()`.
- Run all integration targets with `-- --test-threads=1`; `session_turn_recovery_e2e`, `dependency_recovery_e2e` and `release_install` require `--features parity-clock`. This feature supplies a monotonic advancing synthetic epoch and seeded randomness for Rust fixtures.
- `release_install` portable handover acceptance runs real candidate trial, retirement, supervisor startup and shared health against fake dependencies. `HER_TEST_HANDOVER_CONTROL` supplies only parity-clock fault/clock controls and before/after-start barriers; the control file and derived barrier paths must stay outside the selected installation. Approved-update fixture launches also capture helper stderr in the guarded control-path `helper.stderr` extension; normal builds discard it. Native deadline/junction/identity-wait/hidden-start checks unset both handover fixture variables.
- The focused `release_install` platform fault driver uses `HER_TEST_UPDATE_PLATFORM` only in parity-clock builds; the fake state file is guarded outside the selected throwaway installation. Fake errors never fall back to native operations. Native handoff checks unset this variable. The ignored handover child entry is invoked explicitly by the owned-process fixtures, not a skipped acceptance test.
- Before native fixture tests, align the runner's `USERNAME` with `([Security.Principal.WindowsIdentity]::GetCurrent().Name).Split('\')[-1]`. A brokered Codex account can inherit the operator's username; the existing fixture ACL hardener grants that environment name, so a mismatch makes the live child unable to reopen its own data. Record the inherited name and actual account; keep this environment adjustment local to the test runner.
- Path regressions: `powershell.exe -NoProfile -File scripts/test-external-path.ps1` exercises the retained external-path helper; `supervisor::` covers the dependency-helper argument boundary and Node/MCP paths. The window observer uses a pinned native limited-query handle for liveness/start/image, so missing CIM fields alone do not decide identity; an exited instance is excluded, an alive unknown instance still fails.
- PowerShell static checks: `powershell.exe -NoProfile -File scripts/test-ps-count.ps1` runs in 5.1, parses maintained `.ps1` sources as UTF-8 without executing them, flags parenthesized command/pipeline collection counts, lengths and indexing, and checks zero/one/multiple manual-success records. It also requires an immediate Handle read for assigned asynchronous `Start-Process -PassThru` objects with local ExitCode consumers or returns to callers; `-Wait` is allowed. Raw string character lengths are allowed. Discovery excludes reparse points, baseline/install trees, build/dependency output and archived scratch evidence. Assigned-variable collection consumers and indirect/aliased process flows require source review.
- A fixture root holding a handle that a task on a test runtime owns (conversation store, turn owner lock) is removed only after that runtime is shut down with a stated bounded wait: build the runtime in the test, return the fixture from the async body, `shutdown_timeout` it, then drop the fixture. Removing it inside the async body races the task and `remove_dir_all` fails with Windows os error 32 in the fixture's `Drop`.
- `health_check`'s reconcile case bounds the supervisor's own reconcile path, not a fixed five seconds: a fresh desired revision is noticed only on the one-second scheduler pass and the console owner starts only after that (~5 s of supervisor delay, ~7 s to a healthy console natively), so that case uses the fixture's explicit `check_bounded` allowance instead of the shared 12-second `assert-running` bound.
- `scheduled_task` drives real install/supervisor binaries with a file scheduler. Its single native round trip registers only a GUID `HER-Test-*` task when elevated, reads and compares it, and removes it without triggering it; otherwise it emits a stated elevation skip reason. Ordinary test runners set `HER_TASK_SCHEDULER_FILE` to a guarded disposable file so no test consults production Scheduler state. Fixtures counting administrator notices install a matching definition into their own file scheduler and pass it to every supervisor restart unless task drift is under test; a missing task intentionally sends an additional drift notice.
- Native lifecycle proof runners: `scripts/test-release-proof.py <candidate.exe> <installed-dsh-support-root> <evidence-dir>` covers the combined lifecycle fixture; `scripts/test-release-chains.py` with the same arguments covers generated MCP/curl/digest independently. Use hidden runners and synthetic memory paths. Failed readiness/observation remains failure; the nominal 250 ms interval cannot exclude shorter windows.
- Elevated AC3: in an administrator PowerShell in the interactive user's session, run `python scripts/test-release-proof.py <candidate.exe> <installed-dsh-support-root> <new-evidence-dir> --highest`. This passes `-RunLevelHighest` to the fixture, requires elevation before creating a fixture root or registering a task, and registers only its GUID task with the caller's Interactive/Highest principal to match production start-all. Default runs retain Limited. After destination guards pass, `execution-context.json` records caller elevation, including a `--highest` elevation refusal; `artifacts/task-principal.json` records the Scheduler principal read back before any trigger is installed, caller account/SID/session and inherited/effective USERNAME. Highest aligns USERNAME locally with the caller for ACL hardening; the task, observer and cleanup use the same account and elevated token. The elevated root needs no additional ACL grant to another account. Native descendant identity and window checks remain mandatory. Non-elevated `--highest` exits 2 without registering a task; the direct PowerShell switch refuses too.
- The `supervisor_dependencies` integration target covers supervisor launch/adoption, restart backoff, failure alerts, hang recovery, explicit dependency stop, outliving ordinary stop, native port holders and inspection denial, cmd/npx resolution/refusal and hidden windows through seam 1. With `--features parity-clock` and `HER_TEST_DEPENDENCY_CLOCK=1`, a fixture publishes integer epoch milliseconds atomically in `data/lifecycle/dependency-clock`; only dependency-manager timers use it. A transient read keeps the last fixture time; an unavailable initial clock fails the fixture worker. Default builds do not read the clock or flag. A VM_READ-denied fake models inaccessible elevated-process inspection; it is not an actual elevated-token proof. Window samples cannot exclude windows shorter than the sampling interval.
- Release runner timeouts: `--timeout <seconds>` overrides the combined fixture budget or each chains command budget; final cleanup keeps its independent bound. Timeout receipts use 124 (launch failure: 125). Finalization verifies owned Windows jobs empty, removes only the selected GUID tasks after checking their action points into the fixture root, and pins/reaps Scheduler descendants before archiving diagnostics. Cleanup/archive failure retains the temporary root and fails the run. `python scripts/test-release-timeout.py [evidence-dir]` forces timeout and nonzero-exit paths, including an external process tree and descendants surviving their leader; it registers or starts no tasks.

## GitHub-hosted CI

- `.github/workflows/checks.yml` runs on free GitHub-hosted runners for every push and pull request, on Windows and Linux: repository checks, the public scan (which runs gitleaks itself), the guard's own tests, the build and the full integration suite discovered from `her/tests/*.rs`. It is the merge check, and its result is linked from the issue.
- Local gates stay necessary for what a hosted runner cannot do: native desktop and window checks, elevated scheduler fixtures, production-adjacent paths and the release proof runners. A hosted pass never replaces them.
- `scripts/ci/run-tests.py` is the single suite runner in CI and locally; it passes `--features parity-clock,release-test-keys` to `release_install`, because a test target whose `required-features` are absent is silently skipped and a skip is not a pass.
- Fork pull requests wait for a maintainer-approved workflow run, and this repository never gets a self-hosted runner.

## Elevated tests

- The owner-installed scheduled task `HER-Elevated-Test` (Run with highest privileges, interactive user) runs `C:/ProgramData/HER-Elevated/run.ps1` (admin-only folder; source copy `C:/her-orch/elevated/run.ps1`) on demand, so elevated checks need no owner action. Write `C:/her-orch/elevated/request.json` as `{"id":"<new id>","ticket":"<n>","test":"<module path>"}` (or `{"id":"<new id>","selftest":true}`), then `schtasks /run /tn HER-Elevated-Test`; results land in `C:/her-orch/elevated/results/<id>/` (`test.*` receipts, `exit.txt`) and each run is logged in `C:/ProgramData/HER-Elevated/runs.log`.
- It runs only `--bin her` unit tests inside a `native_tests` or `elevated_tests` module, built from `C:/her-wt/<ticket>` with that worktree's `scripts/cargo-slot.ps1` into `C:/her-targets/<ticket>`, with `HER_INSTALL_ROOT` set to an unused folder inside the result. Elevated tests belong in those modules; anything else is refused. Coordinators only start it; changing the runner needs the owner (admin-only file).

## Crate contracts

Recorded corpora live under `tests/fixtures/`; Node fake-world tooling and shared helpers under `../scripts/` support Rust integration tests. Tests use no JS bridge or `memory/` tooling. `supervisor_dependencies` fixtures record child cleanup identities after exec. Reserved-mode fixtures comparing console/live timestamps share the host clock and seed randomness rather than giving each process an independent fixed epoch. Advanced synthetic ingress and companion-console clocks share one epoch; with `parity-clock` and a fixed epoch, `HER_PARITY_ADVANCE_FILE` adds the file's nonnegative integer milliseconds on each clock read (absent/invalid means zero; fixtures publish by rename), and cap/observation fixtures witness the matching `activeWait` and its held OS lock before advancing. Read-only console fixtures await HTTP success before checking asynchronously published state. Reply-timing fixtures use seeded virtual time for exact attempt deadlines, witness durable arrivals before releasing typing-cleanup barriers, and keep owned fake gateways alive until scenario completion. Replay fixtures await observable settlement within configured wake/quiet bounds while retaining exactly-once assertions. Parallel console wait fixtures use distinct conversation keys because wait leases are process-wide, independent of fixture roots.

Gap-refusal restart fixtures reserve the SQLite writer after all opening windows return to pending and hold it through the owned child kill. A refusal log alone does not establish a settled notice attempt.

Restart fixtures asserting group retry counts await the persisted history attempt before assertions or the next owned child kill; row creation and private notice receipts can precede completion of group recovery.

Session recovery, persona and shared chat/harness fixtures use `tests/support/console.rs` for console startup. They reserve the console port through fake-listener setup and await successful health naming the owned console PID and selected port, including after restarts. An exited or unready owned console is reaped before retrying on a fresh port, with at most three attempts and bounded readiness probes; fake DSH relay calls follow the replacement port. Failure diagnostics retain every startup attempt and console output alongside the live candidate logs. Wake-snapshot receipt assertions await persisted ingress of every expected message.
