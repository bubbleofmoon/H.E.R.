# Social state, access and sends

- `GET /api/qq/login` requires current console administrator or desktop-session authentication and refuses either agent header, including when combined with an administrator credential. It returns only `ok`, `state` (`logged-in`, `needs-login`, `unknown`) and verified native QQ `processes` (`pid`, `start`) needed by the desktop action. It returns no UIN, process path, upstream error text or dependency credential. The route probes read-only; only the supervisor claims episode alerts.

Read for social configuration, authorization, console writes, quotas, feedback or send ordering.

- Release approval uses `POST /api/releases/approve` with the displayed tag and explicit confirmation. It accepts current console administrator or desktop-session credentials, refuses either agent header, and rechecks authorization under the configuration gate before persisting approval. Host, origin and JSON checks match other console administration routes. Approval and execution contracts: `docs/agents/lifecycle-tasks.md`. Dependency approval uses `POST /api/dependencies/approve` with `confirm:true`, the displayed `name` and `version`, under the same current-credential, mixed-agent-header, Host, Origin and JSON checks. Dependency status/check routes share administrator-only access.
- Persona routes (`GET /personas`, `GET /api/personas`, `GET /api/personas/item?id=`, `POST /api/personas/{create,update,duplicate,delete,approve,assign,import-roles}`, `GET /api/personas/wake-words?conversation=`, `POST /api/personas/wake-words/undo`) are administrator-only: either agent header refuses with 403. They are mounted from `console_persona.rs` behind the console front (Host, credential, JSON, Origin, audit). POST routes re-check the console credential under the configuration gate before committing, like release approval. Storage, validation and re-brief belong to `persona.rs`; the wake-word view and undo belong to `wake_words.rs` (the undo writes `social-v2.json` while the route's authority holds the social gate). Bodies name a conversation as `conversation`, never `key`.
- Settings routes (`GET /settings`, a page that lists every setting from the list route with set and reset buttons, and the history newest first with an undo button per entry and an older-entries button; `GET /api/settings`, `POST /api/settings/set` with `{"setting","value"}`, `POST /api/settings/reset` with `{"setting"}`, `POST /api/settings/undo` with `{"entry"}`, `GET /api/settings/history` with optional `setting` and `before`) are administrator-only (either agent header refuses with 403) and need a selected runtime (503 otherwise). They are mounted from `console_settings.rs` behind the console front (Host, credential, JSON, Origin, request audit); every POST route is a bounded JSON POST (1 MB, 413) and re-checks the console credential under the configuration gate before it commits. The list shows each registry setting's label, hint, group, when it applies, type and bounds, default, stored value and the value the next use reads (`null` for a model id that is not configured), plus `storeError` when stored values cannot be read; the page sets an integer setting from a number input and a model id from a text input. A refused value is 400 and keeps the stored value; an unreadable or newer store is 503. Each change also writes one `settings_audit` row (actor `administrator`; source `console` for a set, `reset` for a reset, `undo` for an undo) and is written back into `config.json`; when that write fails the change stands and the reply (set, reset or undo) carries `mirrorError` (seeding and write-back: `docs/agents/runtime-paths.md`). A reset stores the setting's default, which then wins over `config.json`; its reply is the set route's. An undo names a history entry (a positive integer, else 400; an unknown entry, or any entry before the store exists, is 404) and restores that entry's old value; it is refused with 409 and changes nothing when the setting changed again after the entry (any later entry, even one back to the same value) or its stored value is no longer the entry's new value, when the entry's setting is retired or not global, when the entry is a seeded copy of `config.json` (source `migration`), or when its old value is no longer accepted. Its reply names the entry, the setting and the stored value now (`null` when the undo removed it; the undo then removes it from `config.json` too, so the default applies again, and when that removal fails the undo is 503 and changes nothing). The history route lists entries newest first, at most 100 (`entry`, `atMs`, `actor`, `source`, `scope`, `setting`, `old`, `new`; `null` is no stored value; a value seeded from `config.json` is an entry with actor `system` and source `migration`), and `next`, the `before` of the next page (`null` when the page holds fewer than 100 entries; a page of exactly 100 gives a `next` whose page may be empty); `setting` narrows it to one registry key, an unknown key or a `before` that is not a positive integer is 400, and no store yet is an empty list. Bodies and queries name the setting as `setting`, never `key`. Store and registry: `docs/agents/runtime-paths.md`.

- Reserved2 stores `text`/`plain`/`tail` as 200-unit previews. A message whose rendered text is longer also keeps `textChars` (its real length in UTF-16 units) and `textTruncated: true` in `recentMessages` and `unread`, and its `fullText` once, in `recentMessages` (the list message detail reads), cut on arrival at the `socialV2.context.fullTextMaxChars` then in force (default 4000, range 200..20000); a later setting change does not re-cut stored text. Model-facing message lists and tool results carry the preview and the two markers but never `fullText`; `qq_get_message_detail` returns the full text in `info.text` (by QQ message id or local seq) with `textChars` and `textTruncated`, true only when the message exceeds the cap it was cut at. A message not stored locally is read from OneBot up to the cap now in force.
- Selected `social-v2.json` mutations take `locks/social-v2.lock`, waiting up to five seconds. A busy holder returns 503 without writing. Config, mode, role and social-state atomic replacements also take `locks/authority.lock`. Sticker send/add/remark hold authority across fresh validation, connect and request transmission, releasing before the response wait. Social writers acquire the social gate first. Authority writers wait up to 20 seconds; other queued social writers can exceed their five-second bound during a transmission.
- Text, burst, poke, sticker and voice sends recheck token epoch, mode, allow/deny policy, role silence, pause, social enablement and the relevant tool flag before each item. Pokes recheck after the member lookup. Text/burst/sticker/voice tool sends and chat-mode replies, commands and interaction notices share `recorded_send::send_chain` (per process). Sticker sends pause 800–2000 ms inside the chain, outside state gates, before the final guard and attempt. Debug/test-clock builds may override the pause; release builds ignore that override.
- Outbox `intent`, `attempt` and outcome are durable. Append locks cover `sync_all`; errors propagate. A torn final line is terminated before another append. Readers skip only truncation JSON errors, with a warning naming file/line; other corruption fails. Unknown delivery is never automatically resent. Text resume refuses sticker and voice batches.
- `recorded_send.rs` alone claims batches and writes intent, attempt and outcome records for chat, tool, voice and sticker sends. Every unknown outcome is checked against the gateway's recent history before anything else: our own message after the attempt carrying the same canonical text, or a `record`/`image` segment, and one history message proves one item. Chat mode accepts the wait for the chain and the history read, but never on a runtime worker: `chat::send_recorded` (and the pipeline's `send_chat_text`) run through `recorded_send::off_worker`, which on the multi-thread runtime hands the worker's other tasks, ingress included, to another thread (`block_in_place`) while the send waits and runs; on a plain thread, a blocking-pool thread or a current-thread runtime it runs inline. Send order, the chain and the intent/attempt/outcome records are unchanged. Command replies and closed-agent answers sent from the ingress loop itself still finish before the loop reads its next event. `block_in_place` still suspends the other futures of the same task: the closed-agent pump's timers wait while one of its replies waits for the chain. Tool, voice and sticker sends run on console threads or the blocking pool and take the chain directly. History proof needs exactly one own matching message after the attempt that no confirmation already claims; an unreadable outbox, a confirmation without a message id, or another unresolved send from another batch in the last 24 hours leaves the item unknown.
- Group mute (`group_mute.rs`): `data/group-mutes.json` under `locks/group-mutes.lock`, keyed `group:<id>`, stores personal (`personalUntil`, -1 = end unknown) and whole-group (`wholeGroup`) restrictions apart; it never touches `social-v2.json` records, so resets keep it. Sources: an own-id `group_ban` notice (lift or zero duration clears; no readable duration = end unknown; other users' notices are ignored), a `user_id:0` whole-group notice (narrow parse; it first advances the entry's write counter so any refresh that began earlier is dropped, then triggers a refresh that carries its operator), a once-per-connection refresh of the groups the allow/deny lists admit at that connection (`get_group_member_info` self `shut_up_timestamp`, `get_group_info` `group_all_shut`, owner/admin exempt from whole-group) plus a ten-minute recheck of unknown-end mutes, and a send or poke refused with retcode 100 and `result=120` (not committed; retcode 100 without it stays unknown), including the first-generation CLI reply path. A refresh started before a newer write, notice or refusal is dropped; an unknown-end personal mute is cleared only by a refresh that also read the whole-group state. While muted, text, burst, direct, poke, sticker, voice, chat and CLI replies are refused locally with no gateway call (403 `{ok:false,error}`, never unknown delivery, even when the refusal's own outbox record cannot be written; model text "muted in this group until HH:MM"; the reserved2 CLI relay treats that 403 as a clean sleep); a send with an agent token marks its open turn as ended, which needs the `waitMessages` tool flag, and without it the turn ends when the model stops. Ingress differs by mode: reserved2 stores a muted group's messages as unread, dispatches no wake for it, and answers them when a new message or timer wakes it after the mute; chat and first-generation reserved ingress mark the muted message handled and drop it. The first-generation reserved scheduler keeps a muted group's queued jobs queued (they become eligible for dispatch again once the mute ends, subject to the normal dispatch checks: authority and generation, DSH health, one turn per group) and does not advance its proactive topics, probes, timers or farewells, with one log line per mute. Each new episode sends one content-free owner notice (group, duration, operator); a lift sends none, and a notice refused by the limiter is not retried. Not mute-aware: the legacy wake pump (`entry.rs` `pump_all`), the administrator test send, a notice for a group the allow/deny lists do not admit when it arrives, and `unknown` outbox records written before the mute existed. Reads fail open.
- Sticker quotas reserve fresh independently identified pending liabilities before network work. Proven non-submission/refusal releases; confirmed and unknown outcomes settle into numeric quota arrays. Text checks include pending sticker sends. Ambiguous refunds retain quota. Confirmed history and settlement share one mutation; failed persistence keeps liability and reports partial success without a second gate wait. Confirmed collection remains successful if settlement fails. Pending reservations expire after one hour; settled arrays retain the newest 500 entries. OneBot connect/write budget is 15 seconds total, with connect at most five seconds; write failures remain unknown.
- Resets preserve only pending sticker liabilities and mark pending IDs revoked; settled timestamps and other conversation state are discarded. Already submitted operations can settle their own ID. Submission validates ownership under authority coordination.
- `socialV2.send.duplicateWindowMs` atomically marks duplicate text before quota reservation. Concurrent duplicate calls receive 429. Successful sends, rather than model text, update reply state and read watermarks.
- Selected console front checks Host against its bound loopback port before credentials, exempting icon no-ops and `/api/health`. Authenticated writes require `application/json` (415); supplied Origin must match the console (403). Agent credentials cannot reach administrator routes. Console agents need a live conversation token; paused/disabled/non-reserved2 contexts refuse social calls. Status/send/image exceptions remain explicit in `console_agent.rs`.
- `POST /api/desktop/sign-in` additionally requires a selected runtime, proof of reading `data/console-token` and a live Windows loopback peer whose token user matches the console's installing-user task principal. Both desktop and console validate the token file's native owner and DACL through the same pinned read handle, allowing only the current user, SYSTEM and Administrators; missing, unreadable or broadly accessible files refuse even with a configured token. `process_identity` resolves the full TCP tuple, pins the peer process and rechecks its instance and tuple; supplied PIDs confer no authority. Unknown identity and non-Windows callers refuse. Desktop sessions use existing console header/query authentication, expire after 12 hours and are revoked by credential rotation or console exit; at most 128 are retained. Every successful rotation advances a generation independent of token contents, so restoring a prior token cannot revive sessions. Issuance captures the generation before reading credentials. Sign-in secrets do not enter audit records. Debug seam-1 fixtures may further restrict the peer SID with `HER_TEST_DESKTOP_PEER_SID_HEX`; release builds ignore it, and it cannot authorize a different real peer.
- `conversation_authority.rs` owns a conversation's agent token (its SHA-256 epoch is the generation), revocation and rotation, the runtime mode and the owner's conversation; memory actions, stdio MCP and harness tools read authority there. Social-state storage and allow-lists remain in `console.rs`.
- Memory routes accept raw `x-console-token` administrator credentials only against nonempty `cfg.consoleToken` (trimmed); a generated file token confers no memory authority. A valid desktop session bound to the effective credential and current generation also grants memory administration. Agent-token rules and console preflight authentication still apply.
- Whitelist/security/token/undo writes hold the social gate across fresh raw config read, atomic write and audit capture. Owner-only whitelist changes preserve existing alias lists; naming a root's list rewrites that root as `{private, groups}`. Access changes acquire the closed-agent interaction gate, retire revoked mappings, rotate every affected token, clear bootstrap, cancel turns and settle queued ingress before responding. A later re-grant creates a fresh epoch. Failures are reported even if another cleanup step succeeded. An access change (whitelist write, `POST /api/conversations/scope` or `her-cli conversation`, audit undo) records its revocation in `data/access-revocations-pending.json` (mode and the allow, deny, `allowAllWhenEmpty` and owner policy before and after) before it writes `config.json`, and removes the entry once every revocation step succeeded. Console start, and every access change before its own write, finish each pending entry by its recorded policies, so a re-grant made meanwhile never brings the old epoch back; a crash before the write still finishes the recorded revocation (the conversation keeps its access with a fresh epoch). A failed `config.json` write removes its entry only when the file still holds what the change read (nothing was published); a failure after publication, such as the folder sync, keeps it for the next console start or access change. While an entry cannot be finished, the record file is unreadable or malformed, or an entry lacks `before` or `after` as policy objects (a missing mode or reason uses the current mode), access changes answer 503 and write nothing. A revoked conversation's DSH session stop is recorded in the same file (`stops`: conversation and session) before its mapping is retired, and removed only once the stop succeeded; console start and every access change run the recorded stops again in the background (a failed stop never refuses a change), and a retried closed-agent owner change also selects the conversations those stops name. Each revocation attempt records the conversations it selected in its entry (`targets`) before any step, and a retry selects them again, so an attempt cut off after retiring a mapping or after its stop finished still rotates the token before the entry clears. A `stops` field that is not an array of `{key, session}` strings, `targets` that are not an array of strings, a target that is not a canonical conversation key, or two pending entries with the same `id`, refuses access changes like an unusable entry; a record without `stops` is accepted.
- A conversation is answered only when two configuration keys agree: its allow list (`allow.groups` or `allow.private`, minus `deny`) and `rollout.rustGroups`. Every inbound gate reads the configuration through `RuntimeContext::load_config` for each event, so an edit applies to the next event without a restart: reserved2 and the first-generation path use `console::inbound_admitted` (listed in the allow list and not denied; `allowAllWhenEmpty` does not widen it), chat mode keeps `chat::allowed_in_mode`. Reserved2 tick invalidation and dispatch, wake claims, turn validity, turn recovery and wake snapshots use the same rule with the configuration read at that use, so adding `deny` also stops a wake already queued. Gap recording, saved-event replay, mute refresh, group cards and mute notices use `console::inbound_admitted` with the configuration read at that connection or notice. At a reconnect, saved events of conversations no longer admitted are settled; an unreadable configuration leaves them saved. `rollout.rustGroups` is the explicit array of canonical keys (`group:<id>`, `private:<id>`) the supervisor passes to the live process as `--live-groups`. The live process serves only that list, fixed at launch, because it holds the per-conversation source gates for it (`docs/agents/lifecycle-tasks.md`). `rollout.enabled: false` silences the admitted-but-unserved report and the startup check against `--live-groups`; the supervisor serves `rollout.rustGroups` either way. Live startup and the health check report both kinds of gap (served but refused, admitted but unserved).
- `POST /api/conversations/scope` (`{"conversation":"group:<id>" or "private:<id>","action":"admit" or "remove"}`; administrator only; the body never says `key`, which the console's key preflight would refuse for a conversation not admitted yet) and `her-cli conversation <admit|remove> <conversation> --runtime-root <root> --confirm` change both keys in one read-modify-write of `config.json` under the closed-agent interaction gate and the social gate, then revoke as a whitelist write does. Admitting a denied conversation, or a runtime without an explicit `rollout.rustGroups` array, is refused with 409 and nothing written; a malformed body is 400. Other allow-list entries keep their values; an alias list of the changed kind (`allow.group`, `allow.privates`) moves to `allow.groups` or `allow.private`; served entries are matched in canonical form. The reply lists `changed` keys, `revoked` conversations, `scope` (`notAllowed`, `notServed`) and `liveRestart`: `none` (no live process, or it already serves the new list), `required` (it serves the list it started with: the supervisor's watchdog restarts it with the new list on its next two-minute run, or run the watchdog task now) or `unknown`. Console requests are audited and can be undone there. The CLI writes no console audit record; it waits up to ten seconds for retired DSH sessions to stop (else the reply carries `sessionStops`), prints the reply as its last stdout line and exits 0 done, 2 usage or malformed request, 3 refused or failed.
- `qq_wait_for_messages` (`POST /api/socialV2/wait`) holds a generation lease per normalized conversation. A new wait supersedes the previous one, which returns `superseded: true` with no messages within one poll and records no observation; a dropped handler releases only its own generation. A console wait (no agent token) never supersedes an agent's wait: it is refused with 429 while one runs. Every reply/messages/quiet poll rechecks the lease. Agent waits also recheck the agent token: a poll whose state read fails is skipped, and only a read state with a different token or no conversation ends the call (403). A lone agent wait retires on token rotation within its polling interval (80/100/200 ms); console waits recheck the lease only.
- Whole reset records ledger reset `*`, settles ingress, retires mappings, writes fresh conversations with `resetEpoch`, cancels turns and stops DSH work. Manual reserved2 wake rechecks authority and mode, queues at most 20 epoch-bound admin wakes, buffers while busy and obeys rate limits. The hub cancels only the captured old DSH session across reset/mode changes.
- Audits record method/path/status/result/error/key without request bodies; changed files have blobs, with config tokens redacted. Failed audit leaves the operation's status and adds `audit.ok:false`. Undo supports config/role-map only, checks the file's current state under the state gate (a configuration record compares `afterRegistryFreeSha`, the digest of the canonical document without the settings-registry members, so a settings write-back is no later change; a record without it, and role-map, compare the raw `afterSha`), retains the current console token and the current file's value at every settings-registry pointer (the reply's `settingsKept` lists the registry keys whose backup value differed; those settings are undone on the settings page; an undo whose backup has a non-object where a registry value lives, so the value cannot be kept, is refused with 409 and writes nothing), refuses token-change/no-file records and is itself audited. Retry of a `send-unresolved` turn needs `confirm:true`; abandon revokes its token first.
- `feedback.rs` exclusively owns `<data>/feedback.json`, newest 500 redacted entries. A process mutex and five-second OS gate serialize it. Non-array data is renamed before starting an empty array; failed preservation refuses the mutation. Agent submissions obey session/tool/length limits plus five/minute and twenty/hour; console submissions use the console policy. Owner error notifications deduplicate by key for 60 seconds, ten/hour.
- `activity.rs` owns redacted `<data>/qq-activity.log`, rotating after 500 lines and serving the newest 100 to the console only. Writes are best effort. Feedback, sends, ingress decisions, turn outcomes and slang completion record their activity. Pause affects reserved2 scheduling and agent gates; resume does not replay old pending wakes. First-generation and chat modes ignore pause.

- Outbound replies and console text/voice requests read `security.outboundGuard` per reply/request. Only boolean `false` disables the outbound sentinel, sensitive-reply hiding and blocked-reply notices; missing, invalid and `true` preserve the default guard. `security.interceptNotify` separately controls notices while enabled. Model-input stripping and owner-only model/backend failure routing remain independent of the switch.
