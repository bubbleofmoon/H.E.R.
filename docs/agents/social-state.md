# Social state, access and sends

- `GET /api/qq/login` requires current console administrator or desktop-session authentication and refuses either agent header, including when combined with an administrator credential. It returns only `ok`, `state` (`logged-in`, `needs-login`, `unknown`) and verified native QQ `processes` (`pid`, `start`) needed by the desktop action. It returns no UIN, process path, upstream error text or dependency credential. The route probes read-only; only the supervisor claims episode alerts.

Read for social configuration, authorization, console writes, quotas, feedback or send ordering.

- Recorded group sends approved from the Admin agent use the group's current token, explicit allow and deny policy, common send quota, repeat guard, silent mode and mute checks. Approved sends have their own per-turn scope for the target group, formed from the group token epoch and the approving turn ID. The send chain precedes the authority gate. The authority gate covers the last owner and target policy check and request transmission, then releases before the gateway response or history read. Resume refuses the outbox purposes `approved-group`, `owner-interaction` and `owner-interaction-timeout`, including in `reserved2`.

- Release approval uses `POST /api/releases/approve` with the displayed tag and explicit confirmation. It accepts current console administrator or desktop-session credentials, refuses either agent header, and rechecks authorization under the configuration gate before persisting approval. Host, origin and JSON checks match other console administration routes. Approval and execution contracts: `docs/agents/lifecycle-tasks.md`. Dependency approval uses `POST /api/dependencies/approve` with `confirm:true`, the displayed `name` and `version`, under the same current-credential, mixed-agent-header, Host, Origin and JSON checks. Dependency status/check routes share administrator-only access.
- Persona routes (`/api/personas`, `/api/personas/item?id=`, `POST /api/personas/{create,update,duplicate,delete,approve,assign,import-roles}`, `GET /api/personas/wake-words?conversation=`, `POST /api/personas/wake-words/undo`; UI served at `/persona` with a `302` redirect from `/personas` via `console_ui.rs`) are administrator-only: either agent header refuses with 403. They are mounted from `console_persona.rs` behind the console front (Host, credential, JSON, Origin, audit). POST routes re-check the console credential under the configuration gate before committing, like release approval. Storage, validation and re-brief belong to `persona.rs`; the wake-word view and undo belong to `wake_words.rs` (the undo writes `social-v2.json` while the route's authority holds the social gate). Bodies name a conversation as `conversation`, never `key`.
- Settings routes (`GET /api/settings`, `POST /api/settings/set` with `{"setting","value"}`, `POST /api/settings/reset` with `{"setting"}`, `POST /api/settings/undo` with `{"entry"}`, `GET /api/settings/history` with optional `setting`, `conversation` and `before`; the conversation scope's `GET /api/settings/conversations`, `POST /api/settings/conversation/set` with `{"conversation","setting","value"}`, `POST /api/settings/conversation/reset` with `{"conversation","setting"}` and `POST /api/settings/conversation/switch` with `{"conversation","engine"}`; UI served at `/settings` and `/conversations` with a `302` redirect from `/settings/conversations` via `console_ui.rs`) are administrator-only (either agent header refuses with 403) and need a selected runtime (503 otherwise). They are mounted from `console_settings.rs` behind the console front (Host, credential, JSON, Origin, request audit); every POST route is a bounded JSON POST (1 MB, 413) and re-checks the console credential under the configuration gate before it commits. The list shows each registry setting's scope (`global`), label, hint, group, when it applies, type and bounds, default, stored value and the value the next use reads (`null` for a model id that is not configured), plus `storeError` when stored values cannot be read; the page sets an integer setting from a number input, a model id from a text input and a text setting (the prompt text in `docs/agents/prompts-modes.md`) from a text area, sent as typed. A refused value is 400 and keeps the stored value; an unreadable or newer store is 503. Each change also writes one `settings_audit` row (actor `administrator`; source `console` for a set, `reset` for a reset, `undo` for an undo) and is written back into `config.json`; when that write fails the change stands and the reply (set, reset or undo) carries `mirrorError`, which the settings page displays in its message line (seeding and write-back: `docs/agents/runtime-paths.md`). A reset stores the setting's default, which then wins over `config.json`; its reply is the set route's. An undo names a history entry (a positive integer, else 400; an unknown entry, or any entry before the store exists, is 404) and restores that entry's old value; it is refused with 409 and changes nothing when the setting changed again after the entry (any later entry, even one back to the same value) or its stored value is no longer the entry's new value, when the entry's setting is retired, when the entry is a conversation's value cleared by an access change (source `access`) or names no canonical conversation, when the undo would store a conversation's value while that conversation is not admitted (an undo that removes a value is allowed), when the entry is a seeded copy of `config.json` (source `migration`), when the entry records a failed switch’s restoration (source `switch-rollback`), or when its old value is no longer accepted. Its reply names the entry, the setting and the stored value now (`null` when the undo removed it; the undo then removes it from `config.json` too, so the default applies again, and when that removal fails the undo is 503 and changes nothing). The history route lists entries newest first, at most 100 (`entry`, `atMs`, `actor`, `source`, `scope`, `setting`, `old`, `new`; `null` is no stored value; a value seeded from `config.json` is an entry with actor `system` and source `migration`), and `next`, the `before` of the next page (`null` when the page holds fewer than 100 entries; a page of exactly 100 gives a `next` whose page may be empty); `setting` narrows it to one key of either scope and `conversation` to one conversation's entries (its key canonicalized), an unknown key, a `conversation` that is not a conversation key or a `before` that is not a positive integer is 400, and no store yet is an empty list. Bodies and queries name the setting as `setting`, never `key`. A console configuration page save that sends a registry setting (`POST /api/socialV2/config` with `reply.wakeQuietMs`) changes it through the store as a set does, when the value differs from the one the next use reads (validated first, against that value: a refused value is 400 and nothing is written, the page's other members included; a `config.json` the runtime cannot load is 503 before the store takes anything; one audit row, actor `administrator`, source `console`, undone on the settings page). The save's one console audit record keeps the `config.json` the request found as its before-state. A console write of `config.json` that changes a registry member itself is refused with `<key> changes only through the settings store` and nothing is written; every other console write keeps the registry members as the file holds them. A set, reset or undo of a security setting (the allow and deny lists, `ownerQQ`, `security.interceptNotify`, `security.outboundGuard`, `security.requirePasswordLocally`; the list marks each with `confirm: true`) needs `"confirm": true` in the body (409 `<key> is a security setting: send the change again with "confirm": true` otherwise, nothing written; `confirm` other than a boolean is 400); the console asks via its confirmation modal first, sets a switch from a toggle control, an id list from comma- or space-separated ids and the owner from a text input. A change of a list or the owner revokes as a whitelist write does, before the reply, which carries `revoked`; an undo whose entry cannot be looked at is refused (503) unless it carries `"confirm": true`, and then runs this path. While the admin agent mode puts another owner in force, the owner's list entry carries `overriddenBy` (`source`, `value`). The conversation scope (`console_settings/conversation.rs`): the list names each conversation setting (scope `conversation`, label, hint, group, when it applies, type and options, default, `global`, the global setting it falls back to) and each conversation that is admitted or holds a stored value, with whether it is admitted, `engineToday` (the desired engine for its next admission; `refused` on an unreadable choice) and, per setting, its stored value and the value that applies (stored, else the global setting's), plus a note explaining when they apply. The inspector's Switch button waits for the current turn, checks that the conversation is still admitted in chat, owner-private closed-agent or reserved2, stores the choice and moves the active generation before reporting success. An unsettled turn or a conversation still draining after 180 seconds returns 409. Engine set, reset and undo request a switch on the next admitted turn. The model route uses a selector control and applies from the conversation's next harness turn. A change to the global default requests a switch at the next message for each conversation without a scoped choice, each with its own summary. A failed explicit Switch restores the preceding scoped value or inheritance and audits the restoration as `switch-rollback` with actor `system`. A newer engine choice for that conversation or an access clear takes precedence. A failed summary or archive leaves the destination unpublished. An inbound switch failure before staging uses the authoritative source and waits for a later inbound past the retry deadline to try switching again. A failure with a pending handover parks the inbound until that deadline. Each conversation starts at five seconds and doubles to ten minutes, clearing the delay on success. The first failed inbound attempt offers the owner a notice with the conversation key and fixed failure class. The admission and recovery rules are in `docs/agents/sessions-recovery.md`. A switch, set or reset writes one scoped audit row when its value changes and replies as the global set route does, with `conversation`; undo and history are the routes above, and an undo of a conversation's entry replies with `conversation` too. A model route is not checked against the chain when it is stored: turns ignore a route the chain lacks, and the model route page lists it with `inChain: false`. Bodies name the conversation as `conversation` (`group:<id>` or `private:<id>`, canonicalized as the persona routes do; anything else is 400). Refusals come in this order: the body, the conversation key and an unknown setting (400); then, under the configuration gate, a conversation that is not admitted (409, for a reset too; admitted means the inbound gate admits it or it is the owner's private chat) and a refused value (400). A reset stores the global setting's default for that conversation (none for the model route: the configured order, whatever `harness.firstRoute` says). Removing a conversation from its allow list (any access change that leaves it unadmitted) clears its values in the same store transaction, with one audit row per value (actor `system`, source `access`) that cannot be undone; admitting it again restores nothing. Store and registry: `docs/agents/runtime-paths.md`. The model route endpoint (`console_settings/models.rs`: `GET /api/settings/models`; UI served at `/models` with a `302` redirect from `/settings/models` via `console_ui.rs`) is a settings route like the others (administrator-only, a selected runtime). The list names `setting` (`conversation.route`), `firstRoute` (the global `harness.firstRoute`, `null` for none), the harness chain in configured order (each route's `id`, `model`, `reasoningEffort`, `maxOutputTokens`, `retry429`, `health` from route health with `state` `ok`, `failed` or `unknown` and, when known, `since` and `class`, and `price` now from the price table, `estimated` for a model the table lacks), `allFailed`, and each conversation that is admitted or holds a stored value with `stored`, `route` (the route its next turn asks first, `null` for the configured order), `inChain` and `order` (the route ids its next turn walks, `docs/agents/harness.md`). A chain that is not configured or invalid gives `error` and no routes; `healthError` and `storeError` say what cannot be read. Route ids and models are shown with harness and endpoint credentials redacted. It reads only the configuration, the settings store and route health. The model page and list skip request-time engine import and load with no DSH running. The UI sets a conversation's route through the conversation set route and resets it to the configured order through the reset route; history and undo are the audit/settings routes'. The DSH model catalog view (`GET /api/dsh/model`) stays until DSH is retired (#78).
- Settings edits the global `harness.routes` setting as an ordered JSON array of route objects. Set parses the array from the text area and the server validates every route. Reset uses `harness.model`, with the same history and undo controls as other global settings. Model routes links to the editor and shows the active chain or its validation error. The settings list, write replies and history mask harness and endpoint credentials in route ids and models. An effective list carrying `redacted: true` opens a blank editor for a full replacement.
- Endpoint credentials in Settings use an empty password input. List, set and reset return only `isSet` for credential values. The store and each history page show `(hidden)` for the old and new values. Undo refuses credential entries. The Settings routes are the write path for these rows. The independent legacy `webSearch.apiKey` config literal is editable through config writes and participates in config audit staleness and undo.


- Reserved2 stores `text`/`plain`/`tail` as 200-unit previews. A message whose rendered text is longer also keeps `textChars` (its real length in UTF-16 units) and `textTruncated: true` in `recentMessages` and `unread`, and its `fullText` once, in `recentMessages` (the list message detail reads), cut on arrival at the `socialV2.context.fullTextMaxChars` then in force (default 4000, range 200..20000); a later setting change does not re-cut stored text. Model-facing message lists and tool results carry the preview and the two markers but never `fullText`; `qq_get_message_detail` returns the full text in `info.text` (by QQ message id or local seq) with `textChars` and `textTruncated`, true only when the message exceeds the cap it was cut at. A message not stored locally is read from OneBot up to the cap now in force.
- `conversation_state.rs` serializes selected `social-v2.json` mutations under `locks/social-v2.lock` (the social gate), waiting up to five seconds (and `social-v1.json` under `locks/social-v1.lock`). A busy holder returns 503 without writing. Config, mode, role and social-state atomic replacements also take `locks/authority.lock`. Sticker send/add/remark hold authority across fresh validation, connect and request transmission, releasing before the response wait. Social writers acquire the social gate first. Authority writers wait up to 20 seconds; other queued social writers can exceed their five-second bound during a transmission.
- Text, burst, poke, sticker and voice sends recheck token epoch, mode, allow/deny policy, role silence, pause, social enablement and the relevant tool flag before each item. Pokes recheck after the member lookup. Text/burst/sticker/voice tool sends and chat-mode replies, commands and interaction notices share `recorded_send::send_chain` (per process). Sticker sends use the registered `reply.stickerPauseMinMs` and `reply.stickerPauseMaxMs` bounds (800–2000 ms by default). The pause runs inside the chain, outside state gates, before the final guard and attempt. A save refuses inverted bounds. Debug/test-clock builds may override the pause; release builds ignore that override.
- Outbox `intent`, `attempt` and outcome are durable. Append locks cover `sync_all`; errors propagate. A torn final line is terminated before another append. Readers skip only truncation JSON errors, with a warning naming file/line; other corruption fails. Unknown delivery is never automatically resent. Text resume refuses sticker and voice batches.
- `recorded_send.rs` alone claims batches and writes intent, attempt and outcome records for chat, tool, voice and sticker sends. Every unknown outcome is checked against the gateway's recent history before anything else: our own message after the attempt carrying the same canonical text, or a `record`/`image` segment, and one history message proves one item. Chat mode accepts the wait for the chain and the history read, but never on a runtime worker: `chat::send_recorded` (and the pipeline's `send_chat_text`) run through `recorded_send::off_worker`, which on the multi-thread runtime hands the worker's other tasks, ingress included, to another thread (`block_in_place`) while the send waits and runs; on a plain thread, a blocking-pool thread or a current-thread runtime it runs inline. Send order, the chain and the intent/attempt/outcome records are unchanged. Command replies and closed-agent answers sent from the ingress loop itself still finish before the loop reads its next event. `block_in_place` still suspends the other futures of the same task: the closed-agent pump's timers wait while one of its replies waits for the chain. Tool, voice and sticker sends run on console threads or the blocking pool and take the chain directly. History proof needs exactly one own matching message after the attempt that no confirmation already claims; an unreadable outbox, a confirmation without a message id, or another unresolved send from another batch in the last 24 hours leaves the item unknown.
- Group mute (`group_mute.rs`): `data/group-mutes.json` under `locks/group-mutes.lock`, keyed `group:<id>`, stores personal (`personalUntil`, -1 = end unknown) and whole-group (`wholeGroup`) restrictions apart; it never touches `social-v2.json` records, so resets keep it. Sources: an own-id `group_ban` notice (lift or zero duration clears; no readable duration = end unknown; other users' notices are ignored), a `user_id:0` whole-group notice (narrow parse; it first advances the entry's write counter so any refresh that began earlier is dropped, then triggers a refresh that carries its operator), a once-per-connection refresh of the groups the allow/deny lists admit at that connection (`get_group_member_info` self `shut_up_timestamp`, `get_group_info` `group_all_shut`, owner/admin exempt from whole-group) plus a ten-minute recheck of unknown-end mutes, and a send or poke refused with retcode 100 and `result=120` (not committed; retcode 100 without it stays unknown), including the first-generation CLI reply path. A refresh started before a newer write, notice or refusal is dropped; an unknown-end personal mute is cleared only by a refresh that also read the whole-group state. While muted, text, burst, direct, poke, sticker, voice, chat and CLI replies are refused locally with no gateway call (403 `{ok:false,error}`, never unknown delivery, even when the refusal's own outbox record cannot be written; model text "muted in this group until HH:MM"; the reserved2 CLI relay treats that 403 as a clean sleep); a send with an agent token marks its open turn as ended, which needs the `waitMessages` tool flag, and without it the turn ends when the model stops. Ingress differs by mode: reserved2 stores a muted group's messages as unread, dispatches no wake for it, and answers them when a new message or timer wakes it after the mute; chat and first-generation reserved ingress mark the muted message handled and drop it. The first-generation reserved scheduler keeps a muted group's queued jobs queued (they become eligible for dispatch again once the mute ends, subject to the normal dispatch checks: authority and generation, DSH health, one turn per group) and does not advance its proactive topics, probes, timers or farewells, with one log line per mute. Each new episode sends one content-free owner notice (group, duration, operator); a lift sends none, and a notice refused by the limiter is not retried. Not mute-aware: the legacy wake pump (`entry.rs` `pump_all`), the administrator test send, a notice for a group the allow/deny lists do not admit when it arrives, and `unknown` outbox records written before the mute existed. Reads fail open.
- Sticker quotas reserve fresh independently identified pending liabilities before network work. Proven non-submission/refusal releases; confirmed and unknown outcomes settle into numeric quota arrays. Text checks include pending sticker sends. Ambiguous refunds retain quota. Confirmed history and settlement share one mutation; failed persistence keeps liability and reports partial success without a second gate wait. Confirmed collection remains successful if settlement fails. Pending reservations expire after one hour; settled arrays retain the newest 500 entries. OneBot connect/write budget is 15 seconds total, with connect at most five seconds; write failures remain unknown.
- Resets preserve only pending sticker liabilities and mark pending IDs revoked; settled timestamps and other conversation state are discarded. Already submitted operations can settle their own ID. Submission validates ownership under authority coordination.
- `socialV2.send.duplicateWindowMs` atomically marks duplicate text before quota reservation. Concurrent duplicate calls receive 429. Successful sends, rather than model text, update reply state and read watermarks.
- The selected browser console uses `http://her.localhost:<bound-port>` on the IPv4 loopback listener. Host validation precedes authentication. Health and icon no-ops are public. The loopback aliases redirect page GETs to the same mount on the canonical host and discard query fields. Existing desktop bearer navigation stays on its original host. Native API URLs stay on their original hosts.
- Native requests without Fetch Metadata use the machine credential with query-token precedence, including explicit empty values. A desktop bearer remains valid for WebView requests with Fetch Metadata. An explicit console credential or agent marker prevents browser cookie fallback. Browser writes require exact canonical Origin and an application/json media type. Browser grants also require canonical Host and reject duplicate Host, Origin or matching cookie names and cross-origin Fetch Metadata. On Windows, an unauthenticated page GET on `http://her.localhost:<port>` without an explicit console token or agent marker and with safe Fetch Metadata (`none` / `same-origin`) and canonical or absent Origin automatically issues a browser session when `same_installing_user` proves the loopback peer runs as the installing user and `security.requirePasswordLocally` is off (`false`, default). Any other user, an unavailable peer (including non-Windows hosts), cross-site requests, `/api/*` requests, or enabling `security.requirePasswordLocally` requires the administrator password.
- A signed-in browser has the same administrator authority as the console token. It may choose the backup destination, generate or choose a new console token and use the other administrator routes under the browser request guards. Rotation replies with `ok`, `token` and `generated`, and deletes the initiating cookie on success. Logout ends the grants it revokes. Completed writes, launched work and credentials already obtained remain effective. Revisit this authority when LAN/TLS is added.
- Each browser grant has a host-only, HttpOnly, SameSite=Strict cookie (`her_browser_<port>_<digest>`) at Path=/ under the bound port's prefix (`Max-Age=604800`). A local program on another `her.localhost` port could receive a cookie; SameSite=Strict stops websites from sending it cross-site. Up to 128 active browser sessions are retained per runtime (oldest evicted on issue). The newest valid issuance sequence selects authority. A successful guarded renewal on non-excluded requests maintains the seven-day idle expiry and renews only that grant's cookie. Expiry at the exact boundary refuses. The persisted clock mark advances even when the presented grant is absent. A backward jump over one minute invalidates all grants without changing the password or throttle. Renewal is capped by elapsed monotonic time since a fixed grant anchor. Restart takes that anchor from the last persisted use.
- Console authentication routes (`/api/auth/*`, selected runtimes only; agent headers or markers are refused with 403 and request bodies are capped at 1 MB): `GET /api/auth/status` reports `passwordSet`, `authenticated`, `authKind`, `canonicalOrigin`, `tokenFile` (`data/console-token`), `consecutiveFailures`, `retryAfterMs`, `retryAfterSeconds`, `requirePasswordLocally` and `localAutoSignInAvailable`. `POST /api/auth/first-run` (`{"consoleToken","password"}`) requires exact canonical browser Host/Origin, JSON media type and non-cross-site Fetch Metadata; it verifies the effective console token, stores the Argon2id hash (8–1024 characters) in `data/settings.db` with a masked `(hidden)` audit row while leaving `config.json` untouched, issues a browser session cookie and refuses subsequent attempts with 409. `POST /api/auth/login` (`{"password"}`) requires canonical browser origin/JSON guards, verifies the stored password and issues a browser session cookie (409 when unset; 401 on wrong password). After 5 consecutive wrong passwords, further login attempts wait 1, 2, 4, 8 and up to 15 minutes (`throttle_delay_ms`, clamped to 15 minutes against clock rollbacks), never locking out permanently; attempts during the active window return 429 with remaining `retryAfterMs` / `retryAfterSeconds` without advancing the counter. Successful login or `her-cli console reset-password` clears the throttle. `POST /api/auth/logout` revokes any current browser session and expires the port's browser cookies (`Max-Age=0`). `POST /api/auth/change-password` (`{"currentPassword","newPassword"}`) requires current administrator admission, verifies the current password, records a masked audit entry, rotates `auth_generation` to end all other browser sessions, clears throttle, and for a browser caller rotates only this session's cookie. `GET /api/auth/sessions` lists valid browser sessions (`id` digest, `origin`, timestamps, `current`) without secrets, and `POST /api/auth/sessions/revoke` (`{"id"}`, `{"others":true}` for browsers, or `{"all":true}`) rechecks authority under the configuration gate before revoking. Offline CLI (`her-cli console set-password|reset-password --runtime-root <root>`) and full backup restore (restores archived PHC or first-run state, never restores sessions or throttle, invalidates every session on full restore, leaves auth alone on memory-only restore) coordinate under the credential mutation, configuration and settings store gates.
- `console_front.rs` owns one declarative route-policy table (`RoutePolicy`, `EXACT_ROUTES`, `route_policy`, `supports_request`) unifying route admission, public probes, `AgentPolicy`, `KeyPreflight`, `BodyLimit` (`bounded_post_body_too_large`), and `SessionCookiePolicy` (renewal/no-renew/delete-on-success), alongside embedded Vite/React SPA & static asset delivery (`console_ui.rs`), Host, Origin, JSON, credential admission (`admit_selected_request`), desktop sign-in and `/api/auth/*` HTTP adapters calling downward into `console_auth.rs`, the audit wrapper, and the `VerifiedCaller` / `AdminCaller` authority passed to routers and admin sub-routers (`console_settings`, `console_persona`, `console_schedule`, `console_tasks`). Embedded HTML and `/assets/*` responses carry `X-Content-Type-Options: nosniff` and strict `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; connect-src 'self'; form-action 'self'; base-uri 'none';`. `/assets/*` serves static bundle files on allowed loopback hosts (and refuses agent markers with 403 and missing assets with JSON 404); legacy URLs (`/personas` -> `/persona`, `/tasks` -> `/schedule`, `/settings/conversations` -> `/conversations`, `/settings/models` -> `/models`) return `302` redirects; other non-API extensionless GETs serve embedded `index.html` unless an explicit invalid console credential (`401`) or agent marker (`403`) is presented; unknown `/api/*` paths never fall back to HTML. `her/build.rs` embeds `her-ui/dist/` (`HER_REQUIRE_UI_DIST=1` or release builds fail if missing/empty; pure-Rust debug tests without it compile with the minimal placeholder stub). A required configuration read failure returns 503 before renewal, routing or audit. Writers and queued work recheck the same proof under their publication or start gate. A revoked proof returns 401 and an unavailable store returns 503. Agent routes keep their live conversation, paused/disabled and mode checks. Status/send/image exceptions remain explicit in `console_agent.rs`. `console_auth.rs` depends downward on `settings` store primitives and runtime/social gates with no `console` dependency, and enforces `credential_mutation_gate -> config_gate -> browser_anchors -> store_gate` (Argon2id outside all gates).
- `conversation_state.rs` owns persisted `social-v2.json` (and `social-v1.json`) storage, tolerant typed parsing (`ConversationState`, `SocialDocument`, `Conversation` owning `token`, `generation`, `unread`, and `impressions` while refusing direct dynamic reads/writes/removals of those reserved keys and preserving unknown fields and existing key insertion order on atomic write), and the social gate (`locks/social-v2.lock`, rechecking any `console_authority` proof under the gate before committing). `social_state.rs` owns social-state domain authority over `conversation_state.rs`, returning typed `SocialError` domain errors: runtime mode reads/transitions, owner-conversation and allow/deny admission predicates (`inbound_admitted`, `admitted_ids`, `access_allowed`, `approved_group_allowed`), token/generation rotation and verification, role-state/wake/reserved2/reset lifecycle transitions, wake-default reconciliation, and immediate access-change revocation behind an internal `SessionStopper` trait and `StopTracker` seam. `config_tx.rs` owns coordinated configuration/settings/access/wake transactions (`ConfigDiff { before, after }` returned directly via `CommitOutcome` and `CommitError` without thread-local buffers) across `config.json`, `settings.db`, pending access revocations, and inherited wake-config refresh under monotonic lock order (`locks/restore-writers.lock` -> `credential_mutation_gate` -> `closed_agent::lock` -> `config_gate` -> `store_gate`). `console.rs` and `console_access.rs` wrap `social_state` and `config_tx` as thin HTTP adapters translating domain/commit errors and recording `ConfigDiff` on `VerifiedCaller` at the HTTP boundary; non-HTTP runtime callers (`memory_actions`, `lifecycle_cli`, `snowluma_heal`, `turn_engine`, `wake_words`) invoke `social_state` and `config_tx` directly.
- Memory administration still accepts a nonempty configured `x-console-token` header on native requests without Fetch Metadata, or a live desktop bearer. Query-first console admission still applies. A generated file credential carries no raw memory administrator capability. A browser ACL GET lists entries and accepts no action or body. A browser grant or revoke uses POST with exact canonical Origin, application/json and a bounded JSON object. Its fields come from that object. The mutation rechecks the admitted browser proof under the configuration gate before calling the memory administrator. Agent and owner-private checks remain conversation-specific.
- Whitelist/security/token/undo writes hold the social gate across fresh raw config read, atomic write and audit capture. The allow and deny lists, the owner and the three `security` switches (`security.interceptNotify`, `security.outboundGuard`, `security.requirePasswordLocally`) are security settings: `POST /api/whitelist`, `POST /api/security`, `POST /api/conversations/scope` and the audit undo change one only with `"confirm": true` in the body (409 otherwise, nothing written; `her-cli conversation`'s `--confirm` confirms), validate it by the registry (400, nothing written), store it through the settings store after the revocation is recorded and keep the file's registry members as the store wrote them back; `confirm` is never written into `config.json`, a whitelist write that does not name the owner leaves it as it is (naming it `null` or blank clears it, under confirmation), and a stored list change shows in `GET /api/whitelist`. `POST /api/whitelist` keeps its JavaScript-compatible id parsing (an id sent as "07001" is stored as 7001, confirmed through the 409 that names the changed lists), while the settings set route refuses a leading-zero id (400). Once the store holds an access change, a failed `config.json` write keeps its pending revocation. Owner-only whitelist changes preserve existing alias lists; naming a root's list rewrites that root as `{private, groups}`. Access changes acquire the closed-agent interaction gate, retire revoked mappings, rotate every affected token, clear bootstrap, cancel turns and settle queued ingress before responding. A later re-grant creates a fresh epoch. Failures are reported even if another cleanup step succeeded. An access change (whitelist write, `POST /api/conversations/scope` or `her-cli conversation`, audit undo) records its revocation in `data/access-revocations-pending.json` (mode and the allow, deny, `allowAllWhenEmpty` and owner policy before and after) before it writes `config.json`, and removes the entry once every revocation step succeeded. Console start, and every access change before its own write, finish each pending entry by its recorded policies, so a re-grant made meanwhile never brings the old epoch back; a crash before the write still finishes the recorded revocation (the conversation keeps its access with a fresh epoch). A failed `config.json` write removes its entry only when the file still holds what the change read (nothing was published); a failure after publication, such as the folder sync, keeps it for the next console start or access change. While an entry cannot be finished, the record file is unreadable or malformed, or an entry lacks `before` or `after` as policy objects (a missing mode or reason uses the current mode), access changes answer 503 and write nothing. A revoked conversation's DSH session stop is recorded in the same file (`stops`: conversation and session) before its mapping is retired, and removed only once the stop succeeded; console start and every access change run the recorded stops again in the background (a failed stop never refuses a change), and a retried closed-agent owner change also selects the conversations those stops name. Each revocation attempt records the conversations it selected in its entry (`targets`) before any step, and a retry selects them again, so an attempt cut off after retiring a mapping or after its stop finished still rotates the token before the entry clears. A `stops` field that is not an array of `{key, session}` strings, `targets` that are not an array of strings, a target that is not a canonical conversation key, or two pending entries with the same `id`, refuses access changes like an unusable entry; a record without `stops` is accepted.
- A conversation is answered only when two configuration keys agree: its allow list (`allow.groups` or `allow.private`, minus `deny`) and `rollout.rustGroups`. Every inbound gate reads the configuration through `RuntimeContext::load_config` for each event, so an edit applies to the next event without a restart: reserved2 and the first-generation path use `social_state::inbound_admitted` (listed in the allow list and not denied; `allowAllWhenEmpty` does not widen it), chat mode keeps `chat::allowed_in_mode`. Reserved2 tick invalidation and dispatch, wake claims, turn validity, turn recovery and wake snapshots use the same rule with the configuration read at that use, so adding `deny` also stops a wake already queued. Gap recording, saved-event replay, mute refresh, group cards and mute notices use `social_state::inbound_admitted` with the configuration read at that connection or notice. At a reconnect, saved events of conversations no longer admitted are settled; an unreadable configuration leaves them saved. `rollout.rustGroups` is the explicit array of canonical keys the supervisor passes to the live process as `--live-groups`. Each item contains one distinct `group:<id>` or `private:<id>` key. The live process serves only that list, fixed at launch, because it holds the per-conversation source gates for it (`docs/agents/lifecycle-tasks.md`). `rollout.enabled: false` silences the admitted-but-unserved report and the startup check against `--live-groups`; the supervisor serves `rollout.rustGroups` either way. Live startup and the health check report both kinds of gap (served but refused, admitted but unserved).
- `POST /api/conversations/scope` (`{"conversation":"group:<id>" or "private:<id>","action":"admit" or "remove"}`; administrator only; the body never says `key`) and `her-cli conversation <admit|remove> <conversation> --runtime-root <root> --confirm` update both keys under the closed-agent interaction gate and the social gate, then revoke as a whitelist write does. Both settings changes and their audit rows commit in one SQLite transaction. Write-back mirrors the committed values to `config.json`. If write-back fails, the reply includes `mirrorError` and the committed settings already apply. Admitting a denied conversation, or a runtime without an explicit `rollout.rustGroups` array, is refused with 409 and nothing written; a malformed body is 400. Other allow-list entries keep their values; an alias list of the changed kind (`allow.group`, `allow.privates`) moves to `allow.groups` or `allow.private`; served entries are matched in canonical form. Settings set, reset, undo and legacy access writes check the proposed subset before commit. Each kind whose allow membership changes must cover that kind’s served entries, and a rollout change checks both kinds. An incomplete legacy admission can be repaired with the scope action. The reply lists `changed` keys, `revoked` conversations, `scope` (`notAllowed`, `notServed`) and `liveRestart`: `none` (no live process, or it already serves the new list), `required` (it serves the list it started with: the supervisor's watchdog restarts it with the new list on its next two-minute run, or run the watchdog task now) or `unknown`. Console requests are audited and can be undone there. The CLI writes no console audit record; it waits up to ten seconds for retired DSH sessions to stop (else the reply carries `sessionStops`), prints the reply as its last stdout line and exits 0 done, 2 usage or malformed request, 3 refused or failed.
- `qq_wait_for_messages` (`POST /api/socialV2/wait`) holds a generation lease per normalized conversation. A new wait supersedes the previous one, which returns `superseded: true` with no messages within one poll and records no observation; a dropped handler releases only its own generation. A console wait (no agent token) never supersedes an agent's wait: it is refused with 429 while one runs. Every reply/messages/quiet poll rechecks the lease. Agent waits also recheck the agent token: a poll whose state read fails is skipped, and only a read state with a different token or no conversation ends the call (403). A lone agent wait retires on token rotation within its polling interval (80/100/200 ms); console waits recheck the lease only.
- Whole reset records ledger reset `*`, settles ingress, retires mappings, writes fresh conversations with `resetEpoch`, cancels turns and stops DSH work. Manual reserved2 wake rechecks authority and mode, queues at most 20 epoch-bound admin wakes, buffers while busy and obeys rate limits. The hub cancels only the captured old DSH session across reset/mode changes.
- Audits record method/path/status/result/error/key without request bodies; changed files have blobs, with config tokens redacted. Failed audit leaves the operation's status and adds `audit.ok:false`. Undo supports config/role-map only, checks the file's current state under the state gate (a configuration record compares `afterRegistryFreeSha`, the digest of the canonical document without the settings-registry members other than the security settings (a missing, null or empty member left on their path included), so a settings write-back of another setting is no later change; a record without it, and role-map, compare the raw `afterSha`), restores the security settings the backup holds through the settings store after recording the revocation (it needs `"confirm": true` then, 409 otherwise; a backup list the store cannot keep is 409), retains the current console token and the current file's value at every other settings-registry pointer (the reply's `settingsKept` lists the registry keys whose backup value differed; those settings are undone on the settings page; an undo whose backup has a non-object where a registry value lives, so the value cannot be kept, is refused with 409 and writes nothing), refuses token-change/no-file records and is itself audited. Retry of a `send-unresolved` turn needs `confirm:true`; abandon revokes its token first.
- `feedback.rs` exclusively owns `<data>/feedback.json`, newest 500 redacted entries. A process mutex and five-second OS gate serialize it. Non-array data is renamed before starting an empty array; failed preservation refuses the mutation. Agent submissions obey session/tool/length limits plus five/minute and twenty/hour; console submissions use the console policy. Owner error notifications deduplicate by key for 60 seconds, ten/hour.
- `activity.rs` owns redacted `<data>/qq-activity.log`, rotating after 500 lines and serving the newest 100 to the console only. Writes are best effort. Feedback, sends, ingress decisions, turn outcomes and slang completion record their activity. Pause affects reserved2 scheduling and agent gates; resume does not replay old pending wakes. First-generation and chat modes ignore pause.

- Outbound replies and console text/voice requests read `security.outboundGuard` per reply/request. Only boolean `false` disables the outbound sentinel, sensitive-reply hiding and blocked-reply notices; missing, invalid and `true` preserve the default guard. `security.interceptNotify` separately controls notices while enabled. Both are security settings, read through the registry (`settings::OUTBOUND_GUARD`, `settings::INTERCEPT_NOTIFY`, `Setting::switch`). Model-input stripping and owner-only model/backend failure routing remain independent of the switch.

Changes to the registered default message-wake probability or batch window refresh inherited wake plans under the held configuration gate (`locks/social-v2.lock`) inside `config_tx` (`commit_setting_write`, `commit_chat_settings`). Social saves of wake defaults, audit undo of wake changes and every console startup run the same reconciliation (`social_state::reconcile_default_wake_configs` via `config_tx`), under the social/configuration gate. Under that gate it requires a successful settings read, patches only fields whose effective values differ and skips the write when all match. An omitted batch window follows the global setting. An omitted probability is zero. Switching to infinite sleep removes the deadline and disarms its timer. Switching to finite sleep or changing the effective finite sleep range draws a deadline and records the range. Older finite plans without a recorded range retain their deadline on startup and use the pre-save range for live edits. Counters, confirmation time and dropped persona names survive. A no-action reset that copies custom keywords records the recommendation in effect so those words survive an empty or unchanged recommendation. Model- and operator-confirmed plans keep their own settings.
