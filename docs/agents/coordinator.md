# Coordinator

Binding for coordinator sessions; plan runs and the `planner` agent read "Planner" and its "Threats": the Linux main session and the Windows coordinator. The rules every agent obeys (hard limits, where ticket material goes) are in `AGENTS.md` "Subagent workflow"; who acts next and how to hand off are in `docs/agents/baton.md`.

## Role

- The coordinator is the Linux main session (Opus) and never implements: it picks ready issues (open, unclaimed, its host label and baton, blockers closed), claims them (`docs/agents/issue-tracker.md`), sizes, investigates by reading, plans and routes them, relays plans, caps fix rounds, owns every owner question, checks reports by their receipts (exit files, test-result lines, diff), runs the merge gates, merges, pushes, keeps the ticket's handoff current and closes the issue after merge. Few status turns while waiting.
- A worker returns its report as its final message; save it to the ticket's report file (`/root/orch/her/<ticket>/report-<run>.md`, Windows `C:/her-orch/<ticket>/report-<run>.md`) before acting on it. A Codex run's report is its `<name>.report.md`.
- A Claude worker that dispatched `quick.yml` ends its message with a "CI running" handback instead of waiting; wait for its runs and resume it with the result ("GitHub API budget"). After a Codex implement run, dispatch the targets its brief names yourself and wait for them.
- Hand off with `scripts/handoff.sh` / `scripts/handoff.ps1` (`docs/agents/baton.md` "Handing over"), and keep the baton watcher running between handoffs (`baton.md` "Watcher").

## Sizing

Size every ticket before routing and record the size on the ticket. Decided: can the exact change be written now (if not, `?`)? Blast radius: files and call sites (grep the symbol), crates crossed. Loop length: a single Linux test target is short; database, migration, release/pack or Windows-native loops are long. Risk area: auth and tokens, keys and release signing, ACLs and isolation, deletes or moves of user data, migrations, production.

| Size | Signals | Route |
|---|---|---|
| XS | decided, 1–2 files, one Linux test target | Codex `gpt-6.2-sol` implements from a coordinator brief |
| S | ≤ ~4 files in one crate, short loop, small design call | Codex `gpt-6.2-sol` implements from a coordinator brief |
| M/L | several crates, long loop or real design | `gpt-6.2-sol` plans (plan and scratch export), then `gpt-6.2-sol` implements the plan |
| ? | cause or approach unknown | `gpt-6.2-sol` investigates (read-only), then size the resulting plan |

Codex runs are in "Codex runs": sol at effort `medium` for implementation and fixes, `high` for plans and investigations.

Escalation: when sol hands back that it cannot do the step, or when CI fails the same way twice on its runs, the step goes to `gpt-6.2-astra` at effort `high`; the escalated step does not return to sol. Escalate before review, never after: a defect caught in a review round costs more than the astra run. Escalation never changes the review route, and the ledger records the escalated run under the same ticket and size.

Fallback: while a Codex run's `<name>.exit.txt` reads `quota`, the Claude routes carry the ticket. XS and S: `ticket-implementer` on Haiku, Sonnet on escalation. M/L: the `planner` agent (Opus) plans, Haiku executes, and a step Haiku cannot finish goes back to the planner once and then to Sonnet. `?`: Sonnet investigates, Opus if hard. The route changes between runs, never inside one; a ticket goes back to Codex at its next run once Codex answers again. `no-report` and `timeout` are not quota: read the run's err log, then rerun once or escalate.

Record every Claude subagent run with `scripts/agent_usage.py record --agent <id> --ticket <n> --size <size> --host <linux|windows>` (ledger `.scratch/her-supervisor/agent-usage.jsonl`, private run data that stays untracked and is never published); after merge compare the predicted size with the measured cost and adjust the borders. The baseline and the weekly verdict live in the vault (`C:/her-vault/.scratch/her-supervisor/agent-usage.md`).

## Codex runs

- The coordinator starts every Codex run, hidden and in the background, from the integration checkout (`/root/her`, Windows `C:/her`), as one plain command per run. Write the prompt from `docs/agents/templates/sol-plan.md`, `sol-implement.md` or `sol-fix.md` into `/root/orch/her/<n>/prompts/<name>.md` (Windows `C:/her-orch/<n>/prompts/`); the run's receipts land beside it. `HER_GITLEAKS=<path to gitleaks>` goes before an implement command.
  - Implement or fix: `scripts/codex-work.sh implement <name> <worktree> <prompt> [model [effort [minutes]]]` (Windows `powershell -NoProfile -File C:/her/scripts/codex-work.ps1 -Mode implement -Name <name> -WorkDir <worktree> -PromptFile <prompt>`, optional `-Model`, `-Effort`, `-TimeoutMinutes`). Defaults: `gpt-6.2-sol`, `medium`. Codex runs unsandboxed like a Claude worker, with network access and the host user's git credentials. It commits and pushes only its own `her/<n>-<slug>` branch. The brief forbids force pushes and requires the pre-push hook and public scan. The wrapper's pre-run refusals and post-run checks guard the workflow (T5). The wrapper sets `TMPDIR` to the ticket's `tmp/` (also `TEMP` and `TMP` on Windows) and passes `HER_GITLEAKS` from the command's environment.
    - Before the run, the wrapper requires a clean worktree on `her/<n>-<slug>`, `HER_GITLEAKS` set, a ticket folder and `tmp` free of links, and a response from the remote (`HER_REMOTE_URL`, default `https://github.com/bubbleofmoon/H.E.R..git`). If the remote branch exists, local HEAD must match it.
    - The brief tells Codex to push with `git push origin <branch>`. The wrapper ignores branch tracking entries in both Git config snapshots.
    - The wrapper checks the config after every run, including failures. After Codex exits 0 with a report and the config check passes, the wrapper verifies the result and writes the receipts below. A failed, quota or no-report run may leave changes in the worktree.
  - Plan: `scripts/codex-work.sh plan <ticket> <name> <prompt> [model [effort [minutes]]]` (`-Mode plan -Ticket <n> -Name <name> -PromptFile <prompt>`). Defaults: `gpt-6.2-sol`, `high`. Codex writes only the ticket's scratch export and `plan-out/`; the wrapper copies `plan-out/plan.md` (a regular file with one link) to `plan.md` and writes `plan.sha256`; a failed install puts the old pair back.
  - Investigate: `scripts/codex-task.sh <name> <workdir> <prompt> gpt-6.2-sol high read-only [minutes]` (`codex-task.ps1 -Sandbox read-only`): no writes.
  - The model is `gpt-6.2-sol`, or `gpt-6.2-astra` on escalation; the effort is `medium` or `high`.
- Receipts beside the prompt include `<name>.exit.txt` (the numeric code, `timeout`, `no-report` or `quota`), `<name>.report.md`, `<name>.plan.txt` (plan: `installed` or `no-plan`; a directory or hard link is `no-plan`) and, for implement, `<name>.push.txt`, `<name>.staged.txt` and `<name>.scan.txt` (public scan output when run).
  - Before the run, `push.txt` records `pre-remote-mismatch` with exit 8 when local HEAD is ahead of, behind or diverged from the remote. After the run, line 1 records the first applicable state in this order, with exit 8 unless noted. `config-changed <files>` (T5, including failed runs), `rewritten` (pre-run HEAD is missing or fails the ancestry check), `branch-changed <branch>`, `git-failed`, `dirty <paths>` (uncommitted or untracked files), `remote-moved` (local HEAD stayed at its starting commit but the remote head changed), `no-changes` (both heads unchanged, exit 0), `unpushed` (local HEAD changed and could not be verified on the remote) or `pushed <sha>` (exit 0). After `dirty`, the next line says `remote moved` or `remote unchanged` against the branch head before the run, or `remote unknown` if the lookup failed.
  - When the commit range can be read, `protected <paths>` follows if commits touch `.githooks/`, `scripts/check-repo.py`, `scripts/scan-public.py`, `scripts/tests/test_scan_public.py`, `.gitleaks.toml` or `.public-scan.json`. The gate reviews each listed path in full. `scan-refused` follows with exit 8 if the public scan refused the commits or could not run (detection only, T5).
  - `staged.txt` lists the commits since the pre-run HEAD (`commit <sha> <subject>`) and the name-status of every path they touched.
  - Only `pushed` and `installed` are results; check the receipts, not the report's claims.
- After `pushed <sha>`, dispatch the brief's CI targets for that sha, wait for them ("GitHub API budget") and review. A red run or a review finding goes to a fix run from `sol-fix.md`.
- `.claude/hooks/agent-guard.sh coordinator` is the guard role for a coordinator session that wires it (none does by default): it pins the forms above (model, effort, ticket files, the worktree's ticket branch) and refuses any other Codex call, a quoted string that starts with `codex` included.

## Planner

- Planning runs on the Linux coordinator only for now: a Windows coordinator hands an M/L ticket to Linux for planning (`baton:linux`) and gets the plan back as its work item.
- A plan run (`codex-work plan`) reads the real code, writes its exact edits into a scratch export of the base and writes the plan to `plan-out/plan.md`, which the wrapper installs as `/root/orch/her/<n>/plan.md`. Those are its only writes. It never builds, formats or runs code. Send a revision as a new brief (`sol-plan.md`) that names the plan and the findings.
- While Codex is unavailable, the `planner` agent (`.claude/agents/planner.md`, M/L only) does the same job: it writes the plan file and the scratch edits itself and returns a short summary with the plan file's `sha256sum` line and its path. Send revisions to the same agent with SendMessage.
- Reuse (`CONTRIBUTING.md` "Reusing code"): prefer a maintained crate over writing a well-established part; code ported from a permissively licensed project (MIT, Apache-2.0, BSD, ISC, Zlib, CC0) is allowed when no crate fits and keeps its notice in `her/THIRD_PARTY_NOTICES.md` (Apache-2.0: also the upstream NOTICE text and a mark on each changed file); never GPL-family, non-commercial or unlicensed code; the qq-bridge upstream stays clean-room (features and bugs only). Every plan and plan brief names the crate or source each step reuses.
- Before each planning round, after `git fetch origin main`, run `scripts/plan-export.sh <n> --replace` from `/root/her` (Windows `scripts/plan-export.ps1 -Ticket <n> -Replace`). It deletes the old `scratch` and `scratch-evidence`, exports `origin/main` into `/root/orch/her/<n>/scratch` with no `.git` (no refs or config shared with the checkout) and prints the commit exported, which is `<base>` for the plan.
- When a plan run reports, `sha256sum -c /root/orch/her/<n>/plan.sha256` (the wrapper wrote it) must pass, and again before relaying the plan. For the `planner` agent, run `sha256sum /root/orch/her/<n>/plan.md`, compare it with the line in the agent's message and save it as `plan.sha256`. A mismatch means another agent wrote the file: plan again.
- Then check the scratch edits yourself. The build-file check is required, because these files run code on whichever host builds the plan, CI included:
  1. `(cd /root/orch/her/<n>/scratch && find . \( -name .cargo -o -name 'rust-toolchain*' -o -name build.rs -o -name Cargo.toml -o -name Cargo.lock \) | LC_ALL=C sort)` prints exactly `./her-memory/Cargo.lock`, `./her-memory/Cargo.toml`, `./her/Cargo.lock`, `./her/Cargo.toml` and `./her/build.rs`, one per line. `find /root/orch -maxdepth 3 \( -name .cargo -o -name Cargo.toml \)` prints nothing.
  2. Each of those five files matches the base: `git -C /root/her show <base>:<f> | cmp - /root/orch/her/<n>/scratch/<f>`. A file the plan changes on purpose: read its diff before building. If the tree at the base tracks other build files (`git -C /root/her ls-tree -r --name-only <base>` and the same name filter), the list follows the tree.
  3. Read the scratch edits against the code. No local build: the executor's first `check` and `lint` runs on CI compile and format the plan.
  4. Send every error back to the plan run as a revision brief.
  5. Run `HER_GITLEAKS=/root/.cache/her-tools/gitleaks/gitleaks python -I scripts/scan-public.py --root /root/orch/her/<n>/scratch` before the executor starts. Reviewed digit-run exceptions are keyed by the whole line, so a plan that appends text to such a line is refused at push time; send it back for revision instead.
- A coordinator brief is a plan too: a hand-written XS/S brief with code in it goes through a plan run, or is checked by one, before the executor starts.
- The executor's first step runs the red tests: Rust on its first `quick.yml` run, scripts locally. A plan that needs a red receipt for each new Rust test follows `docs/agents/templates/red-revert.md`.
- When the plan is accepted, delete `/root/orch/her/<n>/scratch` and `/root/orch/her/<n>/scratch-evidence`.
- Plan format and known pitfalls: Judgement parts (races, ordering, design calls) are written as exact edits too, so the executor follows the whole plan; it stops and hands back where the plan does not hold, and the plan run revises it. Plan format for any handoff: (1) root cause or goal with evidence (file:line, command output); (2) the exact change per file:line, as find → replace when mechanical, or exact steps plus the commit SHA; (3) the first test to write and see fail, then the rest. Every plan ends with a "Known pitfalls" list the executor checks before reporting: processes and temp files cleaned up on every failure path (process groups killed, try opened before the first spawn); boundary cases of every threshold or limit tested on both sides; paths resolved the way the consuming tool resolves them; no stale artifacts from an earlier run; every new test seen failing for the right reason (the plan names the change that turns each new check red, as in `docs/agents/templates/red-revert.md`); a plan that adds a lock, transforms model-bound text or compares canonical forms holds to the matching `CODING_STANDARDS.md` rules ("Concurrency", "Model-facing text", "Comparisons"); line endings and file modes preserved; no step needs a commit amend, a reset or a merge (workers make plain commits only), and no edit appends to a line that carries a reviewed scan exception.

### Threats (risk area: the agent guard)

A plan that touches the guard, the agents or the Codex form carries these threats, and each failure case becomes a required test in its plan. The guard stops plain attempts; it does not enforce. No case is left as "bounded" or "unlikely"; and, for a change to the guard or the agents, the guard is described as stopping plain attempts, never as enforcing.

- **T1. Code execution and the limits of the guard.** python and other interpreters run unrestricted for implementers and gates: through them an agent can write anywhere and read anything the host user can, including the vault checkout, `gh` credentials and, on Windows, the production host's files. For implementers and gates the guard matches parsed shell text and stops plain attempts only; the containment boundary is #85. Reviewers and planners run no interpreter: their Bash calls must fit the allow-list (T11). A changed `her/build.rs`, manifest or `.cargo` config in the scratch edits runs code on whichever host builds the plan, CI included, so the build-file check before relaying every plan is required.
- **T2. No ticket binding for the `planner` agent.** The hook is stateless, so a planner for one ticket can write another ticket's plan file or scratch export. Mitigation: one planner per ticket at a time. The planner's final message carries the plan file's `sha256sum` line; the coordinator compares it with its own `sha256sum` when the planner reports, and again before relaying the plan. The scratch export is re-made from `git archive` before each planning round. A plan run is bound by its wrapper: `codex-work plan <n>` gives Codex write access to that ticket's scratch export and `plan-out/` only, and installs the plan itself.
- **T3. Windows path forms.** Refused: junctions and other reparse points on any part; `.git` in any NTFS spelling (`.GIT`, `.git.`, `.git ` with a trailing space); `:` in any part (streams, `::$DATA`); 8.3 names `git~N`; control characters; `\\?\`, UNC paths, other drives and a different case of `her-orch` (they fail the path pattern). An 8.3 short name of another existing folder inside scratch can only point inside scratch, so it is harmless. `C:/her-orch/…` also matches on Linux, where it is a relative path under the cwd; a write there lands inside the cwd and is harmless.
- **T4. Git metadata.** The scratch export has no `.git`, so it shares no refs or config with `/root/her`. Reviewers and planners run git only as one plain read inside an allowed pipeline, with no assignment, wrapper, `$`, backtick, glob or brace before or in it. Refused git arguments: any starting with `--out`, `--ext`, `--op` or `-O`, any holding `$`; for `git grep`, any single-dash bundle containing `O`; and the global `-c`, `--git-dir`, `--work-tree` and `--exec-path`. A `-C` into a ticket folder or a scratch export (`/root/orch/her/`, `C:/her-orch/`) is refused. `git branch` and `git remote` pass only in their listing forms. A read still runs the repository's own configured drivers. That config is the coordinator's, except in the git dir a Codex implement run can write: after a `config-changed` receipt (T5) nothing is read or run in that repository until the coordinator has inspected it.
- **T5. Codex runs (the coordinator's alone).** Codex can read host files, including the vault checkout and credentials, and send what it reads to the model provider. The coordinator writes the prompt. Containment is #85. Plans use `workspace-write` with the ticket's scratch export and `plan-out/` as writable roots. Investigations use `read-only`. Implement runs are unsandboxed like Claude workers. They can write any ref, hook and config of the shared repository with the host user's permissions. The brief sets the limits (only `her/<n>-<slug>`, never `main`, never force, never `--no-verify`). The wrapper's pre-run refusals and post-run checks guard the workflow.
  - Before and after the run, `codex-work` hashes the output of `git config --file <file> --list` for the common `config` and the worktree's `config.worktree`. It drops `branch.*` lines, treats absent files as empty and reads the entries with fsmonitor, hooks and include expansion disabled. `commondir`, the worktree's `.git` file and files under `hooks/` keep their byte hashes. A difference stops verification with `config-changed <files>` and exit 8, even for a failed run. The coordinator inspects the files before running git in that repository.
  - After the run every git call of the wrapper uses the git dir it found before the run, `core.fsmonitor=false` and `core.hooksPath` off, and reads the remote head from the fixed URL (`HER_REMOTE_URL`, default `https://github.com/bubbleofmoon/H.E.R..git`), never `origin`. Coverage excludes `<common>/config.worktree` for a linked worktree, `info/attributes` and other worktrees' config. The PowerShell wrapper also misses replacement of the common `hooks/` directory with a link.
  - After the config check, `rewritten` and `branch-changed` take precedence over commit-range failures. The wrapper observes only the ticket branch on the remote.
  - The `scan-refused` line is detection after the push: `scan-public.py` of the wrapper's own checkout (never the worktree's copy) runs on the repository's main checkout and its scan config over the new commits, with the mode the pre-push hook uses (`--added-from-stdin`, or `--revs-from-stdin` for a branch the remote did not have, plus `--objects-from-stdin`). It cannot undo a publication, and a run can still publish unseen by it: with `git push --no-verify`, with another hook or `core.hooksPath` set for its own commands, by pushing a URL other than `origin` or a ref other than its branch, or text outside the commits (an issue, a comment). The pre-push hook inside the run is the only barrier before publication. `codex-task.ps1` (Invoke-Cleanup) deletes the paths listed in `<Name>.cleanup.txt` within `C:/her-orch` and `C:/her-targets` in every mode. Sandboxed modes keep `prompts/` outside their writable roots. Unsandboxed implement runs can write the cleanup list. Read-only cleanup is tracked in #86. The guard's `coordinator` role pins the forms only when a session wires it.
- **T6. Concurrency.** Planners for different tickets have separate exports. Nothing builds locally, which keeps memory bounded on the 7 GB Linux host. Two planners never work on the same ticket at once. Planning runs on the Linux coordinator only.
- **T7. A restart midway.** It can leave a scratch export and `scratch-evidence` behind. Before every export the coordinator deletes both. An export into a non-empty folder is not allowed, because stale files would be checked too.
- **T8. Rule changes reach running agents.** The hook script is read on every call from `$CLAUDE_PROJECT_DIR`, so a change to its rules applies as soon as the main checkout pulls the merge; `git pull` replaces files by rename, so it does not break a running call. An unknown role is refused for every call. Through python, which the guard does not restrict for implementers and gates, an agent can still do everything T1 lists.
- **T9. The implementer and gate denies are an approximation.** Command words are found at command positions: after unquoted newlines, the keywords `if then else elif do while until ! { function`, redirection operands, `{` and find -exec. `eval`, `builtin`, `coproc`, `source`, `.` and `watch` are wrappers, and the operand of `<`, `<<<` or `<>` counts too. Comments are dropped, and quoted operators stay inside their word. Not seen: a program not on the wrapper list that runs another program (`parallel`, `unshare`, `chroot`, `systemd-run`); a command held in a variable; brace expansion; nesting deeper than three levels; PowerShell cmdlets after `powershell -Command`. `gh-public`, `handoff` and `codex` are also refused by name anywhere in a command that has a wrapper, `$` or a backtick. This is the T1 class; #85 is the boundary.
- **T10. False denies, accepted because they fail closed.** For reviewers and planners, anything outside the allow-list is refused: `cd … &&`, a newline between commands, `>/dev/null` (only `2>/dev/null` and `2>&1` pass), unquoted globs (quote the pattern, or use the Glob tool), a path-qualified reader (`/usr/bin/git`), `rg --pretty` (the `--pre` prefix), and an apostrophe in a comment (`echo a # it's` is unparseable). For implementers and gates: a nested string that names `codex`, `gh-public` or `handoff` after a wrapper; `timeout 5 grep codex x`; an apostrophe in a comment (`echo a # it's` is refused as unparseable); heredoc body lines starting with a tool name (write such files with the Write tool); and, with a `$` in the command, any mention of `codex`. From the CI-waiter rule: for implementers and gates every Bash command whose text mentions `ci-wait` is refused, wherever the name stands (a path, a quoted argument, an assignment value, `+=`, a worktree path such as `her-wt/90-ci-wait`, `git log --grep 'ci-wait'`, `cat scripts/ci-wait.py`, `echo ci-wait`), so searching or reading the waiter goes through the Grep and Read tools. A quoted argument starting with `watch` (`--search "watch it"`) makes the command count as having a wrapper, so the name rules above apply to it. A quoted argument that is itself a gh polling command (`--search "gh run watch"`) is refused as polling.
- **T11. The read-only allow-list.** A reviewer's or planner's Bash call is one pipeline joined only by `|`. Each command is an allowed reader by bare name, with no option that writes or runs (`sort -o`, `--compress-program`, a second `uniq` file, `rg --pre`/`--hostname-bin`, `file -C`, `date -s` or a date argument, find actions other than `-print`/`-print0`). Arguments are plain words or quoted text: inside double quotes no `$`, backtick or backslash; outside quotes no glob, brace, backslash, `$`, backtick, `;`, `&`, `(`, `)`, `<`, `>` or `#`. The only redirections are `2>/dev/null` and `2>&1`. The allow-list limits writes and execution, not reads: secrets readable by the host user stay readable (the Read tool reaches them too).
- **T12. Polling and the CI waiter.**
  - For implementers and gates the guard refuses the plain polling forms with their own message: gh with `--watch`, `gh run watch`, and gh run by `watch` or in a while/until/for loop.
  - For implementers and gates it refuses every Bash command whose text, dequoted, mentions `ci-wait` in any case: a path, a launcher (`uv run`, `python3.13t`, `parallel`), a quoted argument, an assignment value, a `+=` form. No reader or option grammar is modelled; the need to read or search the waiter is met by the Read and Grep tools. So only coordinators, which have no guard, wait for CI. The waiter's own tests (`python3 -I scripts/tests/test_ci_wait.py`, underscore) stay allowed.
  - Not seen: a glob, a copy under another name, a name built inside python. That is the T1 class.
  - It does not see repeated single `gh run view` calls across tool calls, `curl` or python loops against the API, or an unfiltered `gh run view --log` (T1/T9 class); the rule is in "GitHub API budget".
  - The waiter's cache (`~/.cache/her-ci-wait`, Windows `%LOCALAPPDATA%\her-ci-wait`) is writable by any process of the host user, so a merge reads `statusCheckRollup`, never the cache.
  - `HER_GITHUB_API` accepts only `127.0.0.1`. Against it the script sends only a fixed dummy or `HER_CI_WAIT_TEST_TOKEN`, never `GH_TOKEN` or the gh login, and uses its own cache folder (`her-ci-wait-test`).

## Review and gates

- The merge gate is a Claude `ticket-reviewer` (Opus; Fable for a risk area, any size), never the implementer, a plan run or the `planner` agent; Codex does not gate. Round 1 reads the whole ticket diff, rounds 2 and 3 only the fix diff, and a ticket gets at most three rounds. Write each prompt from `docs/agents/templates/gate-prompt.md`: the diff command, the acceptance criteria, the previous findings and the `protected` paths of a Codex run's receipt, nothing else.
- Reviews check the diff and that it follows the plan; verify each finding in the code before it becomes a required fix. Gates are `merge-gate`: CI is the gate for every target it runs, and local gates run only the native list in `docs/agents/rust-validation.md`; reviews and gates apply `CODING_STANDARDS.md`.

## Flow

- Flow: ticket branch from `origin/main` → execute → review → fix round if needed → merge `origin/main` in (run `python3 -I scripts/merge-check.py` in the worktree before committing the merge; plan a semantic conflict with `docs/agents/templates/merge-plan.md`), push, open a pull request against `main` → gate (CI on the head, plus native checks) → coordinator merges the pull request when CI is green or red only by listed known red (`scripts/ci/known-red.txt`). Every push to `main` runs CI; a red `main` is fixed before the next merge. Before fixing a failing test, search open issues, the known-red list and the other host's branches for its name.

## GitHub API budget

- Limits:
  - The REST limit is 5,000 calls an hour per user account, shared by every token, `gh` login and machine on that account; GraphQL has its own per-account budget. Over it, every `gh` call fails with 403 until the hourly reset.
  - GitHub's secondary limits on bursts answer 403 or 429, with `Retry-After` or only a message. `ci-wait.py` honours `Retry-After` and otherwise waits at least one window; the baton watcher waits at least 180 s.
- The guard refuses workers' plain polling and their plain ways of running the CI waiter; coordinators follow these rules by hand.
- Only coordinators wait for CI. A worker dispatches its `quick.yml` runs once, reads their ids once and ends its message with a "CI running" handback (`implementer-protocol.md` "Test loop").
  - Start one waiter per handback, and resume the worker with its output when it exits.
  - The Windows coordinator waits for its own workers' runs while an item is in progress. Runs still open at handback go to Linux as ids, and Linux waits.
- Wait with `scripts/ci-wait.py` from the integration checkout (`/root/her`, Windows `C:/her`), started with the Bash tool's background option.
  - A worker's runs: `python -I scripts/ci-wait.py --label <n>-<run> --timeout 7200 --run <id> [--run <id> ...]`.
  - A pull request's checks: `python -I scripts/ci-wait.py --workflow checks.yml --event pull_request --sha <head sha> --timeout 7200`.
  - A handback line without an id: read the ids once with `gh run list --workflow quick.yml --branch her/<n>-<slug> --commit <sha> -L 10 --json databaseId,displayTitle`, then wait by id.
- How it saves calls:
  - Every waiter on a machine reads one cached run list per workflow file (`actions/workflows/<file>/runs?per_page=40`) in `~/.cache/her-ci-wait` (Windows `%LOCALAPPDATA%\her-ci-wait`). Several `--run` ids share it.
  - One waiter at a time refreshes the list under a file lock: at most one list call per ~100 s per workflow file, with `If-None-Match`, and a 304 costs nothing.
  - A machine-wide budget file holds the remaining calls and any block. Under 1,000 calls left, calls go every 5 min; under 200, every 15 min.
  - After a rate-limit 403 or a 429, no call of any kind is made until the reset, and at least one window passes. After a refused token (401), no call for 15 min. Any other 403 or error is retried at the next window.
  - A green quick.yml result per commit is cached and reused; checks.yml results never are.
  - Logs are fetched only for a failed run, only the first failed job's, and filtered.
- Exit codes:
  - 0 green; 1 red, followed by the failed job names and the filtered test-result and panic lines; 3 cancelled or another conclusion; 2 usage (including `--timeout` outside 0-86400 s).
  - 4 (still running when `--timeout` ran out) and 5 (GitHub unavailable or internal error) are not results: start the wait again with the `--run <id>` its last lines name.
  - With several runs or `--label`, the output ends with `[<label>]` and one `run <id>: <result>` line each. The exit is then 1 if any run failed, else 5, else 4, else 3, else 0.
- The waiter's two limits:
  - Several `--run` ids are waited for in turn, so a failure in a later id is reported only after the earlier ids finish or the timeout ends. When an early answer matters, start a separate waiter for that run.
  - A run that is no longer among the 40 newest runs of its workflow ends the whole wait: exit 2 and no summary, or exit 1 with a summary naming it "not available" when an earlier id already failed. Read it once with `gh run view <id> --json status,conclusion`, and wait again for the other ids.
- An API error is never a result: no test, CI run or gate is reported failed because GitHub did not answer.
- Never wait with `gh run watch`, `--watch`, a loop or repeated `gh run view`, and do not check what a background waiter will report.
- A merge decision reads the pull request's `statusCheckRollup` once (`merge-gate`). `ci-wait.py` only waits, and its cache is local state any process on the host can write.
- Prefer one list call over many single-item calls. Use GraphQL (`gh api graphql`) where it covers the data, such as issues and labels; Actions runs are REST only.
- Before a burst of calls, and when something returns 403, check the budget with `gh api rate_limit`; it does not count against the limit.
- Intervals: CI at least 100 s (`ci-wait.py`); the baton watcher at least 180 s (`issue_watch.py --interval`).
- If the limit is still too small, a GitHub App installed on the repository gets its own limit; a second token for the same user does not help.

## Windows coordinator

Windows (32 GB, 4 cores / 8 threads, also runs production):

- Executes only items Linux hands with `baton:windows` in the plan format (an XS/S brief, an M/L plan, an investigation run, a native or production check, or a question), same rules otherwise: it runs the item as written (executor, investigation runs), commits the run's changes to the ticket branch and pushes the branch (a Codex implement run commits and pushes itself), and runs only the native Windows checks a gate asks for (Windows-only tests, junctions, ACLs, production hotfix gates); it hands back with `baton:linux` when done or when the plan does not hold (a `?` is resolved on Linux).
- One worker session at a time; each item gets a fresh coordinator session that starts from and ends with a handoff comment.
- Native checks a gate names build via `C:/her/scripts/cargo-slot.ps1 -WorkTree <worktree>` (the integration checkout's copy): two build slots, two test slots (`docs/agents/rust-validation.md`). pi (`scripts/pi-task.ps1`) is paused.
- An M/L ticket's planning goes to the Linux coordinator ("Planner"); Windows executes the plan it gets back.
- "GitHub API budget" applies unchanged. Each host keeps its own cache (here `%LOCALAPPDATA%\her-ci-wait`), so the two hosts together make at most two list calls per window per workflow file. While an item is in progress, wait for its workers' runs from `C:/her` with the Bash tool's background option; at handback, give Linux the ids of the runs still open.
