# Coordinator

Binding for coordinator sessions; planners read "Planner" and its "Threats": the Linux main session and the Windows coordinator. The rules every agent obeys (hard limits, where ticket material goes) are in `AGENTS.md` "Subagent workflow"; who acts next and how to hand off are in `docs/agents/baton.md`.

## Role

- The coordinator is the Linux main session (Opus) and never implements: it picks ready issues (open, unclaimed, its host label and baton, blockers closed), claims them (`docs/agents/issue-tracker.md`), sizes, investigates by reading, plans and routes them, relays plans, caps fix rounds, owns every owner question, checks reports by their receipts (exit files, test-result lines, diff), runs the merge gates, merges, pushes, keeps the ticket's handoff current and closes the issue after merge. Few status turns while waiting.
- A worker returns its report as its final message; save it to the ticket's report file (`/root/orch/her/<ticket>/report-<run>.md`, Windows `C:/her-orch/<ticket>/report-<run>.md`) before acting on it.
- Hand off with `scripts/handoff.sh` / `scripts/handoff.ps1` (`docs/agents/baton.md` "Handing over"), and keep the baton watcher running between handoffs (`baton.md` "Watcher").

## Sizing

Size every ticket before routing and record the size on the ticket. Decided: can the exact change be written now (if not, `?`)? Blast radius: files and call sites (grep the symbol), crates crossed. Loop length: a single Linux test target is short; database, migration, release/pack or Windows-native loops are long. Risk area: auth and tokens, keys and release signing, ACLs and isolation, deletes or moves of user data, migrations, production.

| Size | Signals | Route |
|---|---|---|
| XS | decided, 1–2 files, one Linux test target | `ticket-implementer` on Haiku with an exact coordinator brief |
| S | ≤ ~4 files in one crate, short loop, small design call | `ticket-implementer` on Sonnet |
| M/L | several crates, long loop or real design | `planner` agent (Opus; writes `/root/orch/her/<n>/plan.md`) → Haiku executes; a part the plan cannot make exact goes back to the planner, never to Sonnet |
| ? | cause or approach unknown | investigate (Sonnet, Opus if hard), then size the resulting plan |

Record every run with `scripts/agent_usage.py record --agent <id> --ticket <n> --size <size> --host <linux|windows>` (ledger `.scratch/her-supervisor/agent-usage.jsonl`, private run data that stays untracked and is never published); after merge compare the predicted size with the measured cost and adjust the borders. The baseline and the weekly verdict live in the vault (`C:/her-vault/.scratch/her-supervisor/agent-usage.md`).

## Planner

- Planning runs on the Linux coordinator only for now: a Windows coordinator hands an M/L ticket to Linux for planning (`baton:linux`) and gets the plan back as its work item.
- The `planner` agent (`.claude/agents/planner.md`, M/L only) reads the real code, writes its exact edits into a scratch export of the base and writes the plan to `/root/orch/her/<n>/plan.md`. Those are its only writes. It never builds, formats or runs code, and returns a short summary with the plan file's `sha256sum` line and its path. Send revisions to the same agent with SendMessage.
- Before each planning round, delete and re-create the scratch export: `rm -rf /root/orch/her/<n>/scratch /root/orch/her/<n>/scratch-evidence && mkdir -p /root/orch/her/<n>/scratch && git -C /root/her archive <base> | tar -x -C /root/orch/her/<n>/scratch`. It has no `.git` and shares no refs or config with the checkout.
- When the planner reports, run `sha256sum /root/orch/her/<n>/plan.md`. It must match the line in the planner's message. Save it to `/root/orch/her/<n>/plan.sha256` and check it again with `sha256sum -c /root/orch/her/<n>/plan.sha256` before relaying the plan. A mismatch means another agent wrote the file: ask the planner again.
- Then check the scratch edits yourself. The build-file check is required, because these files run as you during the build:
  1. `(cd /root/orch/her/<n>/scratch && find . \( -name .cargo -o -name 'rust-toolchain*' -o -name build.rs -o -name Cargo.toml -o -name Cargo.lock \) | LC_ALL=C sort)` prints exactly `./her-memory/Cargo.lock`, `./her-memory/Cargo.toml`, `./her/Cargo.lock`, `./her/Cargo.toml` and `./her/build.rs`, one per line. `find /root/orch -maxdepth 3 \( -name .cargo -o -name Cargo.toml \)` prints nothing.
  2. Each of those five files matches the base: `git -C /root/her show <base>:<f> | cmp - /root/orch/her/<n>/scratch/<f>`. A file the plan changes on purpose: read its diff before building. If the tree at the base tracks other build files (`git -C /root/her ls-tree -r --name-only <base>` and the same name filter), the list follows the tree.
  3. `scripts/cargo-slot.sh <n>p /root/orch/her/<n>/scratch /root/orch/her/<n>/scratch-evidence <run> check --tests`.
  4. `/root/.cargo/bin/rustfmt --check --edition 2021 <changed .rs files>`.
  5. Send every error back to the planner.
- The executor's first step runs the red tests: Rust on its first `quick.yml` run, scripts locally.
- When the plan is accepted, delete `/root/orch/her/<n>/scratch`, `/root/orch/her/<n>/scratch-evidence` and `/root/rb-targets/<n>p`.
- Plan format and known pitfalls: Judgement parts (races, ordering, design calls) are written as exact edits too, so Haiku executes the whole plan; Haiku stops and hands back where the plan does not hold, and the planner revises it. Plan format for any handoff: (1) root cause or goal with evidence (file:line, command output); (2) the exact change per file:line, as find → replace when mechanical, or exact steps plus the commit SHA; (3) the first test to write and see fail, then the rest. Every plan ends with a "Known pitfalls" list the executor checks before reporting: processes and temp files cleaned up on every failure path (process groups killed, try opened before the first spawn); boundary cases of every threshold or limit tested on both sides; paths resolved the way the consuming tool resolves them; no stale artifacts from an earlier run; every new test seen failing for the right reason; line endings and file modes preserved.

### Threats (risk area: the agent guard)

A plan that touches the guard, the agents or the Codex form carries these threats, and each failure case becomes a required test in its plan. The guard stops plain attempts; it does not enforce. No case is left as "bounded" or "unlikely"; and, for a change to the guard or the agents, the guard is described as stopping plain attempts, never as enforcing.

- **T1. Code execution and the limits of the guard.** python and other interpreters run unrestricted for implementers and gates: through them an agent can write anywhere and read anything the host user can, including the vault checkout, `gh` credentials and, on Windows, the production host's files. For implementers and gates the guard matches parsed shell text and stops plain attempts only; the containment boundary is #85. Reviewers and planners run no interpreter: their Bash calls must fit the allow-list (T11). The planner's scratch edits would run as the coordinator's user if the coordinator's `cargo check` ran a changed `her/build.rs`, manifest or `.cargo` config, so the build-file check before every check is required.
- **T2. No ticket binding.** The hook is stateless, so a planner for one ticket can write another ticket's plan file or scratch export. Mitigation: one planner per ticket at a time. The planner's final message carries the plan file's `sha256sum` line; the coordinator compares it with its own `sha256sum` when the planner reports, and again before relaying the plan. The scratch export is re-made from `git archive` before each planning round.
- **T3. Windows path forms.** Refused: junctions and other reparse points on any part; `.git` in any NTFS spelling (`.GIT`, `.git.`, `.git ` with a trailing space); `:` in any part (streams, `::$DATA`); 8.3 names `git~N`; control characters; `\\?\`, UNC paths, other drives and a different case of `her-orch` (they fail the path pattern). An 8.3 short name of another existing folder inside scratch can only point inside scratch, so it is harmless. `C:/her-orch/…` also matches on Linux, where it is a relative path under the cwd; a write there lands inside the cwd and is harmless.
- **T4. Git metadata.** The scratch export has no `.git`, so it shares no refs or config with `/root/her`. Reviewers and planners run git only as one plain read inside an allowed pipeline, with no assignment, wrapper, `$`, backtick, glob or brace before or in it. Refused git arguments: any starting with `--out`, `--ext`, `--op` or `-O`, any holding `$`; for `git grep`, any single-dash bundle containing `O`; and the global `-c`, `--git-dir`, `--work-tree` and `--exec-path`. A `-C` into a ticket folder or a scratch export (`/root/orch/her/`, `C:/her-orch/`) is refused. `git branch` and `git remote` pass only in their listing forms. A read still runs the repository's own configured drivers; that config is the coordinator's.
- **T5. The read-only Codex self-review.** A read-only sandbox still reads the whole disk (vault checkout, credentials) and sends what it reads to the model provider. The prompt is written by the worker. Mitigation: the protocol limits the prompt to the ticket diff and forbids naming vault paths; containment is #85. The guard pins the prompt to the implementer's own `review/codex-self-<k>.md` and the workdir to its worktree. `codex-task.ps1` (Invoke-Cleanup) deletes the paths in `<Name>.cleanup.txt` under `C:/her-orch` even in a read-only run. Mitigation: a self-review writes no cleanup file, and the coordinator checks `review/` before the gate. Fix: skip that cleanup for `-Sandbox read-only` (#86).
- **T6. Concurrency.** Planners for different tickets have separate exports and separate `<n>p` targets. The coordinator runs their checks through the build slot, one at a time, which bounds memory on the 7 GB Linux host. Two planners never work on the same ticket at once. Planning runs on the Linux coordinator only, so Windows production memory is never used for a planner check.
- **T7. A restart midway.** It can leave a scratch export, `scratch-evidence` and the `<n>p` target behind. Before every export the coordinator deletes the scratch export and `scratch-evidence`. An export into a non-empty folder is not allowed, because stale files would be checked too. The `<n>p` target is reusable, and is deleted when the plan is accepted.
- **T8. Upgrade path.** The hook script is read on every call from `$CLAUDE_PROJECT_DIR`, so running agents get the new rules as soon as the main checkout pulls the merge. `git pull` replaces files by rename, so it does not break a running call. The new rules that change running agents: the Codex deny (no worker ran Codex before this change); read verbs only for reviewers (a running reviewer's `git fetch` is now refused); command-position matching (fewer false denies). The coordinator launches the `planner` agent only after the merge is pulled. An older checkout has no `planner.md`, and an unknown role is refused for every call. Through python, which the guard does not restrict for any role, an agent can still do everything T1 lists, before and after the upgrade.
- **T9. The implementer and gate denies are an approximation.** Command words are found at command positions: after unquoted newlines, the keywords `if then else elif do while until ! { function`, redirection operands, `{` and find -exec. `eval`, `builtin`, `coproc`, `source` and `.` are wrappers, and the operand of `<`, `<<<` or `<>` counts too. Comments are dropped, and quoted operators stay inside their word. Not seen: a program not on the wrapper list that runs another program (`watch`, `parallel`, `unshare`, `chroot`, `systemd-run`); a command held in a variable; brace expansion; nesting deeper than three levels; PowerShell cmdlets after `powershell -Command`. `gh-public`, `handoff` and `codex` are also refused by name anywhere in a command that has a wrapper, `$` or a backtick. This is the T1 class; #85 is the boundary.
- **T10. False denies, accepted because they fail closed.** For reviewers and planners, anything outside the allow-list is refused: `cd … &&`, a newline between commands, `>/dev/null` (only `2>/dev/null` and `2>&1` pass), unquoted globs (quote the pattern, or use the Glob tool), a path-qualified reader (`/usr/bin/git`), `rg --pretty` (the `--pre` prefix), and an apostrophe in a comment (`echo a # it's` is unparseable). For implementers and gates: a nested string that names `codex`, `gh-public` or `handoff` after a wrapper; `timeout 5 grep codex x`; heredoc body lines starting with a tool name (write such files with the Write tool); and, with a `$` in the command, any mention of `codex`.
- **T11. The read-only allow-list.** A reviewer's or planner's Bash call is one pipeline joined only by `|`. Each command is an allowed reader by bare name, with no option that writes or runs (`sort -o`, `--compress-program`, a second `uniq` file, `rg --pre`/`--hostname-bin`, `file -C`, `date -s` or a date argument, find actions other than `-print`/`-print0`). Arguments are plain words or quoted text: inside double quotes no `$`, backtick or backslash; outside quotes no glob, brace, backslash, `$`, backtick, `;`, `&`, `(`, `)`, `<`, `>` or `#`. The only redirections are `2>/dev/null` and `2>&1`. The allow-list limits writes and execution, not reads: secrets readable by the host user stay readable (the Read tool reaches them too).

## Review and gates

- Review, never by the planner or implementer: Codex in every merge gate (`gpt-6-astra` at `high` via `scripts/codex-task.ps1` / `.sh`, hidden, never `gpt-6.1-sol`); add a `ticket-reviewer` on Fable for risk areas (any size) and on Opus for other M/L work; a low-risk S ticket gets Codex only. Reviews check the diff and that it follows the plan; verify each finding in the code before it becomes a required fix. Gates are `merge-gate`: CI is the gate for every target it runs, and local gates run only the native list in `docs/agents/rust-validation.md`; reviews and gates apply `CODING_STANDARDS.md`. The self-review form is pinned (`implementer-protocol.md` "Self-review"); check that `review/` holds no `.cleanup.txt` before the gate.

## Flow

- Flow: ticket branch from `origin/main` → execute → review → fix round if needed → merge `origin/main` in, push, open a pull request against `main` → gate (CI on the head, plus native checks) → coordinator merges the pull request when CI is green or red only by listed known red (`scripts/ci/known-red.txt`). Every push to `main` runs CI; a red `main` is fixed before the next merge. Before fixing a failing test, search open issues, the known-red list and the other host's branches for its name.

## Windows coordinator

Windows (32 GB, 4 cores / 8 threads, also runs production):

- Executes only items Linux hands with `baton:windows` in the plan format (an XS/S brief, an M/L plan, an investigation run, a native or production check, or a question), same rules otherwise: it runs the item as written (executor, investigation runs), commits the run's changes to the ticket branch, pushes the branch, and runs only the native Windows checks a gate asks for (Windows-only tests, junctions, ACLs, production hotfix gates); it hands back with `baton:linux` when done or when the plan does not hold (a `?` is resolved on Linux).
- One worker session at a time; each item gets a fresh coordinator session that starts from and ends with a handoff comment.
- Builds via `C:/her/scripts/cargo-slot.ps1 -WorkTree <worktree>` (the integration checkout's copy): two build slots, two test slots (`docs/agents/rust-validation.md`). pi (`scripts/pi-task.ps1`) is paused.
- An M/L ticket's planning goes to the Linux coordinator ("Planner"); Windows executes the plan it gets back.
