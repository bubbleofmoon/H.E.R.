# Coordinator

Binding for coordinator sessions; plan runs and the `planner` agent read "Planner" and its "Threats": the Linux main session and the Windows coordinator. The rules every agent obeys (hard limits, where ticket material goes) are in `AGENTS.md` "Subagent workflow"; who acts next and how to hand off are in `docs/agents/baton.md`.

## Role

- The coordinator is the Linux main session (Opus). It picks ready issues (open, unclaimed, its host label and baton, blockers closed), claims them (`docs/agents/issue-tracker.md`), sizes, investigates by reading, plans and routes them, relays plans, caps review rounds, owns every owner question, checks reports by their receipts (exit files, test-result lines, diff), runs the merge gates, merges, pushes, keeps the ticket's handoff current and closes the issue after merge. Few status turns while waiting.
- A worker returns its report as its final message; save it to the ticket's report file (`/root/orch/her/<ticket>/report-<run>.md`, Windows `C:/her-orch/<ticket>/report-<run>.md`) before acting on it. A Codex run's report is its `<name>.report.md`.
- A fallback Claude implementer that dispatches CI returns a "CI running" handback. The coordinator dispatches CI for Codex runs and waits for all runs ("GitHub API budget").
- Hand off with `scripts/handoff.sh` / `scripts/handoff.ps1` (`docs/agents/baton.md` "Handing over"), and keep the baton watcher running between handoffs (`baton.md` "Watcher").

## Sizing

Record the size on the ticket. Use XS/S for a scoped one-crate brief and M/L for cross-crate work, a long validation loop or a design decision. Route XS/S directly to `gpt-6.2-sol` implementation and M/L to sol planning, then implementation. Investigate an unknown cause read-only with sol before sizing. Both routes require code review, CI and applicable red receipts.

Sol uses `medium` effort for implementation and fixes and `high` for planning and investigation. Escalate a step to `gpt-6.2-astra` at `high` effort when sol hands it back or repeats the same CI failure twice, including during a fix. An escalated step stays with astra.

Use the Claude fallback only on a `quota` receipt. Haiku implements, Sonnet handles escalated execution or investigation, and Opus plans M/L work or handles hard investigations. Gate rounds 2 and 3 and risk-area plan reviews fall back to a Claude `ticket-reviewer` with the same review brief. Switch providers between runs. For `timeout`, `killed` and `no-report`, read the error log, then retry or escalate.

Record every Claude subagent run with `scripts/agent_usage.py record --agent <id> --ticket <n> --size <size> --host <linux|windows>`. The ledger `.scratch/her-supervisor/agent-usage.jsonl` stays private and untracked. The baseline and weekly verdict live in the vault (`C:/her-vault/.scratch/her-supervisor/agent-usage.md`).

## Codex runs

- On the four-core Linux host with roughly 8 GB of RAM, cap concurrent Codex runs at five by default. Admit more only with measured memory headroom. Reduce concurrency under memory pressure, including pressure from other projects' builds on the same host. One CI waiter at a time is enough. Restart a stopped or killed CI waiter or watcher (Claude Code's memory reaper, the kernel OOM killer or anything else) only on the owner's go.
- The coordinator starts every Codex run, hidden and in the background, from the integration checkout (`/root/her`, Windows `C:/her`), as one plain command per run. Write the prompt from `docs/agents/templates/sol-plan.md`, `sol-implement.md`, `sol-fix.md`, `gate-prompt.md` or `plan-review.md` into `/root/orch/her/<n>/prompts/<name>.md` (Windows `C:/her-orch/<n>/prompts/`); the run's receipts land beside it. `HER_GITLEAKS=<path to gitleaks>` goes before an implement command.
  - Implement or fix: `scripts/codex-work.sh implement <name> <worktree> <prompt> [model [effort [minutes]]]` (Windows `powershell -NoProfile -File C:/her/scripts/codex-work.ps1 -Mode implement -Name <name> -WorkDir <worktree> -PromptFile <prompt>`, optional `-Model`, `-Effort`, `-TimeoutMinutes`). Defaults: `gpt-6.2-sol`, `medium`. Codex runs unsandboxed like a Claude worker, with network access and the host user's git credentials. It commits and pushes only its own `her/<n>-<slug>` branch. The brief forbids force pushes and requires the pre-push hook and public scan. The wrapper's pre-run refusals and post-run checks guard the workflow (T5). The wrapper sets `TMPDIR` to the ticket's `tmp/` (also `TEMP` and `TMP` on Windows) and passes `HER_GITLEAKS` from the command's environment.
    - Before the run, the wrapper requires a clean worktree on `her/<n>-<slug>`, `HER_GITLEAKS` set, a ticket folder and `tmp` free of links, and a response from the remote (`HER_REMOTE_URL`, default `https://github.com/bubbleofmoon/H.E.R..git`). If the remote branch exists, local HEAD must match it.
    - The brief tells Codex to push with `git push origin <branch>`. The wrapper ignores branch tracking entries in both Git config snapshots.
    - The wrapper checks the config after every run, including failures. After Codex exits 0 with a report and the config check passes, the wrapper verifies the result and writes the receipts below. A failed, quota or no-report run may leave changes in the worktree.
  - Plan with `scripts/codex-work.sh plan <ticket> <name> <prompt> [model [effort [minutes]]]`. The defaults are `gpt-6.2-sol` and `high`. Follow "Linux read-only launcher" to stage the run.
  - Investigate with `scripts/codex-task.sh <name> <checkout> <prompt> gpt-6.2-sol high read-only [minutes]`. Review with the same form and `gpt-6.2-astra`. On Windows use `codex-task.ps1 -Sandbox read-only` with the same model and effort.
- Receipts beside the prompt include `<name>.exit.txt` (the numeric code, `timeout`, `killed`, `no-report` or `quota`), `<name>.report.md`, `<name>.plan.txt` (plan: `installed` or `no-plan`; a directory or hard link is `no-plan`) and, for implement, `<name>.push.txt`, `<name>.staged.txt` and `<name>.scan.txt` (public scan output when run).
  - Before the run, `push.txt` records `pre-remote-mismatch` with exit 8 when local HEAD is ahead of, behind or diverged from the remote. After the run, line 1 records the first applicable state in this order, with exit 8 unless noted. `config-changed <files>` (T5, including failed runs), `rewritten` (pre-run HEAD is missing or fails the ancestry check), `branch-changed <branch>`, `git-failed`, `dirty <paths>` (uncommitted or untracked files), `remote-moved` (local HEAD stayed at its starting commit but the remote head changed), `no-changes` (both heads unchanged, exit 0), `unpushed` (local HEAD changed and could not be verified on the remote) or `pushed <sha>` (exit 0). After `dirty`, the next line says `remote moved` or `remote unchanged` against the branch head before the run, or `remote unknown` if the lookup failed.
  - When the commit range can be read, `protected <paths>` follows if commits touch `.githooks/`, `scripts/check-repo.py`, `scripts/scan-public.py`, `scripts/tests/test_scan_public.py`, `.gitleaks.toml` or `.public-scan.json`. The code reviewer reads each listed path in full. `scan-refused` follows with exit 8 if the public scan refused the commits or could not run (detection only, T5).
  - `staged.txt` lists the commits since the pre-run HEAD (`commit <sha> <subject>`) and the name-status of every path they touched.
  - Only `pushed` and `installed` are results; check the receipts, not the report's claims.
- Codex makes product edits and pushes the real, red and restore commits together when the step needs a red receipt. The coordinator dispatches pinned CI using `docs/agents/templates/red-revert.md`. Expected red is evidence. Send unexpected CI failures and verified review findings to a fix run from `sol-fix.md`.
- For each Rust step and OS, dispatch one batch of red-receipt targets on the pinned red SHA and one batch with `unit` and every affected integration target on the green head. Dispatch `check` and `lint` separately on the green head, in parallel. Split test batches only for different filters or to stay under the workflow's 45-minute limit, especially on Windows.
- `.claude/hooks/agent-guard.sh coordinator` is the guard role for a coordinator session that wires it (none does by default): it pins the forms above (model, effort, ticket files, the worktree's ticket branch) and refuses any other Codex call, a quoted string that starts with `codex` included.

## Linux read-only launcher

Start Linux review, investigation and planning from the coordinator's trusted checkout. The Codex wrappers above and the standalone Claude task below use `scripts/readonly-agent.py`. Each launch uses a fresh session and fails closed when isolation or model access is unavailable.

- Set `HER_READONLY_BASE` to the approved full commit ID and `HER_READONLY_INPUTS` to the approved flat input directory. Read the issue with its comments on the coordinator side and stage them as `issue.md`. Stage approved inputs such as relevant spec excerpts, prior findings, test receipts or a patch showing proposed scratch edits. Use `/inputs/<file>` in the brief. Reserve `brief.md` for the wrapper, which copies the run prompt there and passes it on stdin.
- For Claude review, run `python3 -I scripts/readonly-task.py claude review <name> <checkout> <prompt> [model [effort [minutes]]]`. For fallback planning, run `python3 -I scripts/readonly-task.py claude plan <name> <ticket> <prompt> [model [effort [minutes]]]`. Both default to Opus. Review defaults to medium effort and planning to high. Put a trusted, native `claude` or `codex` executable on the coordinator's PATH. Each wrapper captures the final report and the exit and log receipts beside the prompt.
- A review exports the committed checkout HEAD. For plan review, point the wrapper at a checkout of the plan base and stage the plan and proposed edits separately. A plan exports `HER_READONLY_BASE` from the coordinator checkout. The coordinator approves every path and commit sent into the launcher.
- The launcher resolves the native binary, applies the namespace boundary and sets up the relay before the client starts. A successful report requires a completed model response, a final primary HTTP 2xx status and a nonempty final client result. A final primary HTTP 429 records `quota` regardless of the client's exit code. A deadline expiry records `timeout`. SIGKILL records `killed` unless the final primary status was HTTP 429. Inspect the error log to distinguish missing setup from provider failure. The wrapper caps each of `out.log` and `err.log` at 1 MiB and withholds reports when either log exceeds its cap.
- `/repo` is a read-only detached checkout with the approved head's reachable Git objects and a fresh Git config. The base must be an ancestor of the head. Review the full reachable history for suitability before staging it. Unrelated refs, hooks, remotes, alternates, reflogs, local changes and the host's Git configuration stay on the host. Review mode starts in `/repo`. Plan mode starts in `/scratch`, a writable copy of the head without Git metadata. `/scratch` and `/plan-out` are backed by the ticket's `.readonly-*/run/scratch` and `.readonly-*/run/plan-out` on the coordinator's filesystem. Both modes mount `/home/agent` and `/tmp` as separate disposable tmpfs mounts capped at 64 MiB each. Treat all plan output as worker-controlled when collecting it.
- Bubblewrap requires Linux user, PID, IPC, UTS, cgroup and network namespaces, plus libseccomp and system Python with `asyncio.TaskGroup`. It mounts system binaries, system libraries and loader paths, the single public CA bundle file at `/etc/ssl/certs/ca-certificates.crt` when present, and allowlisted Codex package files read-only. The worker gets a private `/proc` and `/dev`, a loopback-only hosts file, an allowlisted environment and no capabilities. Host credentials, the vault, other tickets and host sockets stay outside. The mounted Unix socket connects only to the run's model relay. A missing prerequisite, missing key or failed boundary setup stops the run. Rejected upstream requests return errors through the relay.
- Codex uses a fresh custom Responses provider on local HTTP with SSE and WebSockets disabled. Supply a scoped OpenAI Platform API key in `HER_OPENAI_API_KEY` on the host. The relay sends that key only to `api.openai.com` on `/v1/responses` and `/v1/responses/compact`. ChatGPT login and OAuth token forwarding are unsupported. [Codex configuration reference](https://developers.openai.com/codex/config-reference)
- Claude Code uses `ANTHROPIC_BASE_URL` and a placeholder `ANTHROPIC_API_KEY` inside the worker. Supply a scoped Anthropic Console API key in `HER_ANTHROPIC_API_KEY` on the host. The relay inserts it only for `api.anthropic.com` Messages and token-count requests. Claude subscription login and cloud provider credentials are unsupported. [Claude Code gateway documentation](https://code.claude.com/docs/en/llm-gateway)
- The relay accepts only approved inference routes and uses fixed HTTPS upstreams, with no redirects, tunnels or caller authentication headers. Requests using hosted tools, remote file inputs or OpenAI stored prompt templates are refused. API-key entitlement is checked by the provider when an inference request reaches it. Repository tests use synthetic keys and a local HTTP fixture to exercise the same launcher, route checks and streaming transport.
- Windows uses the Codex CLI's sandbox setting and the role guard where wired. The PowerShell wrappers also retain `codex-work.ps1 -Mode plan` and `codex-task.ps1 -Sandbox workspace-write` with `plan-export.ps1`. Those Windows paths are outside the Linux containment boundary and retain host read and network access. Coordinator planning runs on Linux. A Windows OS boundary needs separate validation.

## Planner

- Linux plans and implements portable work, including portable changes to Windows code. Planning for host-native work also runs on Linux. A Windows handoff names an exact commit and the implementation or validation that requires the native host, or the question to answer.
- A Linux plan run reads the approved source in `/repo`, writes its exact edits into `/scratch` and writes `/plan-out/plan.md`. The planner never builds, formats or runs code. On a Codex `quota` receipt, start the standalone Claude planner for M/L work.
- Send each revision as a fresh invocation using `sol-plan.md`. Stage the previous plan, the findings and the patch of any scratch edits the new round needs. The new `/scratch` starts at the approved base every round.
- Reuse (`CONTRIBUTING.md` "Reusing code"): prefer a maintained crate over writing a well-established part; code ported from a permissively licensed project (MIT, Apache-2.0, BSD, ISC, Zlib, CC0) is allowed when no crate fits and keeps its notice in `her/THIRD_PARTY_NOTICES.md` (Apache-2.0: also the upstream NOTICE text and a mark on each changed file); never GPL-family, non-commercial or unlicensed code; the qq-bridge upstream stays clean-room (features and bugs only). Every plan and plan brief names the crate or source each step reuses.
- Fetch `origin/main` before selecting the planning base. After the worker exits successfully, the wrapper checks the isolated scratch tree and copies the nonempty, single-link regular plan file. It installs `scratch/`, `plan.md` and `plan.sha256` under the ticket directory on the coordinator. It retains the previous outputs when the worker fails or installation is refused.
- Check the `installed` receipt and run `sha256sum -c plan.sha256` from the ticket directory both after the run and before relaying the plan. Replan if the digest differs.
- Then check the scratch edits yourself. The build-file check is required, because these files run code on whichever host builds the plan, CI included:
  1. `(cd /root/orch/her/<n>/scratch && find . \( -name .cargo -o -name 'rust-toolchain*' -o -name build.rs -o -name Cargo.toml -o -name Cargo.lock \) | LC_ALL=C sort)` prints exactly `./her-memory/Cargo.lock`, `./her-memory/Cargo.toml`, `./her/Cargo.lock`, `./her/Cargo.toml` and `./her/build.rs`, one per line. `find /root/orch -maxdepth 3 \( -name .cargo -o -name Cargo.toml \)` prints nothing.
  2. Each of those five files matches the base: `git -C /root/her show <base>:<f> | cmp - /root/orch/her/<n>/scratch/<f>`. A file the plan changes on purpose: read its diff before building. If the tree at the base tracks other build files (`git -C /root/her ls-tree -r --name-only <base>` and the same name filter), the list follows the tree.
  3. Read the scratch edits against the code. No local build: the executor's first `check` and `lint` runs on CI compile and format the plan.
  4. Check affected test targets, line endings and file modes in the scratch export against what the executor will see. Confirm changed signatures list every caller, including tests and `#[cfg(windows)]` code, and name every existing test whose expected value or matched page text changes. Code used outside tests is available outside `#[cfg(test)]`. For changes at a JSON boundary, name the producer, consumer and exact expected shape, including missing and null fields where applicable.
  5. Run `HER_GITLEAKS=/root/.cache/her-tools/gitleaks/gitleaks python -I scripts/scan-public.py --root /root/orch/her/<n>/scratch` before the executor starts. Reviewed digit-run exceptions match the whole line. Reword an edited line that carried an exception so it passes without a new exception.
- Record the plan base and the files it relies on. Before relaying the plan, fetch `main` and check for overlap with those files. Re-export and revise affected steps when those files changed. Stagger concurrent tickets whose planned edits overlap.
- Before accepting a risk-area plan, send the plan, scratch paths and acceptance criteria to a read-only Codex review using `docs/agents/templates/plan-review.md`. Read its report and combine its findings with the coordinator's checks into one revision brief. Use the same brief format for coordinator findings on other plans.
- Plans that need red receipts for new Rust tests follow `docs/agents/templates/red-revert.md`. Run script tests red locally.
- Delete `scratch` and `scratch-evidence` after plan acceptance and after the executor or merge plan has consumed any referenced files.
- Plan format and known pitfalls: Judgement parts (races, ordering, design calls) are written as exact edits too, so the executor follows the whole plan; it stops and hands back where the plan does not hold, and the plan run revises it. Plan format for any handoff: (1) root cause or goal with evidence (file:line, command output); (2) the exact change per file:line, as find → replace when mechanical, or exact steps plus the commit SHA; (3) the first test to write and see fail, then the rest. Every plan ends with a "Known pitfalls" list the executor checks before reporting: processes and temp files cleaned up on every failure path (process groups killed, try opened before the first spawn); boundary cases of every threshold or limit tested on both sides; paths resolved the way the consuming tool resolves them; no stale artifacts from an earlier run; every new test seen failing for the right reason (the plan names the change that turns each new check red, as in `docs/agents/templates/red-revert.md`); a plan that adds a lock, transforms model-bound text or compares canonical forms holds to the matching `CODING_STANDARDS.md` rules ("Concurrency", "Model-facing text", "Comparisons"); line endings and file modes preserved; no step needs a commit amend, a reset or a merge (workers make plain commits only), and edited lines with reviewed scan exceptions are reworded to pass the scan.

### Threats (risk area: the agent guard)

A plan that touches the guard, the agents or the Codex form carries these threats, and each failure case becomes a required test in its plan. The guard stops plain attempts; it does not enforce. No case is left as "bounded" or "unlikely"; and, for a change to the guard or the agents, the guard is described as stopping plain attempts, never as enforcing.

- **T1. Code execution and the limits of the guard.** python and other interpreters run unrestricted for implementers and gates: through them an agent can write anywhere and read anything the host user can, including the vault checkout, `gh` credentials and, on Windows, the production host's files. For implementers and gates the guard matches parsed shell text and stops plain attempts. The Linux namespace launcher confines review and planning processes. Reviewers and planners follow the Bash rules in T11. A changed `her/build.rs`, manifest or `.cargo` config in the scratch edits runs code on whichever host builds the plan, CI included, so the build-file check before relaying every plan is required.
- **T2. Planner ticket binding.** The Linux task takes an exclusive lock on the ticket directory and gives the planner its fresh scratch and plan-output mounts. After the worker exits, the coordinator-side wrapper validates the files and installs the outputs for that ticket. The coordinator compares the installed digest before relaying the plan.
- **T3. Windows path forms.** Refused: junctions and other reparse points on any part; `.git` in any NTFS spelling (`.GIT`, `.git.`, `.git ` with a trailing space); `:` in any part (streams, `::$DATA`); 8.3 names `git~N`; control characters; `\\?\`, UNC paths, other drives and a different case of `her-orch` (they fail the path pattern). An 8.3 short name of another existing folder inside scratch can only point inside scratch, so it is harmless. `C:/her-orch/…` also matches on Linux, where it is a relative path under the cwd; a write there lands inside the cwd and is harmless.
- **T4. Git metadata.** The scratch export has no `.git`, so it shares no refs or config with `/root/her`. Reviewers and planners run git only as one plain read inside an allowed pipeline, with no assignment, wrapper, `$`, backtick, glob or brace before or in it. Refused git arguments: any starting with `--out`, `--ext`, `--op` or `-O`, any holding `$`; for `git grep`, any single-dash bundle containing `O`; and the global `-c`, `--git-dir`, `--work-tree` and `--exec-path`. A `-C` into a ticket folder or a scratch export (`/root/orch/her/`, `C:/her-orch/`) is refused. `git branch` and `git remote` pass only in their listing forms. Linux reviewers get fresh Git configuration. After a `config-changed` receipt (T5), wait for the coordinator to inspect the host repository before reading or running anything there.
- **T5. Codex runs (the coordinator's alone).** Linux reviews, investigations and plans run inside the namespace and relay boundary described above. The coordinator writes the prompt and approves the staged source and inputs. Plans have the writable `/scratch` and `/plan-out` mounts. The Windows CLI sandbox paths described above retain host reads and network access. Implement runs are unsandboxed and can write shared refs, hooks and config with the host user's permissions. The brief restricts workers to their ticket branch and requires the pre-push hook. The wrapper's pre-run refusals and post-run checks guard the implementation workflow.
  - Before and after the run, `codex-work` hashes the output of `git config --file <file> --list` for the common `config` and the worktree's `config.worktree`. It drops `branch.*` lines, treats absent files as empty and reads the entries with fsmonitor, hooks and include expansion disabled. `commondir`, the worktree's `.git` file and files under `hooks/` keep their byte hashes. A difference stops verification with `config-changed <files>` and exit 8, even for a failed run. The coordinator inspects the files before running git in that repository.
  - After the run every git call of the wrapper uses the git dir it found before the run, `core.fsmonitor=false` and `core.hooksPath` off, and reads the remote head from the fixed URL (`HER_REMOTE_URL`, default `https://github.com/bubbleofmoon/H.E.R..git`), never `origin`. Coverage excludes `<common>/config.worktree` for a linked worktree, `info/attributes` and other worktrees' config. The PowerShell wrapper also misses replacement of the common `hooks/` directory with a link.
  - After the config check, `rewritten` and `branch-changed` take precedence over commit-range failures. The wrapper observes only the ticket branch on the remote.
  - The `scan-refused` line is detection after the push: `scan-public.py` of the wrapper's own checkout (never the worktree's copy) runs on the repository's main checkout and its scan config over the new commits, with the mode the pre-push hook uses (`--added-from-stdin`, or `--revs-from-stdin` for a branch the remote did not have, plus `--objects-from-stdin`). It cannot undo a publication, and a run can still publish unseen by it: with `git push --no-verify`, with another hook or `core.hooksPath` set for its own commands, by pushing a URL other than `origin` or a ref other than its branch, or text outside the commits (an issue, a comment). The pre-push hook inside the run is the only barrier before publication. `codex-task.ps1` (Invoke-Cleanup) deletes the paths listed in `<Name>.cleanup.txt` within `C:/her-orch` and `C:/her-targets` in every mode. Sandboxed modes keep `prompts/` outside their writable roots. Unsandboxed implement runs can write the cleanup list. Read-only cleanup is tracked in #86. The guard's `coordinator` role pins the forms only when a session wires it.
- **T6. Concurrency.** Follow the Linux host capacity rule in "Codex runs" for Codex concurrency and CI waiters. Planners for different tickets have separate exports. Two planners never work on the same ticket at once. Planning runs on the Linux coordinator only.
- **T7. A restart midway.** It can leave a scratch export and `scratch-evidence` behind. Before every export the coordinator deletes both. An export into a non-empty folder is not allowed, because stale files would be checked too.
- **T8. Rule changes reach running agents.** The hook script is read on every call from `$CLAUDE_PROJECT_DIR`, so a change to its rules applies as soon as the main checkout pulls the merge; `git pull` replaces files by rename, so it does not break a running call. An unknown role is refused for every call. Through python, which the guard does not restrict for implementers and gates, an agent can still do everything T1 lists.
- **T9. The implementer and gate denies are an approximation.** Command words are found at command positions: after unquoted newlines, the keywords `if then else elif do while until ! { function`, redirection operands, `{` and find -exec. `eval`, `builtin`, `coproc`, `source`, `.` and `watch` are wrappers, and the operand of `<`, `<<<` or `<>` counts too. Comments are dropped, and quoted operators stay inside their word. Not seen: a program not on the wrapper list that runs another program (`parallel`, `unshare`, `chroot`, `systemd-run`); a command held in a variable; brace expansion; nesting deeper than three levels; PowerShell cmdlets after `powershell -Command`. `gh-public`, `handoff` and `codex` are also refused by name anywhere in a command that has a wrapper, `$` or a backtick. This is the T1 class; #85 is the boundary.
- **T10. False denies, accepted because they fail closed.** Where the review or planner hook is wired, its allow-list refuses: `cd … &&`, a newline between commands, `>/dev/null` (only `2>/dev/null` and `2>&1` pass), unquoted globs (quote the pattern, or use the Glob tool), a path-qualified reader (`/usr/bin/git`), `rg --pretty` (the `--pre` prefix), and an apostrophe in a comment (`echo a # it's` is unparseable). For implementers and gates: a nested string that names `codex`, `gh-public` or `handoff` after a wrapper; `timeout 5 grep codex x`; an apostrophe in a comment (`echo a # it's` is refused as unparseable); heredoc body lines starting with a tool name (write such files with the Write tool); and, with a `$` in the command, any mention of `codex`. From the CI-waiter rule: for implementers and gates every Bash command whose text mentions `ci-wait` is refused, wherever the name stands (a path, a quoted argument, an assignment value, `+=`, a worktree path such as `her-wt/90-ci-wait`, `git log --grep 'ci-wait'`, `cat scripts/ci-wait.py`, `echo ci-wait`), so searching or reading the waiter goes through the Grep and Read tools. A quoted argument starting with `watch` (`--search "watch it"`) makes the command count as having a wrapper, so the name rules above apply to it. A quoted argument that is itself a gh polling command (`--search "gh run watch"`) is refused as polling.
- **T11. The read-only allow-list.** A reviewer's or planner's Bash call is one pipeline joined only by `|`. Each command is an allowed reader by bare name, with no option that writes or runs (`sort -o`, `--compress-program`, a second `uniq` file, `rg --pre`/`--hostname-bin`, `file -C`, `date -s` or a date argument, find actions other than `-print`/`-print0`). Arguments are plain words or quoted text: inside double quotes no `$`, backtick or backslash; outside quotes no glob, brace, backslash, `$`, backtick, `;`, `&`, `(`, `)`, `<`, `>` or `#`. The only redirections are `2>/dev/null` and `2>&1`. The hook applies this list where wired. The Linux launcher controls what the entire worker process can read. On Windows, the Read tool can still reach files readable by the coordinator.
- **T12. Polling and the CI waiter.**
  - For implementers and gates the guard refuses the plain polling forms with their own message: gh with `--watch`, `gh run watch`, and gh run by `watch` or in a while/until/for loop.
  - For implementers and gates it refuses every Bash command whose text, dequoted, mentions `ci-wait` in any case: a path, a launcher (`uv run`, `python3.13t`, `parallel`), a quoted argument, an assignment value, a `+=` form. No reader or option grammar is modelled; the need to read or search the waiter is met by the Read and Grep tools. So only coordinators, which have no guard, wait for CI. The waiter's own tests (`python3 -I scripts/tests/test_ci_wait.py`, underscore) stay allowed.
  - Not seen: a glob, a copy under another name, a name built inside python. That is the T1 class.
  - It does not see repeated single `gh run view` calls across tool calls, `curl` or python loops against the API, or an unfiltered `gh run view --log` (T1/T9 class); the rule is in "GitHub API budget".
  - The waiter's cache (`~/.cache/her-ci-wait`, Windows `%LOCALAPPDATA%\her-ci-wait`) is writable by any process of the host user, so a merge reads `statusCheckRollup`, never the cache.
  - `HER_GITHUB_API` accepts only `127.0.0.1`. Against it the script sends only a fixed dummy or `HER_CI_WAIT_TEST_TOKEN`, never `GH_TOKEN` or the gh login, and uses its own cache folder (`her-ci-wait-test`).

## Review and gates

- Round 1 covers the whole ticket diff. On Linux start the standalone Claude reviewer (Opus or Fable for a risk area). Rounds 2 and 3 cover the fix diff and unresolved required findings. Use the Codex review command under "Codex runs" and the standalone Claude reviewer on quota. On Windows use the Claude `ticket-reviewer` role and the PowerShell review wrapper. Fill `docs/agents/templates/gate-prompt.md` for each round and read the report beside the brief.
- Verify each finding in the code before requiring a fix. After round 3, the Claude coordinator verifies remaining narrow fixes against the last reviewed head and blocks merge while any required finding remains.
- `merge-gate` verifies the hosted `checks` jobs on the final pull-request head and the required native receipts under `issue-tracker.md` "Pull requests and merging" and `rust-validation.md`. Code review applies `CODING_STANDARDS.md`.

## Flow

- Cut the branch from `origin/main`, implement, validate and review. Integrate the current `origin/main` before opening or updating the pull request. Run `python3 -I scripts/merge-check.py` in the worktree before committing the merge and use `docs/agents/templates/merge-plan.md` for semantic conflicts. Push only if the exact head needs publishing, then gate and merge under `issue-tracker.md` "Pull requests and merging". Before fixing a failing test, search open issues, the known-red list and the other host's branches for its name.

## GitHub API budget

- Limits:
  - The REST limit is 5,000 calls an hour per user account, shared by every token, `gh` login and machine on that account; GraphQL has its own per-account budget. Over it, every `gh` call fails with 403 until the hourly reset.
  - GitHub's secondary limits on bursts answer 403 or 429, with `Retry-After` or only a message. `ci-wait.py` honours `Retry-After` and otherwise waits at least one window; the baton watcher waits at least 180 s.
- The guard refuses workers' plain polling and their plain ways of running the CI waiter; coordinators follow these rules by hand.
- Only coordinators wait for CI. Codex reports pending targets after pushing. During quota fallback a Claude implementer may dispatch unpinned batches, reads the IDs once and ends its message with a "CI running" handback (`implementer-protocol.md` "Test loop").
  - Queue handbacks according to the Linux host capacity rule in "Codex runs". Resume each worker with the waiter's output when it exits.
  - The Windows coordinator waits for its own workers' runs while an item is in progress. Runs still open at handback go to Linux as ids, and Linux waits.
- Wait with `scripts/ci-wait.py` from the integration checkout (`/root/her`, Windows `C:/her`), started with the Bash tool's background option.
  - A worker's runs: `python -I scripts/ci-wait.py --label <n>-<run> --timeout 7200 --run <id> [--run <id> ...]`.
  - A pull request's checks: `python -I scripts/ci-wait.py --workflow checks.yml --event pull_request --sha <head sha> --timeout 7200`.
  - Wait for pinned runs by run ID. If an ID is missing, list the dispatch ref once with `gh run list --workflow quick.yml --branch her/<n>-<slug> --commit <dispatch ref tip> -L 10 --json databaseId,displayTitle` and match the full title, including `sha=<red-sha>` for a pinned run. The run's head SHA identifies the dispatch ref tip.
- How it saves calls:
  - Every waiter on a machine reads one cached run list per workflow file (`actions/workflows/<file>/runs?per_page=40`) in `~/.cache/her-ci-wait` (Windows `%LOCALAPPDATA%\her-ci-wait`). Several `--run` ids share it.
  - One waiter at a time refreshes the list under a file lock: at most one list call per ~100 s per workflow file, with `If-None-Match`, and a 304 costs nothing.
  - A machine-wide budget file holds the remaining calls and any block. Under 1,000 calls left, calls go every 5 min; under 200, every 15 min.
  - After a rate-limit 403 or a 429, no call of any kind is made until the reset, and at least one window passes. After a refused token (401), no call for 15 min. Any other 403 or error is retried at the next window.
  - A green quick.yml result per commit is cached and reused; checks.yml results never are.
  - Logs are fetched only for a failed run, only the first failed job's, and filtered.
- Exit codes:
  - 0 green; 1 red, followed by the failed job names and the filtered test-result and panic lines; 3 cancelled or another conclusion; 2 usage (including `--timeout` outside 0-86400 s).
  - 4 (still running when `--timeout` ran out) and 5 (GitHub unavailable or internal error) are not results: start the wait again with the `--run <id>` its last lines name.
  - With several runs or `--label`, the output ends with `[<label>]` and one `run <id>: <result>` line each. The exit is then 1 if any run failed, else 5, else 4, else 3, else 0.
- The waiter's two limits:
  - Several `--run` ids are waited for in turn, so a failure in a later id is reported only after the earlier ids finish or the timeout ends. Put runs that need an early answer first.
  - A run that is no longer among the 40 newest runs of its workflow ends the whole wait: exit 2 and no summary, or exit 1 with a summary naming it "not available" when an earlier id already failed. Read it once with `gh run view <id> --json status,conclusion`, and wait again for the other ids.
- An API error is never a result: no test, CI run or gate is reported failed because GitHub did not answer.
- Never wait with `gh run watch`, `--watch`, a loop or repeated `gh run view`, and do not check what a background waiter will report.
- A merge decision reads the pull request's `statusCheckRollup` once (`merge-gate`). `ci-wait.py` only waits, and its cache is local state any process on the host can write.
- Prefer one list call over many single-item calls. Use GraphQL (`gh api graphql`) where it covers the data, such as issues and labels; Actions runs are REST only.
- Before a burst of calls, and when something returns 403, check the budget with `gh api rate_limit`; it does not count against the limit.
- Intervals: CI at least 100 s (`ci-wait.py`); the baton watcher at least 180 s (`issue_watch.py --interval`).
- If the limit is still too small, a GitHub App installed on the repository gets its own limit; a second token for the same user does not help.

## Windows coordinator

Windows (32 GB, 4 cores / 8 threads, also runs production):

- Accepts Linux handoffs with `baton:windows` at an exact commit for host-native implementation, a native or authorized production check, or a question. Follow the handoff, then return the receipts or answer to Linux with `baton:linux`. Portable work stays with Linux.
- One worker session at a time; each item gets a fresh coordinator session that starts from and ends with a handoff comment.
- Native checks a gate names build via `C:/her/scripts/cargo-slot.ps1 -WorkTree <worktree>` (the integration checkout's copy): two build slots, two test slots (`docs/agents/rust-validation.md`). pi (`scripts/pi-task.ps1`) is paused.
- "GitHub API budget" applies unchanged. Each host keeps its own cache (here `%LOCALAPPDATA%\her-ci-wait`), so the two hosts together make at most two list calls per window per workflow file. While an item is in progress, wait for its workers' runs from `C:/her` with the Bash tool's background option; at handback, give Linux the ids of the runs still open.
