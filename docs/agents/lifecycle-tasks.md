# Lifecycle, owner gates and tasks

Read for supervisor startup/stop, desired state, task dispatch or task-store persistence.

- `scheduled_task.rs` owns the single Windows logon task `HER`. `her-cli install [--install-root <absolute root>]` registers it for the caller's Windows SID with InteractiveToken/HighestAvailable, three one-minute failure restarts and no execution time limit. Its action is `<install>/current/her.exe supervise --runtime-root <install>/runtime --install-root <install>` with the current link as working directory. The GUI subsystem makes startup hidden; no script dispatches the supervisor. Installation registers the task only; release deployment/current-link selection is separate.
- One task interface installs, reads, compares and removes; `her-cli scheduled-task read|compare|remove` exposes inspection and explicit removal. Compare exits 0 on a match, 3 on drift or an unreadable definition. The native adapter reads registered XML through Task Scheduler COM as a UTF-16 BSTR, independent of the console/OEM code page. Install imports BOM-marked UTF-16 XML through hidden `schtasks.exe`; removal is hidden too. Native errors use numeric HRESULTs, never localized output text. Only file/path-not-found from task lookup counts as missing. `HER_TASK_SCHEDULER_FILE` explicitly selects a file fake guarded as a development output, with strict UTF-8/UTF-16 XML decoding; a fake never falls back to the real scheduler. Startup records `scheduled-task-check` in the runtime run record and uses `admin_alert::notify_notice` for missing, changed or unreadable definitions; it reports drift without repairing the task. Registration metadata, XML formatting and schema defaults do not constitute drift.
- Principal and LogonTrigger `UserId` elements compare by Windows SID, resolving account names with `LookupAccountNameW` and parsing SID strings with `ConvertStringSidToSidW`; unresolved names remain drift. Other values retain their existing schema/default comparison rules.
- Tests never register `HER` or `QQBot-*`. The sole real-adapter round trip requires elevation and a GUID `HER-Test-*` name, does not trigger the task, and removes only that task even after assertion failures. Without elevation it states why the native round trip was skipped. All other task tests use a file or in-memory fake.
- Startup notices persist the last admitted drift fingerprint in `data/scheduled-task-drift.json` through `RuntimeContext::write_atomic`. Fingerprints cover normalized expected/actual definitions (including differing values), or the missing/unreadable condition. Repeated starts with the same fingerprint stay quiet; changed drift alerts again. A matching check atomically clears the fingerprint, so recurrence alerts again. The existing administrator notice limiter and fire-and-forget delivery still apply; unreadable state or failed persistence is recorded as `scheduled-task-drift-state`.
- The supervisor independently polls QQ login state every 30 seconds, including while the bridge is unavailable. `data/qq-login-episode.json` stores the active episode, confirmed delivery and next retry under the runtime authority gate. A claim is notified only after successful private delivery; failures, unavailable QQ and limiter skips stay pending across restarts and confirmed login recovery. Attempts are at least one minute apart across restarts and use the existing notice budget (ten per hour). Confirmed login rearms detection; an undelivered notice is retained until delivery or coalesced into a new login-needed episode. Unknown observations preserve the claim. State read/write failure refuses a new attempt. A crash or lost delivery reply can cause a later retry; no delivery acknowledgment is inferred from admission. Native QQ focus and logout-capable Windows notifications belong to the desktop client.

- `release.rs` owns release discovery. `update.feedUrl` defaults to `https://api.github.com/repos/bubbleofmoon/H.E.R./releases`; the feed uses GitHub release-list JSON. Release tags are `vX.Y.Z`, compared numerically, and must equal the authenticated version in the signed checksum list. `update.policy` accepts `off`, `notify` (default) or `auto`. `her-cli release check --runtime-root <absolute root>` uses that setting and returns current/available release metadata. Off performs no release request. The existing runtime/install-root guards apply before configuration access. HTTPS is required except for loopback HTTP fixtures; transfers run hidden with bounded time and size.

- Signed release lists are mandatory. The newest otherwise eligible release must carry exactly one `SHA256SUMS.minisig`, a detached Minisign Ed25519 signature over the exact `SHA256SUMS` bytes (including BOMs and line endings). Check authenticates before offering the release; install fetches and authenticates again before downloading any image or creating its staging directory. A failed discovery check clears cached availability and pending approval. Installed images retain both files; handover admission and the fixed helper authenticate again before reading/executing candidate images. Checksums are bounded to 1 MiB and signatures to 4 KiB on network and disk. Missing, malformed, oversized, wrong-key and invalid signatures refuse with a content-free reason and an administrator alert through the existing notice/update-alert paths; unsigned fallback is never allowed.
- v0.1.0 is the first signed HER release; installations predating it (unsigned or old-format metadata) are unsupported. `SHA256SUMS` contains exactly one signed identity line, `# HER-RELEASE vX.Y.Z N`, and one signed key-set line, `# HER-KEYS <primary-base64> <backup-base64>`. `N` is nonzero and cannot decrease relative to current; changing keys requires a greater generation. Authenticated version must match the feed/directory and be newer than current for candidate admission. The effective keys and version/generation floor come from the current release's stored list and signature, re-verified with its own signed key set at use. Image hashes are verified at installation and every candidate, rollback or recovery execution boundary; cache/status reads re-verify bounded metadata without repeatedly reading executable images. Compiled pins bootstrap only an installation with no versioned `vX.Y.Z` release folders (redirected ones included) and no retained selection link; non-versioned local/bootstrap folders, including the invoking image's, and unpublished private staging do not count. Missing or invalid current metadata is lost selection: derive authority from the newest independently verified recorded selection (last-good, its retained previous link, or the lost current retained by an interrupted switch's previous link), otherwise the newest installed release with verifiable signed metadata. A current link that still names a release whose metadata no longer verifies keeps that release's version as an extra floor for check and install. A current link deleted outright records no floor; authority then comes from last-good, so a validly signed release between last-good and the lost current stays admissible. If none verifies, refuse discovery/install before feed or image acquisition. Reads (status, cache stamps and the supervisor's one-second poll) never write alerts. Check/install admission (CLI, the supervisor's discovery check, install) records one content-free update alert (`failed` current tag or `unselected`, `restored` `unchanged`, rollback `preserved`). An admission alert never replaces an undelivered alert, nor a `pending` rollback alert while another process holds the update-restore gate (rollback holds it throughout; with the gate free the pending alert is stale and admission replaces it). Helper, handover and crash-recovery refusals always record their alert, replacing any earlier one. Invalid current metadata with successfully recovered authority records one such alert naming current, reason `current release metadata unverifiable; using verified installed authority`, which is also the cached discovery error after a successful feed check. The supervisor records a refusal once per new cached discovery error and a lost current once per lost tag under the same authority, across feed failures and its own installs; each CLI `check`/`install` invocation is a separate admission and may record it again once a previous alert was delivered. Interrupted current-link publication uses the same recovered authority until the helper repairs the links. No separate generation/proof state exists: losing, recreating or restoring unrelated state cannot reset current's authority. Staging never advances authority while current remains verified.
- `her/src/release_signature.rs` is the single compiled primary/backup trust anchor for her, her-cli and herupdate. **Replace before v0.1.0:** both production pins are disposable placeholders with no retained private halves; the owner must supply real public keys. The owner alone keeps the real private keys offline; no private release key belongs in this repo, CI or runtime configuration. Synthetic fixture keys are public test data under `her/tests/fixtures/release-signing/`, enabled only by `cfg(test)` or the debug-only `release-test-keys` feature; the package build script rejects it for release profiles or any nonzero optimization level independently of debug assertions, in addition to the compile-time no-debug-assertions guard. `minisign-verify` handles verification; licence choice and upstream notices are in `her/THIRD_PARTY_NOTICES.md`.
- Key rotation puts the replacement primary/backup set inside the signed checksum list. The transition signer must be trusted by current (or the compiled bootstrap pins) and retained in the replacement set, allowing that release to re-verify its own metadata. With a valid current selection, its set becomes effective only when it becomes current; lost-selection recovery follows the installed-authority rule above; running an older binary does not restore older pins. Keep compiled bootstrap pins consistent across all three shipped images. A later transition can rotate the retained key. Feed fields, unsigned files, runtime configuration and environment variables cannot introduce keys. Last-good retains its own authenticated key set and remains an eligible fallback even after a higher-generation candidate is selected.
- The install root is the trust boundary. Installed metadata self-vouches by design: a release's stored list is re-verified with its own signed key set, and there is no separate trust store, so whoever can write `<install>/releases` can install trusted metadata. Per-file writes inside the install root are inside this boundary too: images are verified by hash and then executed by path, so a writer who replaces a verified image before it starts runs code as HER. Keep the install root writable only by the HER account and administrators. The fixed helper published at `<install>/herupdate.exe` is exactly the verified buffer, never a second read.
- Recovery by hand: a missing or unrunnable current `her.exe` records no starts, so nothing requests recovery automatically. Start the fixed root helper hidden as `<install>/herupdate.exe --recover --target <current tag> --old-pid <pid> --old-start <start> --old-exe <current her.exe>` with the install root configured, taking the identity from `runtime/data/logs/rbridge-supervisor.lock.owner.json` (an exited identity reads as gone). It re-verifies last-good, retires only identity-checked owners and restores last-good.

- `her-cli release install --runtime-root <absolute root>` downloads the newest eligible release and returns `installed: {tag, path}`. The release-manager `install(context, release)` interface accepts metadata returned by `check_feed`. Installation requires unique `her.exe`, `her-cli.exe`, `herupdate.exe` and `SHA256SUMS` assets, verifies all three image hashes, and publishes `releases/<tag>` by renaming a private staging directory. The exact checksum file stays beside the images. Failed staging removes only its own directory; under the installation lock, later installers recover abandoned directories in the reserved .staging-her-release-v1-<pid>-<milliseconds>-<sequence> namespace. Other entries and current/last-good releases are preserved. An occupied tag is refused, including repeat installs. The intended installation's `runtime/data/locks/update-restore.lock` (independent of an external configuration runtime) and persistent `releases/.install.lock` serialize installs with restore and other installers. Staging does not change current, last-good, the root updater, runtime configuration or dependencies; trial/handover and pruning are separate.

- Installed supervisors check releases immediately and every six hours; legacy/development runtimes opt in with an explicit `update` block. The release worker reloads settings without restart and runs independently of ordinary task/lifecycle scheduling. `off` issues no release requests. Version-3 `data/releases.json` persists the feed, last admitted check time, available metadata, error and notified tags under `data/locks/release-check.lock`. Check admission is saved before network I/O, so failures and supervisor restarts retain the six-hour cadence. Version-1/2 discovery caches and cached approvals are discarded on load; version-3 caches bind to the exact selected or recovered authority identity, signed metadata and key set (compiled pins only at empty bootstrap). Discovery retains the authority used for verification; if current changes before publication, discard its result and repeat discovery. Cache publication rechecks under the install/restore gate, and never stamps an old result with fresh authority. Feed changes reset discovery; availability is hidden for off, a different feed or a release no newer than current.
- `her-cli release handover --runtime-root <install>/runtime --tag <installed tag>` explicitly admits an already staged release. The release-manager `handover(context, tag)` interface leaves approval and staging-idle policy to its caller. It verifies the installed images and current supervisor identity, publishes the candidate's helper at `<install>/herupdate.exe` and starts it hidden from the install root. The helper holds the install/restore gate through trial and judgment, retires the old HER owners through the candidate CLI, waits on PID/start, switches current and starts the new supervisor hidden. It invokes the candidate's assert-running for up to 120 seconds; each probe receives the shared five-second snapshot allowance bounded by the remaining judgment deadline. Only a passing post-switch check advances last-good. Interrupted previous/pending link publication is recovered under the install/restore gate before requiring either link. Crash startup can locate last-good through its retained previous link to publish the independently verified helper. A missing last-good link is initialized to current after the passing trial and verification of current as rollback authority. A retirement failure after any owner was stopped restarts eligible verified last-good and records an alert; missing or invalid rollback metadata preserves current selection and alerts instead; a failure before any stop preserves the old owners. Retirement exits 3 after a partial stop, and the helper also rechecks captured owner identities after a failed or timed-out retirement child.
- Before retiring owners, the helper re-verifies last-good's own stored checksum list, signature, signed version/key set and all three image hashes. Last-good is initialized and durably selected before retirement when needed, including the retirement-to-current-switch crash window. Rollback and crash recovery repeat those checks before stopping, switching or starting anything; crash recovery publishes last-good's verified helper; rollback retirement runs the failed release's own CLI while its metadata and images still verify and otherwise the already verified last-good's, without executing unverified images; a legitimately installed last-good remains eligible irrespective of current's key generation. Missing or invalid last-good signed metadata/images preserve current selection and alert, leave stopped owners stopped and never execute an unverified image. Missing current image files do not block identity-checked retirement through last-good. There is no unsigned migration or external proof store. Release files are fsynced before publication; Unix directory entries are fsynced after release, state/helper and link renames.
- Failed switch/start/health rolls back to eligible verified last-good after retiring only verified HER owners. The helper records `<install>/update-alert.json` before rollback and records whether restoration completed. The installed supervisor's release worker claims that alert under `runtime/data/locks/update-alert.lock`, waits for bounded administrator-notice delivery and retries unconfirmed delivery at least one minute apart, including across restarts and with update policy off. The helper finishes rollback status in an alert-gated read-modify-write for the same alert ID, preserving concurrent retry deadlines and delivery completion. The helper performs no release-feed or QQ I/O. Runtime configuration, desired state, dependency pins/homes and dependency processes are unchanged by handover.
- Installed current supervisor starts are recorded before runtime configuration is loaded in `<install>/update-starts.json`, serialized under `runtime/data/locks/update-starts.lock`. Three starts in a rolling ten-minute window without a passing shared health check request the fixed helper's `--recover` path. An already active helper observes the same history; it retries exited new supervisors within the original 120-second judgment deadline. Health clears that release's history. A duplicate launch while a supervisor owner is held does not count.
- Update recovery bookkeeping applies to published `vX.Y.Z` current releases. Non-versioned local/bootstrap folders remain valid installed supervisor locations under the existing install-root guard and keep their ordinary startup behavior; they are not installed releases, so a first `release install` from one in an installation without versioned releases or selections uses the compiled pins.
- After success or rollback, the helper prunes ordinary direct `vX.Y.Z` release directories by numeric version, keeping the newest three and always preserving current and last-good even if older. Unknown files/directories and reparse entries are left alone. `<install>/herupdate.exe --prune --install-root <install>` explicitly repeats cleanup under the same install/restore gate; it performs no trial or process starts. No updater runs from a directory being pruned.
- Notify saves a durable tag claim before calling `admin_alert::notify_notice`, retaining it for admitted or uncertain delivery. A definite non-admission (including a full queue or hourly cap) removes the claim durably; later polls retry pending availability, including after restart and without another feed request. Unknown delivery is never retried. Policy/feed edits are rechecked after I/O before notification. `GET /api/releases` returns availability/current/settings/check metadata without network I/O. `GET/POST /api/releases/settings` reads/edits policy and feed URL, refuses agent credentials and preserves unrelated raw configuration. Writes hold the existing configuration gate, recheck credentials, and use atomic config persistence. The Schedule page edits policy and shows availability; the main runtime-supplied console page receives a polling banner. `POST /api/releases/approve` requires `confirm:true` and the displayed `tag`. Approval is serialized with discovery in `data/releases.json`, binds the current version and feed, and is consumed by the supervisor through the existing install and handover interfaces. Approval also requires the install/restore gate to be free, refusing overlapping attempts while a helper is active. A changed feed, off policy or changed current version invalidates a pending approval; admission/install errors appear as `updateError`, while failures after retirement use the existing rollback alerts. Already staged candidates are verified before retry. Auto admits only while the turn ledger has no begun, attempted, running, paused or unfinished reattaching turn. Unreadable ledger state defers installation. `locks/turn-update.lock` is shared for the complete selected-runtime pipeline, including final reply delivery, and exclusive during auto staging. After the read-only trial, the helper waits up to 120 seconds for exclusive turn admission before retiring any owner and retains it through judgment/rollback; that fence survives the old supervisor. A busy or unreadable gate refuses retirement. Automatic launches carry `--auto` through the fixed helper to the candidate retirement CLI, which rechecks the same durable idle predicate under the helper-owned fence immediately before stopping owners. Non-idle or unreadable state leaves all old owners running and records deferral in `updateError`; the automatic attempt remains spent until the next discovery check or explicit approval. Manual approval drains active pipelines without requiring the durable turn ledger to be idle. New turns await admission asynchronously; chat epochs and reserved authority are rechecked after the wait. Queued preparation before ledger begin is not an in-flight turn. Auto attempts once per admitted six-hour discovery check; an administrator can explicitly retry earlier. Dependency pins are outside this path.

- Each runtime role holds one OS file lock for its whole lifetime: data/logs/rbridge-live.lock, rbridge-console.lock, rbridge-supervisor.lock. Locks are never deleted/truncated/replaced. Age never proves ownership. Holder markers publish role plus pid/start/exe, acquisition/refresh times and groups atomically; failed publication releases the gate. Held unidentified owners cannot be displaced. Acquisition retries only within its bound.
- The HER rename preserves established runtime filenames (including legacy log/lock names), database schemas and contents, managed MCP block markers/IDs and retired Scheduler task identifiers. Executable paths use `her`/`her-cli`; no data migration occurs.
- Selected live processes also hold host source gates for endpoint/conversation ownership. Source transition gates remain held by live processes. A second selected root cannot use the same gateway/conversation concurrently.
- `process_identity` owns OS identity, full inspection, configured program/script matching, instance liveness and verified kill; lifecycle re-exports preserve existing owner-marker callers. Owner markers retain PID, OS creation stamp and executable. Full inspection additionally reads cwd and argv. Limited-rights liveness compares PID/start without requiring cwd, argv or image access; unreadable processes stay unknown. Verified kill pins the process handle (pidfd on Linux) and rechecks PID/start/image; mismatch or unreadable identity refuses termination. Lifecycle stop observes owner-gate release after termination.
- Read-only diagnostics use `her-cli process identify|match|check --pid <id> --runtime-root <root>`. `match` requires an absolute `--program` and optional `--script`; relative entries resolve against cwd, falling back to the program folder only when the cwd candidate is absent. Only the interpreter's entry operand counts; npm/npx launchers report `wrapper` and confer no dependency ownership. `process_identity::resolved_script` exposes the resolved entry for descendant classification, excluding launchers and eval. Unknown switches or unreadable paths stay unknown. `check --start <OS stamp>` reports `matches`, `gone`, `mismatch` or `unknown` without full inspection.
- lifecycle status/set and stop-supervisor are retained operator interfaces. Status/stop work with broken config. Stop-supervisor requires an explicit stopped revision, holds lifecycle/ordinary-task gates, retires verified live/console owners before the supervisor and waits for free owner gates. Owners must match the role and caller image or its resolved HER console/GUI sibling in the same directory. Stop authorization and OS identity checks precede writing stopped desired state; owner checks repeat before exact PID/start/image verified kills. Missing/unknown/mismatched identity refuses.
- `her-cli lifecycle assert-running --runtime-root <absolute root> [--wait <duration>]` polls the shared `health_check::check` verdict without starting, stopping or repairing anything. Gate validation and probing never create directories or lock files; missing gates/directories are failed observations. Exit 0 requires every part to pass; exit 1 is an unhealthy JSON verdict, including unavailable runtime contents; exit 2 is malformed CLI syntax (including a missing/relative root or invalid duration). Syntax is validated before inspecting runtime contents. Durations are nonnegative integers in milliseconds (`ms`), seconds (`s`, or no suffix), minutes (`m`) or hours (`h`). Omitted/zero wait takes one snapshot with a five-second probe budget. Positive wait is a total monotonic deadline, including unavailable roots/data and network calls; retries pause at most 100 ms and each snapshot gets at most five seconds. Configuration and desired state are reread each snapshot.
- Assert-running stdout is one JSON object: `{"v":1,"ok":false,"parts":{"desired":{"verdict":"pass","reason":"desired state is running"},"supervisor":{"verdict":"fail","reason":"supervisor owner is not held"},"console":{"verdict":"fail","reason":"console is not healthy"},"snowluma":{"verdict":"fail","reason":"SnowLuma is not healthy"},"dsh":{"verdict":"fail","reason":"DSH is not healthy"},"dshLogin":{"verdict":"fail","reason":"DSH login could not be checked: DSH did not answer"}}}`. Each part always has `verdict` (`pass`/`fail`) and a nonempty safe `reason`; `ok` is true exactly when all parts pass. Unknown observations fail. Consumers select parts by name and allow additional parts and fields. `dshLogin` passes only when DSH accepts a freshly minted cookie (one rejection is refreshed and retried once) and fails after two rejected fresh cookies in a row with a reason naming the likely causes. Reasons explain the observation and are not a parsing interface.
- Health requires effective desired state running, a held supervisor owner with the correct role and verified PID/start/image (either sibling HER image), a successful console `/api/health` matching the selected held console owner, SnowLuma `get_status` reporting `status:ok`, `online:true`, `good:true`, the configured relay passing its authenticated models probe, and DSH answering the existing `settings/describe` probe. Endpoints and DSH credentials come only from the selected runtime. A DSH RPC refusal still proves it answered, per dependency recovery; authentication refusal fails. The health check never calls a model or sends a QQ message.
- Health owner-image authorization accepts only the checker's own executable or its same-directory HER twin. An updater judging a release invokes that release's `her-cli`; a fixed-root updater image is not itself an authorized health caller for another release.
- A read-only trial invokes the candidate `her-cli lifecycle assert-running` with `HER_TRIAL_CURRENT` identifying the selected install root's resolved current release. Only an installed caller can use that health authority, and only current's verified HER owners can pass it. Adoption and process-control authorization do not use the trial authority. The candidate does not take owner gates or dispatch turns/jobs beside the existing supervisor. This trial proves candidate-checker compatibility with current; candidate-supervisor startup health is judged only after the switch.
- The supervisor reconciles every new desired-state revision, including running-to-running writes, so a stopped/running restore shorter than a scheduler tick still starts the bridge.
- Desired state is data/lifecycle/desired-state.json: running/stopped/maintenance plus by/reason/at/until/revision. Writes hold lifecycle.lock for at most five seconds and append intent/applied audit entries. Conditional updates check expected revision under that gate. Missing/expired maintenance means running; unreadable means unknown and starts/stops nothing. Explicit writes preserve corrupt input aside. Running wants live/console/jobs; maintenance console only; stopped nothing. Stop/maintenance require confirmation; exit 3 means unknown/unwritten desired state.
- lifecycle guard runs a bounded local maintenance command under desired-state and all owner gates while stopped. Confirmed session reset preserves unknown document fields and creates verified backup/audit.
- Selected live startup calls session_map::verify_cutover to validate existing ownership receipts and fences. Its verification helpers reject redirected or oversized files; its path helper can create a missing legacy logs directory.
- Watchdog decides/applies from explicit mcpRustBridge, distinct nonempty rustGroups and valid consolePort. Two bad heartbeats (90-second freshness, live and same groups) are counted per owner identity. Console starts only on a free port; scope changes use verified stop and observed gate release before replacement. Unknown desired state, locks, markers, console probes or heartbeats start/stop nothing.
- Registry: watchdog every two minutes/internal; memory-digest 03:00; memory-digest-check every 30 minutes at :21/:51; backup daily at backup.time (default 04:00); upstream-check 05:00/disabled by default; console-restart manual. Retired report and start-all dispatch are unavailable. tasks.<id>.enabled, nodePath, installRoot and limits control dispatch/storage. Legacy Windows task names in the console are informational; HER installation never changes them.
- Schedules use local wall clock (UTC+8 unless UTC/GMT), run late slots once and never catch up missed slots. Desired state holds jobs. Ordinary jobs use Unix groups or Windows jobs. Dependencies are supervisor-owned startup decisions with hidden, file-backed child stdio and no kill-on-close ownership; ordinary stop, crash and replacement leave them running.
- Dependency launch configuration is config.json `dependencies.snowluma` and `dependencies.dsh`, each with absolute `program`, `script`, `workingDirectory`. Existing explicit `tasks.nodePath` and `tasks.start-all.{snowLumaDirectory,dshScript,dshWorkingDirectory}` remain readable as path configuration only. No configured dependencies means no dependency launch. Endpoints come from selected dependencies.json (`onebot`, `dsh`), must be distinct loopback HTTP origins, and never confer process ownership. DSH launches as `<program> <script> web --no-open`, with DSH_HOME fixed to selected runtime/user/dsh pending the switchover decision (#20); SnowLuma receives SNOWLUMA_HOOK_AUTOLOAD=1. A pinned DSH program or script under an npx cache (`_npx` path component, including its canonical path) is refused. An unpinned legacy npx install remains usable with one warning per supervisor process; switchover adds the pin.
- The permanent model relay (CLIProxyAPI) is opt-in as `dependencies.relay`: absolute `program`, string-array `arguments`, absolute `workingDirectory`, exact `version`, absolute `loginDirectory` and `clientKeyFile`. Its origin is selected `dependencies.json`'s optional `relay`, a plain loopback HTTP origin on a port distinct from OneBot and DSH. The administrator installs the declared pin in `<dependencies.directory>/relay/<version>`; the directory defaults to `<install root>/deps` only for `<install root>/runtime`, as for managed DSH. Program, working directory, login directory and key file must stay in that version folder without symlinks/reparse points. File operands in arguments (including `--config=<path>`) stay in the pin folder; parent traversal and redirected operands are refused. Arguments never contain inline client keys. The supervisor does not download relay binaries or migrate logins. Existing runtimes without relay configuration retain their launch behavior.
- Initial startup ensures SnowLuma, then the configured relay, then DSH. A relay HTTP refusal or unknown response defers initial DSH startup even when the relay port listens; established dependencies heal independently. Relay adoption requires exact program, arguments, working directory and PID/start/image. It uses the shared 5/30/60-second crash backoff, outage notices and explicit dependency-stop rules; ordinary HER stop and release handover preserve it.
- Relay readiness and shared health use only `GET /v1/models` with the selected client key in an Authorization header, with a bounded deadline, direct loopback socket and no redirects or model calls. HTTP 200 proves readiness. HTTP refusals and timeouts fail health; only connection refusal contributes to the shared two-minute hang timer. The optional `relay` health part reports `pinnedVersion`. Neither response bodies nor headers are included in diagnostics.
- Before relay launch/adoption, the supervisor restricts the entire version folder (including configuration, key and login files) to the HER process account. Unix requires owned regular files/directories without external hardlinks and removes group/other access. Windows applies only `DACL_SECURITY_INFORMATION | PROTECTED_DACL_SECURITY_INFORMATION`, using the process token SID, with one full-control allow ACE and no inherited ACEs on every existing file/directory. Directory ACEs include object/container inheritance so future login/refresh files and subdirectories inherit only the HER ACE; the next preparation protects those entries too. Read-back verification requires protection, exactly that SID/ACE, access mask and inheritance flags; a failed apply/read/verification defers initial DSH startup. Ownership is unchanged: preparation requires WRITE_DAC and read-back requires READ_CONTROL, never WRITE_OWNER, SeRestorePrivilege or SeTakeOwnershipPrivilege. No SYSTEM or Administrators ACE is needed: Scheduler launches the supervisor as the HER account (including Interactive/Limited), and the relay uses that account; Scheduler's service identity does not read relay credentials. ACL diagnostics identify the affected file, native step and Win32 failure code; verification mismatches name the violated condition. Relay stdout/stderr are discarded because upstream diagnostics may contain credentials. Login contents, client keys and upstream text never enter HER alerts, status or evidence; ACL failure diagnostics may include the affected filesystem path. Native Windows ACL and hidden-start proof uses a throwaway installation; interim task/directory removal and production changes are separate Windows work.
- Pinned versions: `dependencies.<name>.version` is one exact release version (`1.14.22`, `0.2.1-rc.2`; no ranges, tags, build metadata or leading zeros in numeric prerelease identifiers). Assert-running reports it as `pinnedVersion` on the `snowluma`/`dsh` part (and `relay` when configured); an invalid pin fails that part. SnowLuma's pin is the administrator's declaration for the configured install, used in place until an approved upgrade replaces its entry and working folder. A pinned DSH works in runtime/dsh/work (a configured `workingDirectory` is refused). With a configured `script`, that install is used in place only when its canonical entry belongs to the nearest enclosing package, `@deepseek-ai/dsh`, at the pin. Canonical program/package/entry paths cannot enter `_npx`; managed bin entries must stay in that package, excluding nested node_modules packages. Without `script`, DSH is managed: `<dependencies.directory>/dsh/<version>` (default `<install root>/deps` only when the runtime is `<install root>/runtime`), whose `@deepseek-ai/dsh` package must be the pinned version; its `bin` entry (`dsh`, or the only one) is the script. A reminder is marked run when the hub claims it, so a crash between the claim and its queued wake loses that run rather than repeating it (at most once). The hub claims a reminder only for a conversation it could run now: not while DSH is down (unless a CLI is pinned for it), and not while a wake of that conversation is queued, parked for DSH, held or waiting for a retry, so an outage ends with one late run, not a burst. Finished items are compacted to the 200 most recently finished, except items finished in the last 24 hours and any item finished in the same write, which are never dropped; the cap is therefore exceeded temporarily while they are recent, so a claimed reminder's text is still there when its wake runs. A reminder cancelled after its claim reaches HER as cancelled. System jobs keep the tasks scheduler's slots. HER's sleep, reply-check and reach-out timers are published by the reserved2 hub to `data/schedule-timers.json` when they change and at least every 60 s; a snapshot older than 120 s is shown as stale with no actions. When the cancels cannot be read, the hub tick defers the due reply checks and reach-outs until a tick can read them, so a cancelled one does not fire on that tick; the residual is that incoming traffic handled outside the tick can still fire a cancelled timer if the store turns unreadable just after the cancel was saved (harmless: no message is sent to anyone for it). Cancelling a reach-out skips that chance: the next one is armed from it, never re-rolled from now. System jobs offer pause, resume and run (each needs `confirm: true`; an action a job does not offer answers 409 before confirmation) and no edit or cancel. Reminders offer pause, resume, edit, cancel and run. Sleep offers edit, cancel and run; reply check and reach-out offer cancel and run only, and HER's timers cannot be paused. Run now on a timer is an admin wake (reason `timeout`, `replyCheck` or `proactiveCheck`). A due reminder is delivered as the wake `reminder:<id>` only to a conversation the reserved2 hub schedules, and waits while that hub is suspended; a pinned CLI receives the reminder content in its text-only prompt. Hub store errors are logged at most once a minute. The page is `/schedule` (alias `/tasks`); History holds the task run history beside the reminder history, and a run's log shows below both tabs.
